# Мануал — SynchrotronSim (командный справочник)

Все команды — из корня проекта. Интерпретатор — **`py -3.14`** (в нём numpy, pandas, pyvista, scipy,
matplotlib). Диффурное ядро — бинарь `build\SynchrotronTracker.exe`, оптимизатор —
`build\SynchrotronOptimizer.exe` (собираются из `src/` через CMake).

> **То же самое мышкой:** `gui.bat` (или `py -3.14 gui_app.py`) — графическая оболочка над всем
> конвейером ниже. Она ничего не считает сама, а запускает эти же команды и показывает их вывод,
> поэтому результаты совпадают. См. **§12**.

> **Linux / macOS.** Везде ниже вместо `py -3.14` пишите `python3` (лаунчер `py` — только Windows),
> вместо `gui.bat` — `./gui.sh`. Бинари собираются без суффикса (`build/SynchrotronTracker`), код
> подставляет его сам через `_common.exe_name`. Каталог исходных карт ANSYS лежит вне репозитория и
> задаётся переменной `SS_ANSYS_DIR` (по умолчанию — путь рабочей машины). Единственное, чего нет
> вовсе, — ярлык `make_shortcut.py` (`.lnk` — формат Windows).

**Установки в БД:** `1` — СИЛА, полное кольцо (2082 магнита, замкнутое); `2` — Сибирь (сторонний
импорт, 144 магнита); `3` — SP1, первый супериод СИЛЫ (53 магнита). Эксперименты `1`/`2`/`3` ссылаются

## 1. Проверка и замыкание .lte

**`lte_ring.py`** — универсальный инструмент, работает по ПУТИ к файлу, ничего не знает про имена
папок и установок.

```powershell
py -3.14 lte_ring.py ring.lte                                  # один файл с LINE=(...) — только отчёт
py -3.14 lte_ring.py desc.lte --line line.lte                  # последовательность отдельным файлом
py -3.14 lte_ring.py desc.lte --line line.lte --out fixed.lte  # записать замкнутую копию
py -3.14 lte_ring.py ring.lte --beamline RING --out fixed.lte  # выбрать линию, если их несколько
```

Без `--out` ничего не пишет. Форматы определяются по содержимому: голый список токенов в отдельном
файле (СИЛА), `NAME: LINE=(&...)` внутри файла (Сибирь, elegant); разворот с вложенностью, `n*ELEM`, `-SUB`.

**Что проверяет:**
- **Σ ANGLE** по кольцу — замыкание по УГЛУ (нужно ровно 2π).
- **Замыкание по ПОЛОЖЕНИЮ** — прогон всей линии **с дрейфами**, зазор конец→начало. Это ОТДЕЛЬНОЕ
  условие: угол свести мало, кольцо может не сойтись в точку.
  ⚠️ Мерить «выход последнего магнита → вход первого» **нельзя** — на стыке стоит законный длинный
  дрейф (`RING` начинается с `DR_01_2P651` = 2.651 м), и такой замер даёт метры мнимого зазора.
- **δ = E1+E2−ANGLE** — константность внутри группы (тип+длина). Если разошлась, сборка БД упадёт
  в `build_matrix_db.add_edge_delta`.

**Чем замыкает:** масштабирует ANGLE **и E1/E2** чистых диполей (без K1) на
`close_scale = (2π − Σ ANGLE_DQ) / Σ ANGLE_pure`; combined-function (K1≠0) не трогает. Края обязаны
ехать тем же множителем, иначе δ перестаёт быть константой типа.

### Приведение чужого .lte к плоскому виду (`lte_flatten.py`)

Файлы установок приходят в разном синтаксисе: многострочные определения через `&`, вложенные линии,
повторители `38*CELL`, МАТРИЧНЫЕ типы элементов (`SBEN/QUAD/SEXT/OCTU`), служебные элементы (импеданс,
апертура, ВЧ, WATCH). Загрузчик `s2lattice_to_db` ждёт одно определение на строку и одну развёрнутую
линию `ring: LINE=(...)`, а сверка с elegant — КИКОВЫЕ типы (иначе elegant считает элемент матрицей и
`N_SLICES` на него не действует). `lte_flatten.py` делает и то и другое за один проход.

```powershell
py -3.14 lte_flatten.py вход.lte --list                        # какие линии есть в файле
py -3.14 lte_flatten.py вход.lte --beamline R                  # только отчёт (состав, периметр, зазор)
py -3.14 lte_flatten.py вход.lte --beamline R --out workspace/lte/configuration_vN/имя.lte
```

Переводит `SBEN/RBEN/BEND → CSBEND`, `QUAD → KQUAD`, `SEXT → KSEXT`, `OCTU → KOCT`,
`EDRIFT/DRIFT → DRIF`; `KQUSE` (квад+секступоль) оставляет как есть, а `KQUAD` с `K2` переводит в `KQUSE`
(у `KQUAD` в elegant нет `K2`). Ставит `N_SLICES` (`--n-slices`, по умолчанию 5); выбрасывает то, чего нет в
матричной модели (ВЧ, апертуры, импеданс, заряд, WATCH) и печатает, что именно. Мультиполи `K1…K3`
переносит у ЛЮБОГО типа, у `CSBEND` ещё дробную форму `F1…F3` + `XREFERENCE`; прочие ненулевые параметры
(`K4+`, `G1…G8`, `J1`, `DX`, `FSE`, файлы мультиполей…) попадают в отчёт «не перенесено параметров».
Силы и углы НЕ трогает — замыканием занимается `lte_ring.py`.

⚠️ **Готча продолжений строк.** `&` в конце переносит ТОЛЬКО следующую строку; пустая строка обрывает
определение — так читает сам elegant. Если склеивать `&\s*\n\s*` (с `\s`, который ест переводы
строк), определение съедает соседние и часть элементов теряется.

### Импорт плоского .lte как новой решётки

```powershell
py -3.14 s2lattice_to_db.py --lte workspace/lte/configuration_v5_sila2026/sila2026.lte `
    --lattice 26 --exp 26 --prefix "sila26_"
```

`--prefix` — префикс имён устройств (по умолчанию `s2_`), `--n-slices` — срезы в строке решётки
(по умолчанию 40), `--monitors` — заводить `MONI` как датчики положения (`kind=monitor`, устройство
`BPM`) — по умолчанию выключены. Опыт импорта получает явные плоскости по умолчанию (`exp_planes.default_planes`:
кольцо — старт в середине шва, финиш пуст; линия — вход первого и выход последнего элемента).

**Мультиполи у любого магнита.** Поле от формы полюсов (секступоль в DQ или квадруполе, градиент
секступоля, октуполь изгиба) задаётся в `.lte` обычными `K1`/`K2`/`K3` у ЛЮБОГО типа (`KQUAD`, `KQUSE`,
`KSEXT`, `KOCT`, `CSBEND`) и пишется в `mat_G`/`mat_S`/`mat_O` — всегда АБСОЛЮТНЫМИ, у всех видов (прежнее
правило «у `dipole` `mat_G` — доля `mat_B`» отменено). У `CSBEND` можно задать и дробную форму elegant:
`F1…F3` при `XREFERENCE` (доли дипольного поля на радиусе `XREF`, профиль поля там `1 + F1 + F2 + F3` —
формат «гармоники карты на опорном радиусе»), импорт переводит её в `K_n += F_n·n!/XREFⁿ·ANGLE/L`. Изгиб
с `K1` помечается видом `dq` (метка; физика у `dipole` и `dq` одна — секторное тело). `KSEXT` без поля (все
`K = 0`) — слот корректора, `kind=kicker`. Что импорт НЕ переносит (`K4+`, `B1…B8`/`USE_BN`, `F4+`,
`G1…G8`, `J1`, `TILT≠0`, `DX/DY`, `FSE*`, `HKICK/VKICK`, строковые вроде `SYSTEMATIC_MULTIPOLES="…"`), он
печатает сводкой `[!] параметр … не учитывается`; элементы неподдержанных типов (`MULT`, матричные
`QUAD/SBEN…` без `lte_flatten`) — тоже с предупреждением, т.к. их длина выпадает из геометрии. `!` в строке
определения — комментарий. Края `E1/E2` переносятся со знаком угла: `edge = −E` (в БД `θ0 = −ANGLE`).

**Фриндж диполя (мягкий спад поля на торцах)** задаётся в `.lte` как в elegant — параметрами CSBEND
`HGAP` (полузазор, м), `FINT` (форм-фактор спада), `FINT1`/`FINT2` (отдельно вход/выход). Импорт
считает длину зоны спада каждого торца `L_f = ∫b(1−b)ds = 2·HGAP·FINTi` и пишет её в `lattice_configs`
столбцами `lf1`/`lf2` (м; столбцы появляются при первом `.lte` с ненулевым `HGAP`). Умолчания — elegant:
`HGAP=0` (эффект выключен), `FINT=0.5`, `FINT1/FINT2 = −1` ⇒ берётся `FINT`; `EDGE1_EFFECTS=0`/
`EDGE2_EFFECTS=0` выключают грань целиком (и угол, и фриндж). Ядро (Python и C++) меняет только
ВЕРТИКАЛЬНУЮ линзу грани: `py −= tg(E − ψ/(1+δ))/ρ·y`, `ψ = L_f/ρ·(1+sin²E)/cos E`; горизонталь
остаётся `tg E/ρ`. Это метод elegant `EDGE_EFFECTS=1, EDGE_ORDER=1` (по умолчанию); на другие методы
импорт печатает предупреждение. Совпадение с elegant на одиночном CSBEND — до 1e-13 по добавке к y′.
⚠️ У диполя, нарезанного на куски с РАЗНЫМИ именами, `HGAP` на всех кусках даёт фриндж и на внутренних
стыках (там спада поля нет): ставьте `FINT2=0` у предыдущего куска и `FINT1=0` у следующего.
`lte_flatten.py` переносит эти параметры, сохраняя значимые нули (`FINT=0`, `FINT1=0`, `EDGE*_EFFECTS=0`).

## 2. Загрузка конфигурации в БД

**`load_config.py`** принимает ПУТЬ (папку или файл):

```powershell
py -3.14 load_config.py --list                                     # что лежит в workspace/lte/
py -3.14 load_config.py workspace/lte/configuration_v1_closed --force
py -3.14 load_config.py path/to/desc.lte --line path/to/line.lte --force
py -3.14 load_config.py path/to/ring.lte --lattice 2 --force       # сторонний плоский .lte
py -3.14 load_config.py --config v1 --force                        # короткое имя (удобство)
py -3.14 load_config.py <путь> --parse-only                        # только разбор, БД не трогается
```

| Формат | Определяется по | Пайплайн |
|---|---|---|
| **desc+line** | `*_desc.lte` + `*_line.lte` | `lte_to_lattice` → `assemble_lattice_configs` → `build_matrix_db` → `warmstart_ring` → `assemble --sync-subs` |
| **плоский** | один `.lte` с `LINE=(...)` | `s2lattice_to_db` |

- `--force` обязателен, если решётка уже есть: полная загрузка **сбрасывает `mat_*` к проектным K**
  из `.lte` (бэкапы → `workspace/tables/backups/`).
- **Конфигурации сосуществуют.** Загрузка объявляет СВОИ решётки (сама + суб-решётки из
  `sub_lattices.json`) и передаёт их вниз через `--lattices`; строки чужих установок переносятся как
  есть, со всеми столбцами. Раньше каждая загрузка СИЛЫ стирала Сибирь — теперь нет.
- **Порядок конвейера важен:** он обязан заканчиваться `assemble_lattice_configs.py --sync-subs`.
  `assemble` создаёт суб-решётки в начале, когда `mat_*` ещё пусты, а заполняют их следующие шаги и
  только у родителя — без финального шага суб-решётка остаётся с нулевой физикой.

### Отдельные шаги (вызывает load_config, можно и вручную)

| Команда | Что делает |
|---|---|
| `lte_to_lattice.py [--lte-dir DIR]` | `.lte` → `sp_elements.csv` (шаблон супериода) + `lattice_layout.csv` (геометрия экземпляров). Существующие `arg_val` сохраняются. |
| `assemble_lattice_configs.py` | Шаблон + геометрия → `lattice_configs.csv`. Запускать после правки `sp_elements.csv`. |
| `assemble_lattice_configs.py --sync-subs` | Суб-решётки = копия родителя со всеми столбцами. ПОСЛЕ warmstart. |
| `build_matrix_db.py [--lte-dir DIR] [--lattices 1,3]` | Структурные столбцы, края E1/E2 и δ из `.lte` папки `DIR`, связность. `--lattices` — какие решётки можно перезаписывать. |
| `warmstart_ring.py N [--lte-dir DIR]` | `mat_*` решётки N = проектные K из `.lte`. |
| `lte_to_design_orbit.py` | `.lte` → сегменты опорной орбиты (для оптимизатора). |
| `s2lattice_to_db.py --lte <файл> --lattice N --exp M` | Импорт стороннего плоского `.lte`. |

## 3. Откуда ядра читают конфигурацию

**Оба ядра читают `lattice_configs.csv`** — матричное (`matrix_tracker.py:186`) и диффурное C++
(`src/main.cpp:174`, по индексам столбцов). Это и есть «большая таблица»: строка на каждый экземпляр
магнита, со своей геометрией и коэффициентами. `element_connectivity.csv` задаёт **порядок** обхода.

```
.lte → lte_to_lattice → sp_elements.csv   (ШАБЛОН: слот в супериоде, правится руками)
                      → lattice_layout.csv (геометрия каждого экземпляра)
                           ↓ assemble_lattice_configs
                      → lattice_configs.csv   ← ОБА ЯДРА ЧИТАЮТ ЭТО
                           ↓ build_matrix_db  (структурные столбцы, края)
                           ↓ warmstart_ring   (mat_* = проектные K)
                           ↓ assemble --sync-subs
```

⚠️ **Адресные правки в `lattice_configs.csv` живут до следующей пересборки.** `assemble` берёт
`arg_val`/`correct_coeff` из ШАБЛОНА по ключу `(sp_type, sp_element_id)` — то есть все супериоды
получают одно значение слота, — а `mat_*` следом перезаписывает `warmstart`. Сценарий рабочий:
«собрал → поправил руками → посчитал», просто не перезагружать `.lte` после правок. Сохранение
per-instance правок между пересборками сознательно не делалось (решение 2026-07-17: не усложнять БД).

### Библиотечный загрузчик: `synchrotronsim.db` и модель `Machine`

Единый слой чтения БД для новой библиотеки (шаг 1 `docs/LIBRARY_ARCHITECTURE.md`); формат таблиц тот же.

```python
import synchrotronsim as ss
db = ss.open_db()                      # корень проекта; работает из любой текущей папки
m = db.machine(26)                     # Machine: instances (строки БД), elements (магниты), devices, groups,
                                       #   cavities, kickers, bpms, screens, meta; m.fingerprint — sha256
m.elements.kind, m.elements.mat_G      # столбцы numpy, только чтение; обмотки: m.elements.members(i)
db2 = ss.open_db(overlay=ws_dir)       # ws_dir — папка errors.perturbed_workspace: её таблицы главнее
```

Магниты `m.elements` совпадают с `matrix_tracker.build_line` бит-в-бит (склейка обмоток по совпадающим
строкам x, y, z; фолбэки L_eff/kind/n_slices на тип; `mat_Gv` пусто ⇒ `mat_G`); `n_slices = 0` — «из
настроек опыта». В модели СИ (экраны мм/мрад → м/рад, `rot_*_deg` → рад, `field_pct` → доля); `arg_val` «-»
и пустые ячейки — NaN. Паспорт установки (`m.meta`: энергия, ВЧ, суперпериоды) — из
`synchrotronsim/machines.py` (бывший `facility_report.LATTICE_INFO`; правьте там). Тест — `TestDataModel`.

## 4. Трекинг

```powershell
py -3.14 track3.py --author-only --exp 20 --lattice 1 --group 3    # только строка опыта (установка+пучок; плоскости — exp_planes)
py -3.14 track3.py --mode kick-phys --exp 1 [--turns N] [--thin ε_мм] [--local]
py -3.14 track3.py --mode kick-phys --exp 1 --long --turns 10000 --sr --rf ideal   # излучение + затухание
py -3.14 track3.py --mode diff      --exp 1
```

Установка и пучок берутся из `experiments.csv[exp]`; `--lattice`/`--group` переопределяют (и создают
строку опыта, если её нет). Траектории (ГЛОБАЛЬНЫЕ X,Y,Z) → `workspace/results/trajectories_expN.bin` —
их пишет **только `track3.py`**, поэтому после любой правки физики прогоните его заново, иначе визуализатор
покажет старое.

### Конфигурация опыта: плоскости, пучок, портал, резонаторы

Опыт задаётся **явно** — двумя плоскостями и пучком в рамке старта (`beam_injection.py`, C++ `matrix_ring.h`,
диффур `src/exp_config.h`; все ядра читают одно и то же):

| таблица | столбцы | смысл |
|---|---|---|
| `experiments.csv` | `start_x;start_y;start_z;start_nx;start_ny;start_nz` | старт-плоскость: точка (= начало локальных координат пучка) и нормаль (направление пролёта) |
| | `finish_x … finish_nz` | финиш-плоскость; **пусто ⇒ финиш = старт (кольцо)** |
| `particle_groups.csv` | `group_id;part_id;m;q;x;xp;y;yp;ct;delta` | частицы в рамке старт-плоскости, СИ: x, y — смещения; xp = dx/ds, yp = dy/ds (как elegant); ct — начальное t; δ = (p − P0)/P0 |
| `rf_cavities.csv` | `cavity_id;lattice_id;x;y;z;nx;ny;nz;volt_share;note` | ВЧ-резонаторы **установки**: плоскость и доля напряжения (пусто — 1/N); тип/V/h/фаза — по-прежнему `radiation_params` опыта |
| `pulsed_kickers.csv`, `kicker_timing.csv` | см. «Импульсные кикеры» ниже | импульсные кикеры установки и их импульсы в опыте |

- **Рамка плоскости:** ось = нормаль, u — горизонталь (нормаль, повёрнутая на +90° в XY), v = n×u. Ядро плоскость
  не подправляет — `modified_drift` переводит состояние между любыми рамками точно. Плоскость на опорной орбите
  с нормалью вдоль неё ⇒ x, y — отклонения от опорной. Каноника ядра: px = (1+δ)·xp/√(1+xp²+yp²).
- **Положение в линии** (`locate_plane`): промежуток между элементами (включая шов кольца), где опорная прямая
  пересекает плоскость по направлению нормали; иначе луч до первого / после последнего элемента. Плоскость
  внутри элемента — ошибка.
- **Оборот = пролёт старт → финиш.** Плоскости совпадают — кольцо (полный оборот). Разные — **разомкнутая
  система с порталом**: состояние на финише (в его рамке) — вход следующего пролёта на старте (тот же кортеж
  x, px, y, py, t, δ). `--turns N` у разомкнутой линии теперь работает (раньше — только 1 пролёт). «Невязка»
  разомкнутой линии — скачок на портале |финиш − старт|.
- **Резонатор — плоскость.** Резонаторы установки встают в свой промежуток пути (узел нулевой длины: дрейф до
  плоскости, кик, дрейф дальше). Нет строк у решётки ⇒ ВЧ в конце пролёта (как всегда было); резонатор в плоскости
  финиша (у кольца — старта) — тоже конец пролёта; вне пути старт → финиш — пропускается с предупреждением (если
  на пути нет ни одного — ошибка). Правила: **ideal** — после резонатора у частицы ЗАДАННАЯ энергия
  `radiation_params.rf_ideal_energy_mev` (пусто — проектная, δ = 0), какой бы она ни прилетела: можно стартовать
  с любой энергией, на резонаторе она станет заданной (у разомкнутой линии с порталом частица восполняет потерянное); **sine** — часы ВЧ: внутри пролёта t — «сырой» путь, на
  резонаторе запаздывание τ = t0 + Σ Δt_raw/β − (s_c/L)·C_RF, ΔE = V·share·sin(φ + 2πh·τ/C_RF), в конце пролёта
  t ← t0 + Σ Δt_raw/β − C_RF (отрезки между резонаторами). φ — фаза, которую видит опорная частица; auto —
  π − asin(U0/V). Без резонаторов внутри формулы дословно прежние (бит-в-бит).
- **Аналитическое кольцо и кокпит** (`ring_analysis.Ring`, `ring_cpp.CppRing`, сервер `--ring-serve`) берут те же
  резонаторы по `lattice_id`: кик на резонаторе в своём промежутке (оборот, ELEM и срезы PIECES — одиночный
  пролёт применяет резонаторы внутри пути, иначе 6D-орбита после резонатора неверна), в конце оборота — только
  резонатор в плоскости наблюдения. Резонаторы входят в отпечаток кэша откликов только когда они есть.
- **Сверка с elegant:** `elegant_diag.write_lattice(rf=dict(…, at_s=[s, …], shares=[…]))` ставит RFCA в точки s
  линии, разрезая дрейф. СИЛА (реш. 1), резонатор в середине кольца: δ(s) замкнутой 6D-орбиты совпадает до 1e-8
  (размах «пилы» 3,3e-4, скачок δ на резонаторе = U0/E), x(s) до 1e-9 м, Qs одинаков.

```powershell
py -3.14 exp_planes.py --show --exp 26                       # где стоят плоскости, кольцо/линия, резонаторы на пути
py -3.14 exp_planes.py --exp 26 --start-s 0                  # старт в шве (s = 0 — середина шва кольца), финиш пуст
py -3.14 exp_planes.py --exp 3 --start-s -0.5 --finish-after QF1J#2 --finish-d 0.1   # разомкнутая линия
py -3.14 exp_planes.py --cavity --lattice 26 --s 556.76 [--share 1] [--id 1] [--note "резонатор"]
py -3.14 exp_planes.py --cavity-remove 1 --lattice 26
```

`exp_planes.py` ставит плоскость на опорную орбиту в промежутке (точка + нормаль вдоль орбиты) по дуге s (кольцо:
s = 0 — середина шва, по модулю периметра; линия: s = 0 — вход первого элемента) или «ЭЛЕМЕНТ[#k] + d». Миграция
старых таблиц (глобальные XYZ/скорости, p1..p3/dir) — `migrate_explicit_planes.py` (разовая, с резервной копией):
старт = плоскость пучка (центр, направление), финиш отрезка — прежний финиш матричного ядра или p-плоскость Boris.

### Импульсные кикеры (инжекция, выпуск, «пинг»)

Импульсный кикер — тонкий дипольный удар, **амплитуда которого зависит от времени прихода частицы**. Это не
стационарный корректор `kind=kicker` (слоты SH, `orbit_correct.py`): тот — элемент решётки с постоянным полем,
этот — плоскость нулевой длины в промежутке пути, как резонатор. «Железо» — у установки, импульс — у опыта:

| таблица | столбцы | смысл |
|---|---|---|
| `pulsed_kickers.csv` | `kicker_id;lattice_id;x;y;z;nx;ny;nz;shape;duration_s;rise_s;note` | кикер **установки**: плоскость (точка + нормаль), форма импульса `half_sine` или `trapezoid`, длительность основания (с), фронт = спад трапеции (с; 0 — прямоугольник) |
| `kicker_timing.csv` | `exp_id;kicker_id;theta_x_rad;theta_y_rad;delay_s;period_s;note` | импульс **в опыте**: пиковый удар по x и y (рад), начало импульса от старта опыта (с), период (с; пусто — один импульс). Несколько строк одного кикера — несколько импульсов, удары складываются |

- **Удар** (как elegant `BUMPER` при L = 0): px += θx·f(τ), py += θy·f(τ) в канонике, то есть x' += θ/(1+δ) —
  поле задано для опорного импульса. t и δ удар не меняет. f: `half_sine` — sin(π·τ/D) на [0, D]; `trapezoid` —
  линейный фронт, плато, линейный спад; вне импульса — 0; с периодом τ берётся по модулю периода.
- **Время:** τ = T/c − delay, T — абсолютное время опыта в c·t (м) с момента, когда опорная частица пересекла старт
  на пролёте 0. Начально T = `ct` частицы; дальше копится Δt_raw/β(δ) по отрезкам между узлами (кикеры и
  резонаторы), портал мгновенный — время идёт дальше. β — по проектной энергии опыта (`radiation_params`,
  нет строки — 6000 МэВ), как у ВЧ; с sine-ВЧ T = n·C_RF + t, кикер синхронен ВЧ.
- **Место:** кикер в промежутке пути — удар после дрейфа до его плоскости; в плоскости финиша (у кольца — старта)
  — в конце пролёта; в старте разомкнутой линии — в начале пролёта; вне пути — пропускается с предупреждением.
- **Где работает:** трекер опытов — `track3.py --mode kick-phys` (полный и `--long`), `long_trajectories`,
  `local_trajectories`, C++ `MatrixTracker --track/--full` (печатает кикеры на пути). Аналитическое кольцо, кокпит,
  сервер `--ring-serve`, невязка опыта и диффур Boris кикеры не видят. Кикер без строки в `kicker_timing` у опыта в
  путь не встаёт — опыт считается бит-в-бит как без него.

```powershell
py -3.14 exp_planes.py --kicker --lattice 26 --after QF1J#2 --d 0.2 --shape half_sine --duration 2e-6
py -3.14 exp_planes.py --fire --exp 26 --kicker-id 1 --theta-x 1e-3 --on-pass 0
py -3.14 exp_planes.py --fire --exp 26 --kicker-id 1 --theta-x 1e-3 --delay 1.5e-6 --period 1e-3 --add
py -3.14 exp_planes.py --unfire --exp 26 --kicker-id 1
py -3.14 exp_planes.py --kicker-remove 1 --lattice 26
```

`--on-pass n` ставит пик импульса на приход опорной частицы на n-м пролёте: T_ref = (n·C_pass + s_k/β0)/c,
C_pass = C_RF у sine-ВЧ опыта, иначе L/β0; `--offset` сдвигает пик. `--add` добавляет ещё один импульс того же
кикера (без него строки опыта с этим кикером заменяются). `--show --exp N` перечисляет кикеры на пути.

**Проверено:** C++ ≡ Python (кольцо СИЛА-26 с sine-ВЧ и СИ — 2·10⁻¹¹; портал SP1 с кикерами в середине и в финише
на каждом пролёте — 1·10⁻¹¹); отклик на удар 1 мкрад = θ·√(β_k·β_0)·sin(2πν·n − ψ_k) по Твиссу (1·10⁻⁴ отн.);
бамп из трёх кикеров замыкается (утечка 2·10⁻³ от амплитуды); elegant `BUMPER` (СИЛА, 4 частицы с разными ct/δ,
20 оборотов, одиночный и «сползающий» периодический импульс) — эффект удара совпадает до 10⁻⁸ м на 10⁻⁴ м.
`elegant_diag.write_lattice(kickers=[dict(at_s, theta_x, theta_y, shape, duration, rise, period, time_offset)])`
ставит `BUMPER` с таблицей волны; `time_offset` — TIME_OFFSET elegant (время волны отсчитывается от среднего
времени пучка у кикера на первом пролёте).

**`--local`** доп. пишет `trajectories_local_expN.npz` — **ЛОКАЛЬНЫЕ** координаты матядра (S · x · x'≡px · y ·
y'≡py · ct · δ + элемент, на границах элементов). Локальный трек идёт СЕКТОРНОЙ моделью `m.body()` (x =
отклонение от опорной орбиты, бит-в-бит elegant), поэтому `track3.py` по умолчанию форсит `SS_SECTOR=1`
(`SS_SECTOR=0` — боксовая; глоб. `.bin` всегда боксовый `body_global`). ГОТЧА: боксовая модель диполей
раздувает пучок (её `x` = отклонение от ПРЯМОЙ оси), секторная — нет.

**`traj_analyzer.py N [--no-open] [--out f.html] [--csv]`** — анализ траектории в относительных координатах,
**ИНТЕРАКТИВНОЕ ОКНО** (самодостаточный HTML, авто-открытие в браузере; панели тянутся мышкой за разделители):
таблица общей информации, координаты x(S)/y(S) раздельно, спектр колебаний (**Фурье** — амплитуда по
**ЧАСТОТЕ (МГц)**, `частота = Q·c/кольцо`, пучок v≈c; у явных пиков вертикальный пунктир + ранг + тюн Q + частота). Для
**многооборотных опытов** (`track3 --turns K --local`) x(S)/y(S) — **ПОЛНАЯ траектория за все K оборотов**
(склейка S=0..K·кольцо, равномерно прорежена), спектр за K оборотов даёт **точный тюн** Qx/Qy с дробной
частью (напр. 55.22), плюс выживание за K оборотов в таблице. `--csv` — сводка запятой-десятичной; `--no-open`
— не открывать окно.

**ДЛИННЫЙ режим (10к+ оборотов):** полную траекторию не переварить, поэтому `mte.long_trajectories(lattice,
group, n_turns, states_override)` пишет (x,x') у плоскости РАЗ ЗА ОБОРОТ (поле `mode='long'` в .npz).
`traj_analyzer` сам детектит long-режим и строит отчёт: таблица · x(оборот) · **огибающая амплитуды** ·
**фазовый портрет (x,x')** цвет по обороту (эллипс=сохранение, спираль=затухание/рост). `states_override`
(список 6-состояний у плоскости) — трек ПРОИЗВОЛЬНОЙ частицы вместо пучка группы (сканы апертуры).

### Синхротронное излучение и затухание амплитуд (SR + ВЧ)

```powershell
# длинный турн-by-turn трек СИЛЫ (радиация/ВЧ берутся из radiation_params.csv по exp_id — флаги не нужны):
py -3.14 track3.py --mode kick-phys --exp 1 --long --turns 10000 --x0-mm 5
py -3.14 traj_analyzer.py 1            # огибающая покажет затухание (спад амплитуды)
```

**ПРАВИЛО (таблица `workspace/tables/radiation_params.csv`):** трекер (матричное ядро) проверяет её по
`exp_id` **перед запуском**. Есть строка для опыта → синхротронное излучение учитывается (энергия/ВЧ из
строки); **нет строки → СИ не учитывается** (дефолт). Столбцы: `exp_id; design_energy_mev; isr(0/1);
rf(none/ideal/sine); rf_ideal_energy_mev; rf_voltage_mv; rf_harmonic; rf_phase_deg; rf_freq_hz`. Загрузчик —
`matrix_tracker.load_radiation(exp_id)`, спецификация резонатора для трекеров — `matrix_tracker.rf_spec(rad)`.
Так проектная энергия не хардкодится в код, а лежит по машине в БД. CLI-флаги ниже **перекрывают** таблицу
(приоритет аргумент > БД > дефолт).

**Типы резонатора (`rf`):**

| тип | что делает | параметры |
|---|---|---|
| `none` | ВЧ нет, δ дрейфует вниз от излучения | — |
| `ideal` | после резонатора у частицы заданная энергия, какой бы она ни прилетела (резонатор — в конце пролёта, если у установки их нет) — затухание без синхротронных колебаний | `rf_ideal_energy_mev` — энергия после резонатора, МэВ (те же единицы, что `design_energy_mev`); пусто — проектная (δ = 0); δ = E/E_design − 1 |
| `sine` | **реальный** синусоидальный резонатор (RFCA на резонаторах установки `rf_cavities.csv` или в конце пролёта): ΔE = V·share·sin(φ + 2πh·τ/C_RF), τ — запаздывание от часов ВЧ | `rf_voltage_mv`, `rf_harmonic` (обязательны); `rf_phase_deg` — число (°) или пусто/`auto` = синхронная фаза π − asin(U0/V) по потере U0 опорной частицы за оборот; `rf_freq_hz` — пусто = h·c/L (резонатор на длине линии), число — расстроенный резонатор |

С `sine` видны синхротронные колебания (СИЛА-26: период ≈ 273 оборота) и равновесная энергия задаётся
частотой: C_RF = h·c/f_RF, δ_eq ≈ −Δf/(η·f). Позиция в БД: **опыт 26 (СИЛА-26) — `sine`, 8 МВ, h = 1296,
фаза auto**. C++ `--track` и Python-эталон `matrix_traj_export.long_trajectories(rf=rf_spec(...))` совпадают
по всем 6 координатам до 1e-10 (`test_matrix_core_ring.test_sine_rf_sila26`).

`--long` — длинный турн-by-turn трек СЕКТОРНОЙ моделью (минует боксовый глоб. путь), пишет
`trajectories_local_expN.npz` (`mode='long'`) для `traj_analyzer`. `--x0-mm/--y0-mm` — ОДНА частица
со смещением вместо пучка группы.

- **`--sr`** — **распределённое синхротронное излучение**: на каждом срезе изгиба частица теряет энергию
  `δ −= rad_coef·(1+δ)²·F²·ds` (порт elegant `integrate_csbend_ordn`). `rad_coef = (2/3)·r_e·γ³/ρ²`.
  ГОТЧА: трекер гоняет **сурогатный** пучок (γ≈7 из `particle_groups.csv`), а SR ∝ γ⁴ зависит от
  **ПРОЕКТНОЙ** энергии — её задаёт **`--design-mev`** (СИЛА `6000`, дефолт). Всё в формуле дробное
  (δ, нормир. F, сохранение угла `QX/(1+δ)`), поэтому проектную γ подставляем прямо в `rad_coef`.
  Проверка: осевая частица теряет за оборот СИЛЫ **U₀ = 1.99 МэВ** (совпало 0.17%).
- **`--rf ideal`** — идеальный ВЧ-резонатор: после него у частицы заданная энергия `rf_ideal_energy_mev`
  (пусто — проектная), какой бы она ни прилетела (компенсация потерь; без резонаторов у установки — в конце
  каждого пролёта). Именно ВЧ переводит падение канонич. импульса в диполях в **затухание поперечного УГЛА** — без
  ВЧ распределённая SR только роняет δ, углы не гасит (сохраняются). Проверка: τx≈14.7, τy≈22.3 мс.
- **`--rf sine`** — реальный синусоидальный резонатор; V/h/фаза/частота берутся из строки опыта в
  `radiation_params.csv` (без них — ошибка). t в выходе — запаздывание от часов ВЧ, δ — синхротронное движение.
- **`--isr`** (требует `--sr`) — квантовое возбуждение ISR (гауссов шум фотонов) для равновесного
  эмиттанса/энергоразброса. Без него амплитуда затухает к нулю; с ним — к равновесию.

По умолчанию (нет строки опыта в `radiation_params.csv` и нет флагов) радиации нет (`rad_coef=0`), тело
бит-в-бит как раньше (симплектика). Флаги-переопределения: `--sr`/`--isr`/`--rf`/`--design-mev` (env
`SS_SR`/`SS_ISR`/`SS_DESIGN_MEV`). Диффурное ядро (`--mode diff`) радиацию не моделирует — правило только
для матричного. См. `matrix_tracker._body_sector_symplectic` и `load_radiation`.

### Автономное матричное ядро на C++ (MatrixTracker)

```powershell
cmake --build build --target MatrixTracker           # собрать (MinGW g++ / MSVC через CMake)
./build/MatrixTracker.exe --track 1 10000 5 0        # СИЛА, 10к об., 1 частица x0=5мм → .npz
py -3.14 traj_analyzer.py 1                           # Python ТОЛЬКО рисует
```

C++ ядро (`src/matrix_core.h` физдвижок + `src/matrix_ring.h` кольцо) считает **автономно**: читает БД
(`experiments`/`lattice_configs`/`element_connectivity`/`particle_groups`/`radiation_params`/`rf_cavities`/`pulsed_kickers`/`kicker_timing`),
строит путь опыта старт → финиш с полной геометрией (`frame`/`_rot`, секторные дуги, `modified_drift`), ставит
пучок в рамку старта, трекает N пролётов (у разомкнутой линии — через портал) с СИ+ВЧ (правило
`radiation_params.csv`, резонаторы установки) и пишет `results/trajectories_local_exp<exp>.npz` для `traj_analyzer`.
В заголовке вывода печатаются плоскости, кольцо/линия и резонаторы на пути (`# start plane …`, `# rf cavity …`).
Python больше **не считает** — только БД/анализ/визуализация. Режимы:
- `--track <exp> <turns> [x0_mm y0_mm]` — turn-by-turn у плоскости + ВЧ → mode=long (затухание/огибающая);
- `--full <exp> <turns> [x0_mm y0_mm]` — запись на границах элементов → mode=full (x(S)/спектр/тюны, без ВЧ);
- `--element …` — тело одного элемента (валидация). x0/y0 ⇒ одна частица (скан).
- `--ring-serve <lattice> <lead_m|nan> <design_mev> <sr> <isr> <nsl> <order> <rf> <volt_mv> <harmonic> <phase_deg> <seed>`
  — **сервер кольца для анализа** (`src/matrix_ring_serve.h`): порт `ring_analysis.Ring` (плоскость наблюдения
  перед первым магнитом, ВЧ как RFCA с FIDUCIAL=light, СИ и ISR по срезам изгибов, у каждой частицы свой
  генератор). Двоичный протокол по stdin/stdout: `TRACK`/`TBT`/`ELEM`/`PIECES`/`JUNCTION` + float64,
  `INFO`/`PIECEMETA`/`DESCRIBE` (описание узлов, раскладка `DESCRIBE_COLS`), возмущения `KICK`/`VKICK j θ` (гор./верт. доп. кик) / `DK j dk` (±Δ нормального
  градиента k1 обеих плоскостей — BBA) / `DKV j dk` (±Δ только вертикального k1v) / `BSCALE j f` (угол и грани
  изгиба j = f × исходные, рамки заново — живой зазор ондулятора, `TbtPlant`) / `DSK j dks` (скью-градиент ks, связь x↔y — коррекция связи) /
  `DK2 j dk2` / `DK3 j dk3` (±Δ секступольной k2 / октупольной k3 — нелинейный тюнер ν(δ), коррекция
  хроматизма: ξ1 семействами SF/SD, ξ2 октуполями) / `YAW j α` / `RESET` / `RF on V h φ f` (параметры ВЧ на
  лету; `f` ≤ 0 ⇒ f_RF = h·c/C, иначе длина ВЧ-оборота C_RF = h·c/f — расстроенный резонатор сдвигает
  равновесную энергию δ ≈ −Δf/(η·f); живёт в конфиге, переживает `RESET`). Срезы `PIECES`/`PIECEMETA` всегда
  по текущим (возмущённым) магнитам: `KICK`…`DK3` помечают их устаревшими, перед следующим запросом срезы
  пересобираются (как `ring_analysis._bend_slices`; доп. кик `KICK`/`VKICK` изгиба — на последнем срезе), так
  что выход последнего среза = выход магнита в `ELEM`. Частицы параллельно (OpenMP).
  Python-обёртка — `ring_cpp.CppRing` (интерфейс как у `ring_analysis.Ring`: `track`, `track_tbt`,
  `track_elements`, `track_pieces`, `with_kick`, `with_yaw`, `perturbed`, `junction`; `rf=dict(volt_mv,
  harmonic, phase_deg[, freq_hz])` и `set_rf(freq_hz=…)` — частота ВЧ на лету (`rf_frequency()`,
  `rf_circumference()`; Python-эталон — `ring_analysis.Ring.set_rf`/`rf_circumference`, elegant — `FREQ=freq_hz`);
  `apply_perturb(kicks, vkicks, dks, dsks, dk2s, dk3s, dkvs, bscales)` — RESET + набор возмущений на том же сервере,
  ошибки рассогласования и возмущения создания `with_*`/`perturbed` сохраняются, сбрасывается только прежний
  `apply_perturb`; описание магнитов `mags`/`plane` для `ring_matrix`/`ring_response`/`ring_map` — **из ядра**
  (команда `DESCRIBE`: рамки, силы, грани, флаги тела — текущее состояние со всеми возмущениями; объекты
  `matrix_tracker.Magnet`, без излучения и ВЧ; кик изгиба и полевого элемента — атрибут `hkick`/`vkick`, кик
  «ящика» корректора — его θ0, как `ra.kicked`); сверка с Python-эталоном — до
  1e-11, быстрее в 150–450 раз. Дешёвые пути БЕЗ RESET (~0,3 с): `set_kicks(kicks, vkicks)` — задать
  изменившиеся кики (смена корректоров FOFB; снять — 0), `add_perturb(dks=…, dkvs=…, dsks=…, dk2s=…, dk3s=…)` —
  доложить аддитивные приращения, `set_bend_scale([(j, f)])` — масштаб изгиба полюсов (живой зазор ИД);
  `TbtPlant._apply` сам выбирает путь.
  `nsl_dev={device_type_id: n}` — срезы сектор/кик-тела по типу устройства (env `SS_NSL_DEV="dev=n,…"`,
  её же читает Python-эталон — паритет 1e-11); не задано — из окружения, по умолчанию всё как было.

**То же ядро в процессе Python — модуль расширения `synchrotronsim._engine`** (шаг 0 плана библиотеки,
`docs/LIBRARY_ARCHITECTURE.md`). Собирается из тех же заголовков (`src/py_engine.cpp` над `mc::RingModel`),
nanobind, MinGW; рантайм MinGW и OpenMP влинкованы статически — модуль зависит только от `python314.dll`,
`msvcrt.dll`, `KERNEL32.dll` и грузится без `C:\mingw64\bin` в PATH. Отдельная папка сборки `build-py/`:

```powershell
py -3.14 -m pip install nanobind                                         # один раз
$py = py -3.14 -c "import sys; print(sys.executable)"
cmake -S . -B build-py -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Release -DSS_BUILD_PYTHON=ON "-DPython_EXECUTABLE=$py"
cmake --build build-py --target _engine                                  # → synchrotronsim/_engine.cp314-win_amd64.pyd
```

После правки `src/matrix_*.h` пересобирать ОБА: `MatrixTracker` (сервер) и `_engine`. Обёртка —
`synchrotronsim.engine.ExtRing` с интерфейсом `CppRing` (`track`, `track_tbt`, `track_elements`, `track_pieces`,
`piece_meta`, `junction`, `apply_perturb`, `add_perturb`, `set_kicks`, `set_bend_scale`, `set_rf`,
`rf_frequency`, `rf_circumference`; срезы по типу `nsl_dev` передаются явно, не через окружение). Числа —
**бит-в-бит с сервером** при той же последовательности запросов, включая ISR (тест `TestEngineExtension`).
На время трекинга GIL отпущен: разные `ExtRing` в разных потоках Python считаются параллельно (8 колец × 1
частица на 16 потоках — ×6,3). Скорость трекинга та же, что у сервера (канал не был узким местом);
`set_kicks` — 1 мкс вместо 60 мкс.

**Решётка из модели, RESET без диска, снимки и копии (шаг 2).** По умолчанию `ExtRing` берёт решётку из
`synchrotronsim.db` (`Machine`, `ws` ⇒ overlay) и передаёт в C++ массивами (`line_spec`, `cavity_specs`): ядро
не читает таблицы ни при сборке, ни при `RESET`. `RESET` (`apply_perturb`, `reset()`) — откат к снимку свежего
кольца, ВЧ на лету сохраняется (как у сервера): **~6 мс против ~0,3 с**. `snapshot()`/`restore(snap)` — снимок и
откат живого состояния (~30 мс / ~5 мс); `clone()` — независимая копия (~30 мс). `source="csv"` — ядро читает
таблицы само (для сверок). Все три пути (сервер, расширение из CSV, расширение из модели) — бит-в-бит.

**`CppRing` выбирает бэкенд сам** (`ring_cpp.choose_backend`): аргумент `backend="ext"|"pipe"` → переменная
окружения `SS_ENGINE=ext|pipe` → по умолчанию **`ext`** (модуль в процессе), если модуль собран и не задан
`timeout`; с `timeout` — `pipe` (сторож убивает зависший процесс сервера, у модуля процесса нет). Интерфейс и
числа одинаковы; на `ext` копии `with_*`/`perturbed` — клон свежего кольца (~30 мс вместо запуска процесса
~1 с), RESET — 6 мс. Вернуть прежнее поведение во всём проекте — `SS_ENGINE=pipe`.

**Копии и параллельные столбцы отклика (шаг 6).** `CppRing.clone()` — независимая копия в текущем состоянии
(ext — в памяти, ~30 мс; pipe — новый процесс). `control.response.parallel_columns(ring, n, fn)` считает
независимые столбцы на 8 копиях параллельно, бит-в-бит как последовательно; на нём матрицы отклика
(`response.build_response`, `orbit_correct.response_matrix`, протяжка, базис сдвигов `orbit_infer`). Полная
матрица корректоров СИЛА-26 — 6,4 с вместо 38 с. `SS_RESP_WORKERS=N` — число копий (1 — последовательно).
**Замкнутая орбита** (`ring_analysis.closed_orbit`) останавливается, как только невязка Ньютона ниже `floor`
(1e-11 м — шум округления орбиты за оборот): 4–5 оборотов вместо 10, точность та же; `floor=0` — прежнее.

### Сходимость срезов по типам устройств (`nsl_convergence.py`)

```powershell
py -3.14 nsl_convergence.py --lattice 26            # ~2 мин; --reuse — подбор заново по сохранённому скану
```

Эталон — всё кольцо на 40 срезах (точность паспорта). Для каждого типа устройства с сектор/кик-телом его
срезы по отдельности уменьшаются (1…24, на лету — `Ring.set_nsl`), и меряются отклонения от эталона дробных
тюнов (матрица оборота) и карты оборота пробных частиц (1 мм, δ = 1e-3). Жадный подбор (по невозрастающим
огибающим кривых) выбирает каждому типу наименьшее число срезов, при котором суммы отклонений укладываются в
допуск при наименьшей цене «элементы × срезы»; набор проверяется целиком. Выход —
`workspace/results/nsl_convergence_<lat>.csv` (кривые по типам, для Excel), `.json` (рекомендации и проверка),
`_scan.json` (сырой скан). Итог для реш. 26 (2026-11-25):

| набор | Δνx / Δνy | Δ карты | оборот 1 частицы, СИ+ВЧ | такт кокпита (12 частиц × 15 об.) |
|---|---|---|---|---|
| кокпит сейчас (nsl 8, полюса ИД 1) | 2,1e-3 / 4,5e-3 | 14,5 мкм | 8,9 мс | 185 мс |
| `tight` (допуск 1e-4, 0,1 мкм) | 8e-6 / 7e-6 | 0,06 мкм | 9,0 мс | 184 мс |
| `loose` (допуск 1e-3, 1 мкм) | 2,3e-5 / 9e-5 | 0,26 мкм | 6,5 мс | 135 мс |

Диполям (в т.ч. полюсам ИД) и октуполям хватает 1 среза, секступолям 1–3; квадруполям и DQ — 6–40 (больше
всего DQ1B/D и QF8B/D — самые сильные).

**Кокпит по умолчанию — набор `tight`** (решение 2026-11-25): берётся из `workspace/configs/slices_<lat>.json`
(отслеживается git; пишется `nsl_convergence.py --save tight`; в нём допуск, проверка набора целиком и
отпечаток машины). Нет файла — как раньше (`--nsl`, полюса ИД на 1 срезе); решётка изменилась после подбора —
набор применяется, а в статус-строке предупреждение «перегнать nsl_convergence.py». Флаг
`py -3.14 -m client --slices auto|none|tight|loose|<json>`: `none` — прежние срезы, `tight`/`loose` — из
`workspace/results/nsl_convergence_<lat>.json`. Кнопка «Режим 4» оболочки — тоже `auto`.
`TbtPlant(nsl_dev={тип: срезов})` — то же в коде; в опыте — `Experiment.cockpit(nsl_dev=...)`. Срезы можно
сменить и на ходу — окном «Опыт…» кокпита (пересборка модели, см. «Опыт кокпита»).

**Готча x87:** `std::pow` у mingw-w64 считает на x87, и последний бит зависит
от точности x87, которую ставит процесс-хозяин (exe MinGW — 64 бита, Python — 53). Поэтому дробные степени ISR в
ядре — через `sqrt` (`pow_1p5`/`pow_2p5`/`pow_0p75` в `matrix_core.h`); новые `std::pow` с дробной степенью в
ядро не добавлять.

Python-ядро `matrix_tracker.py` — **эталон** для разработки/опытов: новое явление сначала в Python, потом порт
в C++; регрессия `test_matrix_core_cpp.py` (элемент, бит-в-бит) и `test_matrix_core_ring.py` (кольцо+npz,
end-to-end ~1e-11) ловит расхождение до бита; сервер кольца — `TestRingCpp` в `test_synchrotronsim.py`.
ISR и порядок Йошиды 2/4/6 портированы (сервер кольца); box-тело — только кик корректора (`hkick`, дрейф–кик–дрейф
по `n_slices` из БД) для опытов с откликом орбиты.

**Тело выбирается по ПОЛЮ, а не по виду** (одинаково в Python при `SS_SECTOR=1` и в C++):

| условие | тело |
|---|---|
| `kind` ∈ {`dipole`, `dq`} и θ₀ ≠ 0 | секторный CSBEND: θ₀, b₁…b₃ (= K·ρ), края/фриндж |
| иначе `L_eff > 0` и есть k1/k1v/k2/k3 — **любой** `kind` (квад, секступоль, октуполь, kicker, dq с θ₀ = 0…) | симплектический кик (Йошида, N срезов); статический θ₀ (`mat_B` у kicker) — дипольный член кика |
| иначе θ₀ ≠ 0 или `hkick/vkick` (чистый корректор) | «ящик» корректора: дрейф–кик–дрейф по `n_slices` |
| иначе | дрейф |

`DK`/`DK2`/`DK3`/`DSK` сервера кольца пересчитывают выбор тела: возмущение действует и на элементе с нулевым
полем. Аналитика следует тем же флагам: `ring_matrix` даёт толстую линзу любому прямому элементу с K1,
`ring_map` — ряды поля любого прямого элемента; дипольный кик прямого элемента (коррекция орбиты) в
оптику вокруг проектной орбиты не входит.

**Режимы:** `diff` — диффурное ядро (Boris по картам поля, эталон); `kick-phys` — **киковое** ядро
(`matrix_tracker`, симплектич. drift-kick-drift в режиме `SS_SECTOR`, а не передаточные матрицы) на
физкоэф. `mat_*` из `.lte`. Токовый режим (`kick-current`) **архивирован**: связь ток↔физкоэф. не была
доверенной, ядро читает только `mat_*`.

## 6. Карты полей

| Команда | Что делает |
|---|---|
| `scan_field_maps.py` | Инвентаризация карт `workspace/fields_bin/`, `fields_raw/`. |
| `gen_synthetic_maps.py [--no-stl]` | Синтетические карты для элементов без ANSYS-карты: ресайз очищенной карты эталона под `eff_length` → `fields_bin/synthetic/`. Идемпотентно. |
| `symmetrize_maps.py` | **Драйвер:** сырой `.fld` → сглаживание + симметризация по типу мультиполя → очищенный `.bin` в `fields_bin/<тип>/`, обновляет `map_bin_path`. *(нужен scipy)* |
| `symmetrize_map.py <карта.fld> <quad\|sext\|oct\|dq> [σ]` | Одна карта вручную. |
| `clean_dipole_maps.py [dev ...]` | Медианная симметрия средней плоскости диполей (убирает паразитное медианное поле). Бэкап `.orig`. |

Карты: `.bin` (заголовок 96 б + сетка Bx,By,Bz), `.fld` (текст ANSYS). Скейл в трекере:
`map × currentScale × correct_coeff × field_direction`, `currentScale = arg_val / nominal_arg`.
Базовые карты QP/SP/OP/DQ — ANSYS 100А (`nominal_arg=100`, сетка 2 мм v3; QP_L — 5 мм v2). Диполи DP —
постоянные магниты (`nominal_arg='-'`, масштаб через `correct_coeff`).

**Число полюсов при симметризации:** quad — 4 (n=2), sext — 6 (n=3), oct — 8 (n=4). Отражения по
чётностям НЕ разделяют quad и oct — их разделяет грид-точный поворот 90°.

**Каскад при обновлении базовых карт:** новые `.fld` в `fields_raw/` + `map_raw_path`/`nominal_arg` →
`symmetrize_maps.py` → очистить `map_bin_path` у синтетики затронутых семейств + `gen_synthetic_maps.py --no-stl`
→ `clean_dipole_maps.py`. `build_matrix_db.py` при обновлении ТОЛЬКО карт не нужен (он сбрасывает `mat_*`).

### Ошибки установки: ансамбль машин (`--errors`)

Ядро трекает решётку по геометрии x/y/z/yaw/pitch/roll и полям mat_* из `lattice_configs`, поэтому
ошибки моделируются как ВОЗМУЩЁННАЯ решётка. Допуски (СКО) задаются по типу магнита в
**`workspace/tables/element_errors.csv`** (`kind; dx; dy; dz; dyaw; dpitch; droll; field_pct` — сдвиги [м],
повороты [рад], ошибка поля [%]).

```powershell
py -3.14 facility_report.py 26 --errors                 # ансамбль 32 машин, → facility_exp26_errors.html
py -3.14 facility_report.py 26 --errors --correct       # + коррекция орбиты → facility_exp26_errors_corr.html
py -3.14 facility_report.py 26 --errors --correct --nsl 12   # ансамбль в ~3× быстрее (см. ниже)
py -3.14 facility_report.py 26 --errors --seeds 64 --turns 1024
py -3.14 facility_report.py 26 --errors --errors-table my_tol.csv --cutoff 3
```

**`--nsl` (срезов магнита в трекинге).** По умолчанию 40 — «геройская» точность для паспорта идеальной
машины. Для ансамбля это избыточно: бенчмарк ДА решётки 26 показал, что граница (+x/−x = 7.219 мм)
**идентична** при nsl от 40 до 6, а расхождение маски выживания (~20 ячеек из 656) — фрактальный шум на
краю, не ошибка интегратора; лёгкий дрейф числа выживших начинается лишь с nsl=8. Значит для ансамблей
безопасно `--nsl 12` (граница не сдвигается, с запасом над точкой дрейфа) — время ×3 меньше (прогон
32/1024 с коррекцией: ~3–4 ч → ~1 ч). Матрица отклика кэшируется отдельно на каждый nsl.

**Срезы и тюн: дефолт 5 — только для сверки с elegant.** `CppRing`/`ra.Ring` без `nsl` берут 5 срезов
(как `N_SLICES=5` в .lte от `lte_flatten`, ради побитного паритета). Ошибка интегратора Йошида-4 ∝ 1/N⁴,
основной вклад — DQ1B/D (√|K1|·L = 1,43) и QF8/QF6: на решётке 26 тюн при 5 срезах 95,243/33,367 вместо
паспортных 95,230/33,398 (12 срезов — 95,2305/33,3968, 8 — 95,232/33,393), ηx у ондуляторов хуже на ~4%;
линия νx+2νy=162 оказывается по другую сторону. Поэтому всё, что считает оптику или тюны, передаёт `nsl`
явно: `ring_cpp.OPTICS_NSL = 40` (паспорт; `undulators/lattice_optics`, `verify_undulators`, `misalign_demo`),
12 — орбита источников СИ (`undulators/electron_source.ORBIT_NSL`) и ансамбли, 8 — контуры управления и
клиент (`--nsl`, рычаг скорости). Аналитическая оптика паспорта (`ring_matrix`) от срезов не зависит.

`errors.py`: на каждый seed рисует гауссовы (обрезка `--cutoff`·σ) отклонения на КАЖДЫЙ экземпляр,
сдвигает его в ЛОКАЛЬНОЙ рамке (u,v,axis по yaw/pitch/roll), поворачивает, масштабирует поля на (1+δ),
и пишет возмущённую рабочую папку во временный каталог; ядро запускается на ней через новый аргумент
`--ws` сервера (`ring_cpp.CppRing(ws=...)`). Реальная БД не трогается.

Отчёт: ДА как **доля выживших машин**, средняя карта диффузии, импульсная как доля, таблица влияния
(искажение орбиты СКО, разброс частот, доля неустойчивых машин). По умолчанию (без `--errors`) — идеал.

### Коррекция орбиты (`--correct`)

Ультрамалоэмиттансное кольцо СИЛА **без** коррекции терпит лишь ~10–20 мкм рассогласования (при 30+ мкм
орбита разлетается). Реальные допуски 50–100 мкм работают только с коррекцией замкнутой орбиты
корректорами. Флаг `--correct` (вместе с `--errors`) включает глобальную коррекцию на **каждой** машине
ансамбля — отчёт тогда отражает уже скорректированную установку.

`orbit_correct.py` — стандартная схема «матрица отклика + SVD»:
- **корректоры** — магниты `kind=kicker` (в решётках СИЛА это слоты SH1A/SH2B/SH3E; 120 штук, гор.+верт.);
- **точки наблюдения** — выходы всех магнитов (least-squares гладит орбиту по всему кольцу);
- **матрица отклика** R (BPM × корректоры, отдельно x/y) считается ОДИН раз на идеальной решётке
  (≈2–3 мин) и кэшируется в `workspace/results/orbit_resp_exp{N}_nsl{nsl}.pkl` (инвалидация по
  n_mag/периметру/nsl; рядом хранится причинная матрица T для протяжки);
- на каждый seed: измерить искажённую орбиту → θ = −R⁺·o (псевдообратная через SVD, `rcond=1e-2`) →
  применить кики (`CppRing.apply_perturb`: RESET сохраняет ошибки, сбрасывает лишь кики) → повторить
  4 раза → трекинг ДА/диффузии на скорректированном кольце. Настройка **стационарна** для данной машины.

**Бутстрап протяжкой (threading).** При больших ошибках замкнутой орбиты из нуля нет (Ньютон расходится),
и штатный SVD не стартует. Тогда `_thread` сначала гасит ОДНООБОРОТНУЮ траекторию причинной матрицей
отклика T (кик влияет лишь ниже по ходу), сектор за сектором, с недорелаксацией, — пока не появится
замкнутая орбита, — и лишь затем идёт штатный SVD. Важно гасить до МАЛОЙ траектории (не «до апертуры»):
большая орбита через секступоли даёт feed-down и уводит тюн на резонанс. Протяжка сдвигает потолок
коррекции с ~15 до ~30 мкм (доля вытянутых машин: 20 мкм 16→88 %, 30 мкм 0→63 %). Таблица влияния
показывает, сколько машин вытянуто протяжкой.

Таблица влияния тогда показывает: число корректоров, СКО орбиты **до → после** коррекции (x и y),
СКО и максимум углов корректоров. Значения в `element_errors.csv` — плейсхолдеры ~10 мкм.

### Фотонные экраны: тепловая карта, быстрый и точный режим (`--calc`)

Плотность мощности СИ (Вт/мм²) на замороженных экранах `screens.csv` считают `undulators/screen_analysis.py`
(все экраны решётки), `undulators/bend_screen.py --screen …` (волноотводы) и HTML-паспорт
`undulators/screen_report.py --screen …`. Режим выбирает флаг `--calc`:

| режим | модель | время |
|---|---|---|
| `fast` (по умолчанию) | ондулятор — одна точка с табличной угловой мощностью (Льенар, усреднённый по периоду бесконечной синусоиды); диполь — веер из одной точки отбора с жёстким краем; один электрон | ~1 с на экран |
| `accurate` | прямое интегрирование формулы Льенара по траектории электрона (`undulators/sr_trace.py`): каждый участок траектории светит на каждый пиксель из своего места своим направлением | 10–60 с на экран, `--breakdown` ×~3 |

Точный режим: dP/dA = (I/e)·Σ Δt·e²/(16π²ε₀c)·[|β̇|²/q³ − (n·β̇)²/(γ²q⁵)]·|n·N|/R², q = 1 − n·β. Для
мощности это точно (без интерференции — Парсеваль), включая ближнюю зону; отброшено только поле скорости
(~3·10⁻⁸). Эффекты (`--effects all | none | extended,poles,… | all,-beam`):

| эффект | что учитывает | величина на реш.27 (зазор 5 мм) |
|---|---|---|
| `extended` | протяжённый источник: точки дуги и ИД светят из своих мест, точные R и угол падения | ≤0,1% мощности ИД-экранов; на волноотводах сдвиг центроида ~0,1 мм, пик до 1,6% |
| `poles` | реальная структура ИД из БД: полупериоды синусоиды с амплитудами полюсов (концевые UE0/UE1 ≈ 0,49), вход по орбите без начального угла | −2,5% мощности ИД, −2,9% пика (быстрый режим считает 30 полных периодов) |
| `fringe` | мягкий край диполей по продольному профилю карты поля (`hardware_library.map_bin_path`; полукарта зеркалится, соседние модули складываются, ∫f = L_eff — угол изгиба как в решётке); DQ и диполи без карты — жёсткий край | веера на ИД-экранах −1,2% мощности, пик −0,9%; отбор у входа диполя (SCR_BM08_ENTRY) −9,5% и центроид +2,3 мм |
| `beam` | свёртка карты каждого источника с размером пучка на экране σ²(D)=ε(β−2αD+γD²)+σδ²(η+η′D)² (Твисс — `lattice_optics`, εx/κ/σδ — допущения `--emit-x --kappa --sigE`) | ~10⁻⁴ (σ пучка на экране 5–40 мкм ≪ пятна) |

Не входит: энергоразброс в самом излучении (~σδ²), СИ квадруполей и корректоров (мВт), поглощение и
отражение по спектру и материалу, рассеяние фотонов, затенение экранов. Точный режим сам ищет источники
(отсев точек траектории, не достающих экран с запасом `--cull`/γ, по умолчанию 40 → хвост < 10⁻⁸ пика) —
например, на SCR_BM08 он находит второй, дальний диполь, которого нет в быстром.

```
py -3.14 undulators/screen_analysis.py --lattice 27 --calc accurate --breakdown
py -3.14 undulators/bend_screen.py --lattice 27 --screen SCR_BM08_ENTRY --calc accurate
py -3.14 undulators/screen_report.py --lattice 27 --screen SCR_U01 --calc accurate --breakdown
```

В точном режиме печатается и строка быстрого (Δпик, Δмощность, Δцентроид), `--breakdown` — вклад каждого
эффекта (итог минус итог без него). Файлы точного режима — с суффиксом `_acc` (PNG, `screen_readings_L*_acc.csv`;
в CSV колонка `calc`). Численные ручки: `--ppp` точек на период ИД (64 — сходимость 10⁻⁵), шаг дуги — поворот
касательной ≤ 1/(8γ).

**Экраны в кокпите (2026-11-24): все на 20 м.** У каждого ондулятора — экран в 20 м от центра гребёнки по
оси (манифест `undulators/screens.csv`: SCR_U01/U19/U19_TILT — 20 м; остальные — по умолчанию
`SCREEN_DEFAULT_DIST` = 20 м в `client/scene3d`, `undulators/screen_analysis`, `control/recorders`). У каждой
**линейки диполя из 5 модулей** — экран `SCR_DP<instance_id модуля №3>` в 20 м по касательной в центре
центрального модуля, 100×30 мм (`screen_analysis.bend_line_screens`; линейки — модули встык,
`sr_trace.link_chains`; инжекционные `und_JL1E/JL1A`, разбитые вставкой 0,39 м, — по номерам `_1…_5`, в реш.27 —
кускам одного типа со вставкой короче модуля). Решётки 26 и 27: по 160 экранов. В сцене — фиолетовые, одним
актёром (клик — ближайший экран); в дереве — «экраны / у ондуляторов / у линеек диполей».

Окно экрана у линейки: «мощность» — Вт/мм², «поток (E₁ / ε_c)» — на ε_c центрального модуля, спектр в точке —
сплошной. Считается по ТРАЕКТОРИИ электрона (точный режим `sr_trace`: модули с мягким краем по картам поля,
протяжённый источник) — быстрый «веер из точки» на стыках модулей давал щель; поток и спектр — по участку дуги,
касательная которого смотрит на точку экрана, с его локальной ε_c (`sr_trace.stationary_points`). Картина от
зазоров не зависит — считается один раз на (экран, сетка, величина): ~2–3 с при сетке 121.

**Кокпит клиента** (окно экрана, переключатель «величина»): «поток на E₁» — интерференционная картина
центрального конуса на энергии первой гармоники в окне ±8σ_r′ (`control/recorders.ScreenRecorder`; круглое
пятно ~±0,3 мм); «мощность, Вт/мм²» — карта быстрого режима на ВСЁМ экране на живых зазорах всех ондуляторов
(+ веера соседних диполей; `screen_analysis.live_power_map`, ~1–3 с в фоне, вид сам приближается к пятну ИД —
колесо/«View All» показывают весь экран). Экран, которого нет в `screens.csv` решётки кокпита, строится как в
сцене: по оси ондулятора-источника на `dist_m` строки с тем же `screen_id` (нет — 12 м), размер оттуда же
(нет — 50×50 мм). Источник — по рамке железа (номинальная машина); точный режим в кокпите не считается.

Окно экрана в кокпите:
- **лог. шкала** — цвет по log₁₀, 5 декад от пика: видны слабые полосы вееров диполей и хвосты Льенара;
- **значение под курсором** — на карте (u, v и величина в узле), на спектре (энергия и поток ближайшей точки);
  так же на всех графиках клиента (ряды во времени, точка x×y, «η-узор и моды FOFB»);
- **метки спектра** — двойной клик по спектру ставит метку (с «к пику» — на ближайший максимум в ±1% по
  энергии), вертикаль метки можно тащить мышью; в таблице под спектром имя и энергия редактируются (запятая
  допустима), «удалить метку»/Delete и «очистить» убирают метки; легенда на графике повторяет таблицу, поток в
  метке обновляется вместе со спектром. Метки, лог-шкала и величина сохраняются в раскладке;
- **Сохранить…** — PNG или SVG (вектор: кривые и подписи — линии и текст).

### Кокпит: камера по элементам кольца

ЛКМ по магниту или ондулятору ставит его в центр вида (направление и дистанция камеры сохраняются) и
запоминает как текущий. Дальше клавиши (работают в любом окне кокпита):

| клавиши | куда перелетает камера |
|---|---|
| Ctrl + → / ← | соседний элемент по движению пучка / навстречу |
| Shift + → / ← (или Ctrl+Shift) | соседний элемент ТОГО ЖЕ типа устройства — например, следующий ондулятор |

Элементы — тела магнитов и ондуляторы целиком (центр гребёнки полюсов), в порядке пучка; строки в одной точке
(обмотки корректора, DQ I1–I3, пары секступолей) — один шаг; кольцо замкнуто (после последнего — первый).
Если фокус камеры сдвинут панорамой, текущим считается ближайший к фокусу элемент (до 2 м); дальше — подсказка
щёлкнуть по элементу. В статус-строке — элемент и его номер среди однотипных («ондулятор und_05 — 5 из 38»).

**Плавность.** Сцена (2,2 млн треугольников, весь ряд магнитов) рисуется за ~2 мс — дальность прорисовки не
нужна. Рывки при осмотре давали окна графиков: каждый новый снимок движка перерисовывал их в том же потоке
(~80 мс на три окна). Поэтому, пока камеру крутят (зажата кнопка мыши, крутится колесо, идёт перелёт по
стрелкам), окна графиков ждут и после получают последний снимок; сцена, челюсти ондуляторов и панель
обновляются всегда. Ряды во времени и след точки x×y — без сглаживания линий (перерисовка вдвое дешевле).

### Адреса величин и прогоны (`synchrotronsim.addresses`, `synchrotronsim.run`)

Каждая величина, которую показывает кокпит, записывает прогон или двигает команда, имеет **адрес** —
`<область>.<объект>[.<атрибут>][@<место>][:<редукция>]`:

| область | пример | что |
|---|---|---|
| `obs` | `obs.ebpm.x`, `obs.ebpm.x:rms`, `obs.tune:0` | наблюдаемая (вектор; `:rms/mean/max/min/<индекс>` — свёртка) |
| `act` | `act.corr.000.hkick`, `act.corr.000.hkick.slew` | реализованное значение актуатора / поле его привода |
| `undulator` | `undulator.und_01.gap` | ондулятор (gap, gap_target, K, B0, orbit_kick, slew) |
| `optics` | `optics.nux`, `optics.beta_x@QF1A_03` | линейная оптика |
| `element` | `element.SP03.COR05.k1` | магнит |
| `loop` | `loop.fofb_x.enabled`, `loop.fofb_x.gain` | контур |
| `meta`, `screen`, `diag`, `rec` | `meta.model_time`, `screen.SCR_U01`, `rec.orbit_rms.x` | мета прогона, экран, стандартный график, ряд рекордера |

Прежние имена — **псевдонимы** (2026-11-25): `drive.<aid>.<поле>` → `act.<aid>.<поле>`, `actual.<aid>` →
`act.<aid>`, голый id актуатора (`corr.000.hkick`, `quad.QF1A.dk`, `rf.freq`) → `act.<id>`. Старые раскладки окон
открываются (адреса приводятся при восстановлении окна), подписки и команды понимают обе формы.
`synchrotronsim.addresses.meta(addr)` — имя, единицы, виджет, можно ли писать (`writable`), форма, владелец
(доска / движок / рекордер), цена (дешёвый / дорогой). Клиентский `client/addresses.py` — реэкспорт.

Прогон эксперимента (`mode4_run`) пишется в `workspace/runs/<run_id>/` (паспорт `manifest.json`, ряды
`signals.npz`, `tables/signals.csv` для Excel, `artifacts/`) и в индекс `workspace/tables/runs.csv` — подробности в
`docs/CONTROL_MODEL.md`, раздел 10. Из Python: `Run.open(run_id).series(addr)` → (шаг, время, значение);
`synchrotronsim.run.list_runs()` — индекс. Подписка в `fb_record` принимает любой адрес (`WatchRecorder`).

### Запись прогона из кокпита и лимит оборотов

На панели управления — блок **«запись прогона»**:
- **что писать** — кнопка **«● запись»** в окне графика (или точки x×y): нажатая — адрес окна пишется в прогон;
- **«записывать прогон»** — каждый проход (от рестарта до лимита) пишется в свою папку `workspace/runs/<id>`
  (вид `cockpit`; в паспорте — опыт кокпита с текущей подпиской и лимитом, отпечаток машины, git, сборка ядра);
  точка ряда — на каждом кадре движка (шаг = цикл публикации, время — модельное);
- **«лимит прохода»** (оборотов; «без лимита» = 0) и **«по лимиту — новый проход»**: дойдя до лимита, проход
  завершается (статус `done`) и либо начинается заново с нуля (новый прогон), либо модель встаёт на паузу.
  Ручной «Рестарт» и снятие галочки завершают проход со статусом `stopped`.
Строка под блоком показывает текущий прогон, число отмеченных величин и номер прохода. Экраны и стандартные
графики (дорогие величины) пока не пишутся.

### Опыт кокпита: окно «Опыт…», пересборка, `--experiment`

Кокпит исполняет **опыт** (`synchrotronsim.experiment.Experiment`) и строит модель тем же сборщиком, что
`Simulation` (`synchrotronsim.simulation.build_session`). Без явного опыта он собирается из параметров запуска
(`--lattice`, `--nsl`, `--slices`, `--n-part`, `--stride`, `--settle-turns`, `--no-optics`, `--no-fofb` — как
раньше; `client.cockpit.cockpit_experiment`). Явно:

```powershell
py -3.14 -m client --experiment workspace\experiments\my.json
py -3.14 -m client --experiment fb:3
py -3.14 -m client --experiment exp3.zip
```

`путь.json` — опыт, сохранённый окном «Опыт…» или `Experiment.to_json`; `fb:N` — опыт ОС из таблиц fb_*
(контуры включены, как в `mode4_run`); `пакет.zip` — опыт + документ машины (`Experiment.save_bundle`): модель
считает по документу, без БД, и держит этот документ при пересборках той же решётки. Модель без кольца (`plant.kind = optics`, напр. fb:2) кокпит не
показывает — её исполняет `Simulation(exp).run()`.

Кнопка **«Опыт…»** на панели инструментов — опыт текущей модели:
- **модель и точность:** решётка, `nsl`, срезы по типам (как в опыте / tight — конфиг `workspace/configs` /
  loose — из скана `nsl_convergence.py` / нет), частиц, оборотов на такт, осадка при рестарте; у опыта кокпита —
  ещё вид модели (оптические контуры tune/chroma/adts — модель composite; контур частоты ВЧ). При смене решётки
  «как в опыте» берёт набор срезов новой решётки;
- **контуры: включены на старте** — по умолчанию живое состояние переключателей панели;
- **«Применить и перестроить»** — модель пересобирается в фоне (~20 с на реш. 26). Окна графиков и их подписки,
  отметки «● запись», настройки блока «запись прогона», зазоры ондуляторов, настройки экранов и пуск/пауза
  переносятся; модель начинает с нуля (оборот 0). Если шла запись — текущий проход закрывается (`stopped`), а
  новый опыт пишется новым прогоном со своим паспортом;
- **«Сохранить опыт…»** — JSON с живыми флагами контуров, отмеченными величинами (`record`) и лимитом прохода;
  **«Открыть опыт…»** — пересборка по опыту из файла.

У опыта из файла/БД вид модели не меняется, а в аргументы plant'а пишутся только реально изменённые поля
(умолчания plant'а не вписываются). Подписка опыта (`record`, адреса) при запуске становится отмеченными
величинами; рекордеры по имени (`orbit_rms`, `rf`, …) в живом режиме не исполняются — только в `Simulation`.

### Опыт и стандартный цикл из Python (`synchrotronsim.experiment`, `synchrotronsim.simulation`)

```python
from synchrotronsim.experiment import Experiment
from synchrotronsim.simulation import Simulation
from synchrotronsim.run import Watch
exp = Experiment.from_fb(3, smoke=True)          # опыт ОС из таблиц fb_* (то же, что mode4_run --exp 3 smoke)
exp.record.append(Watch("obs.ebpm.x:rms"))        # дописать подписку
run = Simulation(exp).run()                       # сборка + шаги + рекордеры → прогон
run.series("rec.orbit_rms.x")
exp.to_json("exp3.json"); Experiment.from_json("exp3.json")
exp.save_bundle("exp3.zip")                       # опыт + документ машины + таблицы её строк
exp, m = Experiment.open_bundle("exp3.zip")       # → опыт и машина; Simulation(exp, machine=m).run() — без БД
```

`Experiment.cockpit(...)` — опыт живого кокпита (параметры прежнего `build_session`; обратное —
`exp.cockpit_params()`). Сборка у всех входов одна — `synchrotronsim.simulation.build_session(exp)`: `mode4_run`
(через `Simulation`) и кокпит строят модель ею (`client.engine.build_session` оставлен обёрткой для старого
кода). Исполнитель шагов тоже один — `synchrotronsim.simulation.Runner` (шаг, рестарт прохода, лимит оборотов,
`Watch` → `Run`): на нём и `Simulation.run`, и поток кокпита `EngineThread`. Параметры конструктора plant'а лежат в опыте дословно
(`exp.plant.kwargs`), поэтому `mode4_run` после перехода даёт ряды бит-в-бит как раньше. Пакет `save_bundle`
сверяет отпечаток машины при распаковке (`load_bundle` — с таблицами, `open_bundle` — документом).

### Хранилище ревизий и рабочая копия таблиц (`ss_store.py`, `synchrotronsim.store`)

Источник правды проекта — **хранилище ревизий** `workspace/store/store.sqlite` (протокол — `docs/DATA_PROTOCOL.md`).
Таблицы `workspace/tables` — **рабочая копия** (как в git): скрипты, Excel и модель работают с ней, а правка
становится ревизией по `commit` — с показом разницы. Ревизия машины — срез строк её решётки во всех таблицах
машины (текст ячеек без потерь) + паспорт + ссылка на ревизию справочника устройств.

```powershell
py -3.14 ss_store.py status
```
```powershell
py -3.14 ss_store.py diff 26
```
```powershell
py -3.14 ss_store.py commit -m "заметка к правке"
```
```powershell
py -3.14 ss_store.py log 26
```

| Команда | Что делает |
|---|---|
| `init [-m …]` | первые ревизии из рабочей копии: справочник + все решётки (сделано 2026-11-25) |
| `status [--lattice 26] [--all]` | что изменено и не зафиксировано (изменена / новая / отстала / нет в таблицах) |
| `diff 26[@рев] [--to рев]` | разница по ячейкам: ревизия (по умолчанию последняя) → рабочая копия или другая ревизия |
| `commit -m … [--lattice …]` | изменённое → новые ревизии; если с момента выгрузки кто-то зафиксировал — конфликт |
| `log 26` \| `log library` | история (* — последняя, ч — черновик прогона) |
| `checkout 26@рев [--force] [--with-library]` | ревизию — в рабочую копию (файлы байт-в-байт); правки без `--force` не затираются |
| `export 26[@рев\|@working] папка [--no-excel]` | выгрузка для Excel: запятая, «;», UTF-8 с BOM (+ `.base.json`, `export.json`) |
| `import папка [--commit -m …] [--partial]` | правки из Excel → рабочая копия (наложением; конфликт по одной ячейке — стоп) |

Правка через Excel: `export 26 out\sila26` → открыть `out\sila26\lattice_configs.csv`, поправить, сохранить как CSV →
`import out\sila26` → `status` / `diff 26` → `commit -m …`. Ячейка, совпавшая с исходной на 15 значащих цифрах
(точность Excel), правкой не считается; столбцы в выгрузке не правятся. Миграции (`insert_undulators`, `apply_*`)
правят рабочую копию как раньше — затем `commit`.

Из Python:

```python
from synchrotronsim.store import open_store
st = open_store()                                  # SqliteStore (есть store.sqlite) или хранилище этапа 1
m = st.get("machine", "26")                        # рабочая копия (Machine); "head" — последняя зафиксированная
m0 = st.get("machine", "26", "fb37a0fd27f6")       # ревизия по номеру, префиксу или отпечатку Machine
ref = st.pin(m)                                    # для прогона: найденная ревизия или черновик рабочей копии
st.status(); st.diff("machine", "26"); st.commit_working(note="…")
e = st.get("experiment", "fb:3")                   # опыт; st.commit("experiment", "my", e, parent=…) — ревизия
from synchrotronsim.documents import save_machine, load_machine
save_machine(m, "sila26.ssd"); load_machine("sila26.ssd")   # документ Machine: zip document.json + arrays.npz
```

- Модель счёта таблиц не открывает — получает документ `Machine` (тест `TestModelFromDocuments`). Опыт
  ссылается на машину `exp.lattice_id` + `exp.machine_rev` (пусто — рабочая копия / последняя);
  `Simulation(exp, store=…, machine=…)`.
- Каждый прогон фиксирует ревизию машины (`machine.ref` в паспорте): та же, что уже зафиксирована, или черновая
  ревизия незафиксированной рабочей копии. Без файла `store.sqlite` (хранилище этапа 1) — снимок документа в
  `workspace/store/machine/<id>/<ревизия>.ssd`.
- Экраны решётки берутся только из её машины: у решётки 26 своих строк в `screens` нет — все экраны кокпита
  `SCR_und_NN`, 50×50 мм на 20 м (раньше два из них брали имя и размер из строк решётки 27).
- Правка справочника устройств даёт новые ревизии всех машин (ссылка на справочник — часть ревизии машины).

### Сеть: хранилище, вычислитель и клиент на разных компьютерах (`ss_server.py`, `synchrotronsim.Site`)

Три роли в локальной сети: **хранилище** (компьютер с базой), **вычислитель** (сервер счёта), **клиент**
(библиотека, кокпит). Только стандартная библиотека Python. Подробно — `docs/DATA_PROTOCOL.md`, этап 3.

1. Токен площадки (один раз; файл — на все компьютеры площадки, защищённым способом):
   ```powershell
   py -3.14 ss_server.py token --file lab.token
   ```
2. На компьютере с базой:
   ```powershell
   py -3.14 ss_server.py store --host 0.0.0.0 --port 8701 --token-file lab.token
   ```
3. На вычислителе (адрес хранилища — свой):
   ```powershell
   py -3.14 ss_server.py compute --host 0.0.0.0 --port 8702 --token-file lab.token --store http://db-pc:8701
   ```
4. На своём компьютере — профиль площадки и проверка связи:
   ```powershell
   py -3.14 ss_server.py site add lab --store http://db-pc:8701 --compute tcp://calc-pc:8702 --token-file lab.token
   ```
   ```powershell
   py -3.14 ss_server.py site check lab
   ```
   Проверка показывает задержку, протокол, доступ по токену, сервер (ОС, Python, ядра), коммит кода на сервере и
   **сборку ядра**: тот же файл расширения — результаты бит-в-бит; другая сборка (Linux, другой компилятор) —
   предупреждение: сверять с допуском (паспорт прогона пишет, где считалось).

Работа через площадку:

```powershell
py -3.14 ss_store.py --site lab status
```
```powershell
py -3.14 -m client --site lab
```

```python
from synchrotronsim import Site
from synchrotronsim.experiment import Experiment
from synchrotronsim.simulation import Simulation
lab = Site.load("lab")
print(lab.check())
run = Simulation(Experiment.from_fb(3, smoke=True), on=lab).run()   # счёт на вычислителе, прогон — из хранилища
m = lab.store.get("machine", "26", "head")                         # машина из хранилища площадки
```

- `ss_store.py --site lab …` — те же команды (status, diff, commit, checkout, export, import) против сервера
  хранилища; рабочая копия — таблицы этого компьютера.
- `Simulation(exp, on=lab)`: машина фиксируется в хранилище площадки (черновик, если рабочая копия не
  зафиксирована), вычислителю уходит ссылка; прогон кладётся в хранилище и скачивается в `workspace/runs`.
- Кокпит `--site lab`: модель строится и считается на вычислителе, здесь — сцена, окна и ручки. Подписки,
  отметки «● запись», настройки экранов и записи, пуск и зазоры при пересборке («Опыт…») переносятся. При обрыве
  связи — сообщение в строке состояния; новый сеанс — «Опыт…» → «Применить и перестроить».
- Профили — `~/.synchrotronsim/sites.json`, токены — `~/.synchrotronsim/credentials.json` или переменная
  `SS_TOKEN_<ИМЯ>`; в хранилище и в git токены не попадают. Без токена серверы слушают только 127.0.0.1.
  `ss_server.py site publish lab` — профиль (без токена) в хранилище площадки.
- Ядро на Linux-сервере: `cmake -S . -B build-py -DCMAKE_BUILD_TYPE=Release -DSS_BUILD_PYTHON=ON
  -DPython_EXECUTABLE=$(which python3)` и `cmake --build build-py --target _engine` (нужен nanobind; на Linux ещё не
  проверялось).

### Правка параметров проекта из кокпита (журнал правок)

Окно элемента (клик по магниту в сцене) — блок **«проект (правка)»**: проектные значения ячеек решётки (силы,
поле, длина, срезы, грани, положение и углы) и поле ввода. Две цены:
- **на ходу** — силы G, Gv, S, O: модель применяет правку сразу (ручки ядра; переживает рестарт; кольцо побитово как
  пересобранное при изменении силы меньше чем вдвое);
- **пересборкой** — поле диполя, положение и углы (все обмотки элемента вместе), длина, срезы, грани: правка ждёт
  в журнале, модель пересобирается с ней («Правки…» → «Пересобрать модель», ~20–30 с на реш. 26).

Окно **«Правки…»** (панель инструментов) — журнал: элемент, поле, было → стало, применено ли в модели;
«Отменить», «Повторить», «Пересобрать модель», «Сохранить ревизией…» (правки накладываются на рабочую копию
таблиц и фиксируются ревизией хранилища — то же, что `ss_store.py commit`; если ту же ячейку успели изменить в
рабочей копии — конфликт, ничего не пишется), «Сбросить все». Строка заголовка показывает, совпадает ли машина
модели с журналом. Пересборка из окна «Опыт…» тоже берёт машину с правками. Прогон, записанный на правках, хранит
в паспорте машину модели (черновую ревизию) и список правок. С моделью на вычислителе (`--site`) — так же.

Из Python:

```python
from synchrotronsim.store import open_store
from synchrotronsim.edits import Journal
st = open_store()
lib, sls = st.working_slices([26])
J = Journal(sls["26"], lib, "26")
q = 120                                              # индекс магнита (порядок пучка)
J.push(J.make(q, "mat_G", 3.21, name="QF1"))          # правка; J.machine() — машина с правками
J.undo(); J.redo()
J.save(st, "заметка")                                 # → рабочая копия + ревизия
```

Пока правятся только параметры существующих элементов в `lattice_configs`; структурные правки (вставка,
удаление, смена типа устройства) — следующий шаг (редактор решётки).

## 10. Сравнение моделей — диффур vs кик (element_compare)

`element_compare.py` сопоставляет **диффурную** (C++ SynchrotronTracker, Boris по картам поля) и
**киковую** (Python `matrix_tracker` в режиме `SS_SECTOR` — симплектический drift-kick-drift, порт
elegant KQUAD/KSEXT/KOCT/CSBEND, а **не** передаточные матрицы) модели по одиночным элементам. Собирает
временный одно-элементный конфиг (пучок 13 частиц на старт-плоскости → дрейф → элемент → дрейф →
финиш-плоскость; длины
дрейфов **не** из диффура), гоняет обе модели, фитит физкоэф на каждый ток + **один** L_eff на элемент
(геом. константа). Изгибающие сравниваются в **проекции Френе** (отклонение от опорной дуги).

| Команда | Что делает |
|---|---|
| `element_compare.py <dev> [ток_А] [--arg]` | Один элемент при одном **физическом** токе питания (А, по умолч. 10 А; конвертируется в `arg` карты по виткам + `ENERGY_FACTOR`). Флаг `--arg` — трактовать значение как сырой `arg`. Диффур + фит кика, печать физкоэф, L_eff, RMS невязки. Быстрая проверка. |
| `element_compare.py all quad,sext,oct,dipole,dq` | Полный Word-отчёт сравнения → `…/element_compare_report.docx` (глава/элемент: общий L_eff, таблица ток↔коэф+RMS, xy-проекция пучка, траектории) + датасеты `dataset_<dev>.csv`. |
| `element_compare.py combo <base> [ngrid]` | Комбо-датасет DQ: **все комбинации** токов обмоток I1/I2/I3 (`ngrid=4` ⇒ 4³=64 ≤120). `<base>`=`L400`/`L1000` → `combo_dataset_<base>.csv` (`I1;I2;I3;B;G;RMS`). |
| `element_compare.py matrices` | **Только Word-отчёт** матриц связи ток→физкоэф (прямые + обратные) по всему охвату. Однородный раздел/элемент: матрицы → таблица свипа (RMSE, R², **радиус ρ** у изгибающих) → графики траекторий x/y и сечения x-y при нескольких токах. **Все токи — ФИЗИЧЕСКИЕ амперы питания** (arg × `ENERGY_FACTOR` / витки; сырой arg в отчёте не используется) + % номинала. Не трогает таблицу БД / HTML. Быстро. |
| `element_compare.py library` | **Полный конвейер матриц связи для ВСЕЙ библиотеки** (см. ниже): матрицы+датасеты → таблица БД `coupling_matrices.csv` → Word-отчёт → демо-конфиги → HTML-отчёты. |
| `element_compare.py library <element>` | То же для **ОДНОГО элемента**: матрица+датасет+печать M/M⁺, **upsert только его записи** в таблице БД (остальные не трогает). Word/demo/HTML — только по флагам. |
| `element_compare.py viz-all` | Постоянные демо-конфиги для `visualize.py`/HTML по всем элементам, **id 4–15**, каждый при **проектном токе**. Пишет диффур `trajectories_exp<id>.bin` + кик `…_kick.bin`. |
| `element_compare.py viz <dev> [ток] [id]` | То же для одного элемента (по умолч. — проектный ток, id 4). |

**Флаги `library`** (переопределяют дефолты; для `all`-режима всё включено, для single — только матрица+таблица):
`--report`/`--no-report` (пересобрать Word), `--demo`/`--no-demo` (демо-конфиги), `--html`/`--no-html` (HTML).

Примеры:
```bash
py -3.14 element_compare.py library                       # вся библиотека: матрицы+таблица+Word+demo+HTML
py -3.14 element_compare.py library --no-html             # то же, но без (медленных) HTML-отчётов
py -3.14 element_compare.py library QP_L_1A_L295          # один квад: матрица + upsert его записи в таблице БД
py -3.14 element_compare.py library corrector_100A_L100   # корректор (5 обмоток → B,Bv,G,Gs,S)
py -3.14 element_compare.py library L400 --report         # DQ_L400 + пересобрать общий Word-отчёт
```

### Матрицы связи ток→физкоэф (прямые и обратные)

Для каждого элемента с **проектными данными lte** (`mat_*`) **и** картой поля строится **матрица связи**
`M`: (моменты)ᵀ = `M`·(токи обмоток)ᵀ, элемент `M_ij = ∂(коэф_i)/∂(ток_j)`. Извлечение — из **кика** диффура
(выходные наклоны 13 частиц раскладываются по (Y,Z) до октуполя). Обратная матрица `M⁺` (коэф→ток) —
псевдообратная Мура–Пенроуза (`= M⁻¹` для квадратной невырожденной; мин. норма при избытке обмоток, МНК при
недостатке). При калибровке по токам каждый элемент несёт **только свой момент** (как elegant: квад→G,
sext→S, oct→O; корректор многофункционален → B,Bv,G,Gs,S; DQ→B,G через combo; PM-диполи — фикс. поле,
свипа нет). Это ограничение матриц связи, а не решётки: статические `mat_*` из `.lte` могут нести любые
мультиполи у любого вида (§ импорт .lte).

- **Ток свипа привязан к РАБОЧЕЙ точке** каждого элемента (не фиксирован): слабый квад рабочит при ~2 А,
  гнать его до десятков А бессмысленно. **Лестница свипа, таблицы данных и графики отчёта — РАБОЧАЯ
  ОБЛАСТЬ**: 25–150 % рабочего тока (корректор — до 125 % номинала). **Релевантный диапазон** тока —
  критерий **R² ≥ 0.95** (линейность `коэф = slope·ток`); ищется **отдельными пробами выше рабочей
  области** (до 50 А сырого arg, в таблицы отчёта не входят); в этих пределах матрица (и обратная)
  справедлива.
- **Комбо-проверка суперпозиции** (многообмоточные): предсказание `M·I` сверяется с диффуром на сетке
  комбинаций токов обмоток → `datasets/combo_<element>.csv`. Секступоли <0.1 %; у корректора сильные диполи
  1–4 %, слабые G/S на шумовом полу карты.
- **Датасеты** (`workspace/results/element_compare/datasets/`): `sweep_<element>.csv` (лестница токов →
  извлечённые мультиполи), `combo_<element>.csv` (комбо-проверка).

**Имена моментов** (`MULTIPOLES` в `element_compare.py`, `out_label` в таблице БД). Выходные наклоны проб
`x′`, `y′` раскладываются по `(x, y)`; момент = `−(производная наклона)/(QP·L)` (у диполей — без минуса):

| момент | из кика | смысл | столбец решётки |
|---|---|---|---|
| `B` | `x′` в центре | нормальный диполь, горизонтальный изгиб | `mat_B` |
| `Bv` | `y′` в центре | вертикальный изгиб (скью-диполь) | нет (`mat_Bv` в БД нет) |
| `G` | `∂x′/∂x` | нормальный квадруполь | `mat_G` |
| `Gs` | `∂x′/∂y` | **скью-квадруполь**, связь `y→x′` | **нет** |
| `S` | `∂²x′/∂x²` | нормальный секступоль | `mat_S` |
| `O` | `∂³x′/∂x³` | нормальный октуполь | `mat_O` |

⚠️ **`Gs` — не `mat_Gv`.** В ядрах SynchrotronSim (`matrix_tracker.py`, `src/matrix_core.h`) `mat_Gv` —
НОРМАЛЬНЫЙ вертикальный градиент `k1v = QP·mat_Gv` (`∂B_y/∂v`, фокусировка `y→y′`; пусто ⇒ `= mat_G`,
гармонический градиент). Матрицы связи его не измеряют: `∂y′/∂y` в разложение не входит. До 2026-11-16
скью-квадруполь назывался `Gv`, и `_design_ivec` (решатель проектных токов, его же зовёт `design_currents.py`)
брал проект скью-момента из `mat_Gv` решётки. Теперь у `Gs` столбца нет (`MOMENT_MATCOL`): проект = 0, момент
не управляется и в `mat_*` не пишется. Таблицы со старой меткой `Gv` читаются как `Gs`
(`design_currents.LEGACY_MOMENT_ALIAS`), а UPSERT переименовывает её и в файле.
Другие подсистемы (`linear_coupling.py`, `saturation_solve.py`, `library_report.py`, датасеты
`currents_to_kicks/`) пока зовут скью-квадруполь по старой схеме `Gv` (рядом `Bv`, `Sv`/`Ss`). В `lattice_configs` они не пишут, но
столбец `mat_Gv` датасетов `currents_to_kicks` — тоже скью, а не `k1v` ядра.

### Формат отчёта: Word, LibreOffice, PDF

Отчёты собираются в `.docx` **чистым Python** (`python-docx`) — Microsoft Word для сборки не нужен,
на Linux и macOS всё работает, а LibreOffice открывает `.docx` напрямую. Нужен другой формат —
конвертирует сама LibreOffice, второго генератора документов в проекте нет:

```powershell
py -3.14 office_convert.py workspace/results/element_compare/element_compare_report.docx --to odt
py -3.14 office_convert.py <отчёт>.docx --to pdf [--outdir куда]
```

В оболочке формат выбирается **до сборки** — список «Формат отчёта» рядом с кнопками измерения.
DOCX собирается напрямую; при ODT/PDF конвертация ставится в очередь СЛЕДОМ за сборкой и делается
автоматически. Кнопка «Конвертировать готовый» переводит уже собранный отчёт в выбранный формат, не
пересобирая его. Путь итогового файла и его состояние («есть, 8.0 МБ, 24.08 15:33» / «ещё не
собран») показаны строкой под кнопками. Нужна установленная LibreOffice: ищется в `PATH` и типовых
местах, путь переопределяется `SS_SOFFICE`.

**Формулы.** `latex2omml.py` делает НАТИВНЫЕ формулы Word: `latex2mathml` (чистый Python) → OMML
через XSL `MML2OMML.XSL` **из Microsoft Office**. Файл — часть Office, скопировать в репозиторий
нельзя, но путь переопределяется `MML2OMML_XSL`: перенеся копию с Windows-машины, нативные формулы
получают и на Linux. Без XSL формулы вставляются ТЕКСТОМ (курсивом) и печатается предупреждение —
отчёт при этом собирается целиком.

### Таблица БД `workspace/tables/coupling_matrices.csv`

Постоянная таблица со **всеми** матрицами (прямыми и обратными). **UPSERT:** `library <element>` обновляет
**только** запись данного магнита, чужие не трогает. Длинный формат, `;`-разделитель, точка-десятичная.
Одна строка = один элемент матрицы:

| колонка | смысл |
|---|---|
| `element`, `kind` | имя элемента, вид (quad/sext/oct/kicker/dq/dipole) |
| `n_windings`, `n_moments` | размер матрицы: обмоток × моментов |
| `direction` | `forward` (коэф←ток), `inverse` (ток←коэф), `fixed` (PM — фикс. поле) |
| `out_label`, `in_label` | выход←вход: forward — момент←обмотка; inverse — обмотка←момент (имена моментов — выше; скью-квадруполь `Gs`) |
| `value` | элемент матрицы (`coef/A` для forward, `A/coef` для inverse) |
| `units`, `eff_length`, `i_op`, `imax`, `r2` | единицы, L_eff, рабочий ток, релевантный |ток| (R²≥0.95), R² линейности |

Восстановление матрицы: сгруппировать строки по `(element, direction)`. Проверка: `M·M⁺ ≈ I`.

### Проектные токи обмоток (`design_currents.py`)

Обратная задача по УЖЕ измеренным матрицам: проектные `mat_*` решётки (`.lte`) → токи обмоток.
Считает мгновенно — это линейная алгебра над таблицей `coupling_matrices.csv`, диффур не гоняется.

```powershell
py -3.14 design_currents.py                 # таблица на экран + workspace/tables/design_currents.csv
py -3.14 design_currents.py --lattice 2     # проектные mat_* берутся из этой решётки
py -3.14 design_currents.py --no-save --quiet
```

Столбцы: `element; kind; winding; device; arg; current_a; turns; nominal_a; percent; status` —
**сырой ток** (`arg` карты, вход модели) и **физический ток питания** (А при 6 ГэВ = `arg` ×
`ENERGY_FACTOR` / витки-на-катушку) с процентом номинала. Элементы без проектных `mat_*` (корректоры)
и PM-диполи помечаются в `status`.

⚠️ **Свежесть матриц.** Матрица описывает конкретную карту поля и геометрию, поэтому при обновлении
таблицы `element_compare` кладёт рядом **отпечаток входных данных** каждого элемента —
`workspace/tables/coupling_matrices.inputs.json` (хэш от `map_bin_path`, `nominal_arg`,
`use_symmetry`, `field_direction`, `correct_coeff`, `rot_x/y/z_deg` и `eff_length`/`kind` решётки 1).
`design_currents.py` сверяет его с текущим состоянием и называет ИМЕННО ТЕ элементы, чьи матрицы
устарели. Лечится пересборкой: `element_compare.py library --no-report --no-demo --no-html`.

Сравнение идёт по данным, а НЕ по датам файлов: `element_compare` сам переписывает
`lattice_configs.csv` по ходу работы (временные одно-элементные конфигурации, а с `--demo` — ещё и
демо-конфигурации ПОСЛЕ записи таблицы), поэтому таблица оказывалась «старее» собственных входов
сразу после честной пересборки. Витки и номинал в отпечаток не входят — они пересчитывают `arg` в
амперы уже после измерения и читаются всегда свежими.

### HTML-отчёты элементов

`library` (или `--html`) для каждой демо-конфигурации вызывает `viz_html` →
`workspace/results/html/element_<dev>.html` — самодостаточный (offline) HTML: **3D-визуализация** магнита с
траекториями сверху + графики траекторий в **относительных координатах** (`x(s)`, `y(s)`) снизу.

- **Токи:** прямые токовые свипятся вокруг рабочей точки; DQ — вокруг **рабочего** тока (~3–7 А; ±50 А =
  перегруз ×17, пучок раздувается); PM-диполи — одна конфигурация (поле фиксировано). Проектный ток может
  быть **отрицательным** (полярность обмотки).
- **Число киков** (`SS_SECTOR_NSL`, дефолт 5) на невязку **не влияет** — интегратор Йошида-4 сошёлся;
  остаток у нелинейных элементов — от шума карты поля, а не дискретизации.
- **3D-сравнение:** после `viz-all`/`viz` — `visualize.py <id>` (диффур цветной по частицам + кик поверх;
  цвет/толщина кика — `kick_color`/`kick_line_width` в `visualizer.json`). Кик в лаб-XYZ получается
  наложением локальных координат на опорную орбиту в рамке Френе.

### Сверка кикового ядра с elegant (`verify_elegant.py`)

Один и тот же алгоритм (`ring_analysis.py`) считается поверх двух трекеров: SynchrotronSim — **продакшн-ядро
C++** через сервер кольца (`ring_cpp.CppRing` → `MatrixTracker --ring-serve`, решётка БД установки) — и elegant
(`elegant_diag.ElegantRing`, та же решётка). Python-ядро `matrix_tracker.py` (`ring_analysis.Ring`) в опытах
не трекает: оно эталон, с которым C++ сверяется опытом `kernel`. Всё — из трекинга: матрицы разностями
(4-точечная схема, шаг 1e-5), частоты NAFF, затухание по собственным числам и спаду амплитуды, эмиттанс
методом Чао (траектории по срезам изгибов — `CppRing.track_pieces`).

```
py -3.14 verify_elegant.py kernel       # C++-ядро против Python-эталона на решётке установки
py -3.14 verify_elegant.py linear       # орбита, β, α, ψ, η, частоты, αc (+ twiss_output elegant)
py -3.14 verify_elegant.py matrices     # матрицы 6×6 магнитов (+ matrix_output)
py -3.14 verify_elegant.py chrom        # ν(δ), ξ1…ξ3, αc2: отображение ring_map, twiss_output, трекинг обоих
py -3.14 verify_elegant.py integrator   # частоты при N_SLICES 3…40 и порядке 2/4/6
py -3.14 verify_elegant.py tbt          # портреты, спектр, ν от амплитуды (1024 об.), ∂ν/∂J, driving terms
py -3.14 verify_elegant.py long         # ВЧ, U0, Qs, времена затухания (4096 об.) + интегралы излучения
py -3.14 verify_elegant.py rad          # портреты с излучением (40000 об.) + ансамбль 64 частиц с ISR
py -3.14 verify_elegant.py emit         # равновесные εx, σδ, σz: Чао, moments_output, интегралы обеих программ
py -3.14 verify_elegant.py fma          # динамическая апертура, карта частот, сетка резонансов
                                        # (сетка и порог потери — fma_x_mm/fma_y_mm/loss_limit_m установки)
py -3.14 verify_elegant.py analytic     # аналитические матрицы элементов и аффинные матрицы стыков
py -3.14 verify_elegant.py response     # матрицы отклика, коррекция орбиты по SVD, допуска на магниты
py -3.14 verify_report.py               # → workspace/results/verify_elegant_report.docx
py -3.14 verify_report_params.py --machine siberia   # глава на параметр → verify_elegant_params_siberia.docx
```

`verify_report_params.py` — второй формат отчёта: глава 1 — установка и настройки обеих программ, далее по главе на параметр (физический смысл → чем считается → результаты → расхождения отдельной таблицей в конце главы). Данные те же, что у `verify_report.py`; графики орбиты, β и η строятся из кэша в `…/params_report/`.

**Установка — ключ `--machine`** (есть у каждого опыта и у отчёта). Описания в `elegant_diag.MACHINES`:
`sila` (описание + линия, решётка 1 БД, 6 ГэВ) и `siberia` (чужой `s2lattice.lte` берётся файлом целиком,
его линия оборачивается в `SSRING`, решётка 2 БД, 3 ГэВ). Из описания берутся энергия, номер решётки,
промежуток до первого магнита, число супериодов, ВЧ, корректоры, число срезов интегратора и амплитуды
сканов. Результаты чужой установки — в подпапке её имени, отчёт — отдельным файлом:

```
py -3.14 verify_elegant.py linear --machine siberia
py -3.14 verify_report.py --machine siberia    # → workspace/results/verify_elegant_report_siberia.docx
```

Матричный механизм (аналитика, без трекинга): `ring_matrix.py` — матрицы элементов и АФФИННЫЕ матрицы
стыков (модифицированных дрейфов), `py -3.14 ring_matrix.py twiss|check`; `ring_response.py` — матрицы
отклика орбиты на корректоры, обращение SVD, допуска на градиенты, `py -3.14 ring_response.py orbit|tolerances`.
Только секторный режим ядра.

Высшие порядки (аналитика): `ring_map.py` — отображение оборота до порядка N (по умолчанию 5 в опыте `chrom`)
методом дифференциальной алгебры: усечённые ряды по (x, px, y, py, t, δ); стыки — точная формула пролёта между
гранями над рядами (клин входит во все порядки), тела элементов — `exp(L·D)` по векторному полю ядра (без
срезов), края — тонкие линзы. Даёт замкнутую орбиту рядом по δ, ξ1…ξ(N−1) и αc, αc2:
`py -3.14 ring_map.py --lattice 2 --lead 1.4335 --mev 3000`. Готча: элементы разложены около нуля, поэтому
при ненулевой орбите (клинья стыков) старший коэффициент получает подмешивание от усечённого порядка N+1 —
для ξ3 брать N = 5.

`ring_map.normal_form(ring, order=4)` — НОРМАЛЬНАЯ ФОРМА: отображение вокруг замкнутой орбиты переводится в
комплексный базис (линейная часть = поворот), заменой переменных степень за степенью убираются нерезонансные
члены, и остаётся зависимость угла поворота от действий — `∂ν/∂J` (`dnux/dJx`, `dnux/dJy`, `dnuy/dJy`,
`dnuy/dJx`). Действие `J = (q² + (αq + βp)²)/(2β)` (ε = 2J, как у elegant). Контроль внутри результата —
`|re|dnu…`: у настоящей нормальной формы резонансный коэффициент чисто мнимый. Готчи: ветвь частоты
выбирается по частоте Куранта–Снайдера блока 2×2 (у собственного вектора фаза может идти в обратную сторону);
трекинговую оценку ∂ν/∂J брать по САМЫМ МАЛЫМ амплитудам (дальше вступают J² и дробная частота
«заворачивается»); сдвигать ряд к орбите только через `da.var(i, z0)` — `da.var(i) + z0` прибавляет число ко
ВСЕМ коэффициентам ряда (эта ошибка ломала симплектичность на 1e-6).

`ring_matrix.radiation_integrals(ring, nodes=8)` — интегралы излучения I₁…I₅ по описанию решётки (без
трекинга): изгибы проходятся узлами Гаусса–Лежандра, β/α/η/η′ в узлах берутся из матриц, у граней
учитывается краевой член I₄ (`−Σ η·h²·tg E`). Дальше U₀, Jx/Jy/Js, τx/τy/τs, εx, σδ, αc, а при `ring.rf` —
Qs, φs, σz. Совпадает с `radiation_integrals` elegant до 1e-7 на обеих установках:
`py -3.14 ring_matrix.py radiation --lattice 2`.

Результаты и кэш — `workspace/results/verify_elegant/<опыт>/` (`--refresh` пересчитывает). SynchrotronSim
параллелится внутри C++ (OpenMP по частицам), elegant — потоками по запускам. На C++ все опыты Сибири, кроме
`rad` и `fma`, укладываются в пару минут; `rad` (ансамбль 64 × 40000 об.) и `fma` упираются в elegant
(~3.7 мс на частицу-оборот при 40 срезах). У каждого запуска elegant с ISR свой `random_number_seed`.

**Точность геометрии в БД.** Импортёр чужой решётки `s2lattice_to_db.py` пишет x/y/yaw и eff_length с
ПОЛНОЙ точностью double (12 знаков после запятой). Раньше было `%.6f` (шаг 1 мкм) и `%.5f` у длины —
от этого у Сибири была остаточная замкнутая орбита ±2,3 мкм, невязка периметра 0,585 мкм и остаток
аналитической пары νx 6,7·10⁻⁷ / β 4,9·10⁻⁶. После перезаливки: периметр сходится с .lte до 8·10⁻¹¹ м,
νx до 2·10⁻¹³, β до 1·10⁻¹¹, орбита 0,0005 мкм. ГОТЧА: C++-ядро берёт `eff_length`, `kind` и `n_slices`
ИЗ СТРОКИ `lattice_configs` (Python умеет падать на hardware_library/element_transforms, C++ — нет);
импортёр обязан их заполнять, иначе длины элементов в C++ станут нулевыми.

**ГОТЧА ОПОРНОГО ИМПУЛЬСА (найдена 2026-09-21).** elegant считает `p_central` по СВОЕЙ массе электрона
0.51099906 МэВ (старое значение), а `elegant_diag.ME_MEV` — современная 0.51099895069. Если писать
частицы по нашей массе, elegant видит их с δ = +2.1·10⁻⁷: появляется «замкнутая орбита» η(s)·δ
(0.24 мкм у Сибири — форма в точности повторяет дисперсию) и сдвиг частот ξ·δ (3.6·10⁻⁶ по νx,
2.7·10⁻⁶ по νy). Именно это годами выглядело как «предел интегратора». Теперь `elegant_me()` один раз
на процесс узнаёт массу по `pCentral` из служебного twiss, а `write_particles` получает `pc` явно.
После фикса осевая частица за оборот смещается на 0.46 нм у ОБЕИХ программ (при 160 срезах 0.0035 нм),
Δνx = 3.6·10⁻⁹. Диагностика на будущее: прогнать осевую частицу по элементам — если кик появляется
в первом же CSBEND и пропорционален ANGLE, это рассогласование импульса, а не модель изгиба. Постоянные НЕ подгоняются: `ME_MEV` остаётся современной (наше значение точнее), согласованы
только единицы передачи координат; `ME_ELEGANT_MEV = 0.51099906` рядом с ней — документированное
значение elegant, `elegant_me()` предупреждает, если измеренный `pCentral` даёт другое. Остаточный
пол: γ у программ всё равно разные, поэтому U₀ ∝ γ⁴ несёт ~4·δ₀ (измерено 4.3·10⁻⁷). В отчётах это
объясняет `verify_report.mass_section(R, head)` — в основном отчёте своя глава, в отчёте по
показателям h2 в конце главы 1; все числа берутся из summary.csv, а не зашиты.

Готчи: `twiss_output`/`matrix_output` elegant — точные матрицы, не N_SLICES (частоты отличаются от трекинга на
0.01/0.03); `higher_order_chromaticity` — только при `default_order=3`; решётку 1 заполнять
`warmstart_ring.py 1 --lte-dir workspace/lte/configuration_v1_closed`.

**Число срезов у elegant.** По умолчанию `N_SLICES=1` у `KQUAD`/`KSEXT` и 4 у `CSBEND` (`track.h`,
`track_data.c`), то есть линза проходится ОДНИМ шагом интегратора. У СИЛА линзы длинные и слабые, и это
незаметно; у Сибири (`K1` до 4.07 м⁻², набег 0.79 на линзу) один шаг ошибается на 0.7 % по силе линзы, и
трекинг elegant расходится с его же матрицами настолько, что кольцо выходит НЕУСТОЙЧИВЫМ (cos μx = 4.76).
Ставить число срезов обоим трекерам одинаково: elegant — `&alter_elements name=*, type=KQUAD, item=N_SLICES`,
SynchrotronSim — `SS_SECTOR_NSL` (до сборки кольца). Поэлементно — `SS_NSL_DEV="dev=n,…"` (по типу устройства):
клиент ставит 1 срез полюсам ондуляторов (`TbtPlant(id_pole_nsl=1)`, `client.engine.build_session`): 2280 из
4920 элементов СИЛА-26, трекинг вдвое быстрее, тюн −2e-8, частица через 200 оборотов (СИ+ВЧ) 2e-5 от амплитуды.

## 11. Конвенции и грабли

- **Знак изгиба:** положительный `ANGLE` из `.lte` = поворот **ВПРАВО** (yaw убывает), как в
  elegant/MAD. Отсюда `+x` смотрит **наружу** кольца. Единственный источник конвенции —
  `lte_to_lattice.step`; `design_orbit`, `s2lattice_to_db`, `lte_ring` берут её оттуда.
  Следствие: `k1=+K1`, `k2=+K2`, `k3=+K3` из `.lte` верны дословно, а `mat_B = −ANGLE/(QP·L_eff)`
  (`warmstart_ring.py:28`). Если уложить кольцо зеркально, переворот потребуется кикам ЧЁТНЫМ по x
  (диполь ∝x⁰, секступоль ∝x²), а нечётным (квадруполь ∝x¹, октуполь ∝x³) — нет.
- **Все `mat_*` абсолютные у любого вида**, мультиполи допустимы у любого магнита (тело выбирается по полю,
  §4). Правило «у `dipole` `mat_G/Gv/S/O` — доли `mat_B`» отменено 2026-11-16 (из-за него CSBEND с `K2`
  без `K1` импортировался с неверным секступолем); демо-решётки 12/13 переведены в абсолютные значения.
  Пустой `mat_Gv` ⇒ `Gv = mat_G` (гармонический градиент), `"0"` ⇒ вертикальный градиент нулевой.
- **Мультиполи в изгибающих элементах** берут `u = x − x_ref`, где `x_ref` — прогиб опорной дуги
  (`Magnet._ref_bow`): ящик прямой, а опорная внутри изгиба отходит от оси на сагитту `L·θ₀/8`.
  Без этого сама опорная ловит кик `k1·сагитта` (у DQ_L1000 это ~2 мм за элемент). elegant решает то
  же конструктивно: `CSBEND` — СЕКТОР, рама гнётся вместе с опорной.
- **`sp_elements.csv` — точка правки токов руками** (шаблон супериода → всё кольцо). После правки
  нужен `assemble_lattice_configs.py`.
- **Тюн не применён намеренно:** `mat_*` = проектные K из `.lte`, чтобы сверка с elegant шла на одних
  и тех же коэффициентах.
- **Легаси** (скрипты опытов, отчёты, внешние коды) — в `legacy/`, в сценарии не нужны. Токовый режим и
  матрицы связи (`coupling_matrix`, `element_coupling`) архивированы. Ядро на физкоэф. — эталонный Python
  `matrix_tracker.py` (в режиме `SS_SECTOR` = киковый, §4) + автономный C++ `MatrixTracker.exe` (§4,
  валидируется бит-в-бит против Python).
- Сборка C++ (при изменении `src/`): CMake → `build/SynchrotronTracker.exe`, `SynchrotronOptimizer.exe`.

## 12. Графическая оболочка

```powershell
gui.bat                        # или: py -3.14 gui_app.py
```

**Ярлык.** В корне проекта лежит `SynchrotronSim.lnk` — запускает оболочку через `pythonw.exe`, без
консольного окна. Ярлык хранит абсолютные пути, поэтому в git не входит; на новой машине (или после
переноса проекта) пересоздаётся:

```powershell
py -3.14 make_shortcut.py                 # ярлык в корне проекта
py -3.14 make_shortcut.py --desktop       # ещё и на рабочий стол
py -3.14 make_shortcut.py --console       # с консольным окном (видно ранние ошибки запуска)
```

Иконка рисуется в `gui/synchrotronsim.ico` (требуется Pillow; без него берётся иконка интерпретатора).
Запуск без консоли означает, что `print` не виден, поэтому ошибки старта оболочка показывает окном.

Окно на PySide6 поверх всего конвейера. **Оболочка не считает сама** — она собирает те же командные
строки, запускает их процессами и стримит вывод в общий журнал внизу окна. Поэтому результат из окна
и из консоли совпадает, а расхождение оболочки с CLI невозможно по построению. Код — в `gui/`,
точка входа `gui_app.py`.

**Проект** — связка «файл решётки `.lte` ↔ решётка и опыт в базе». Реестр проектов:
`workspace/configs/gui_projects.json` (сама база одна, конфигурации в ней сосуществуют по
`lattice_id`). При старте — окно выбора проекта либо мастер нового.

**Решётки из базы предлагаются сами.** Реестр — файл оболочки, а решётки могли быть загружены
раньше или из консоли, поэтому окно выбора показывает вторым списком «найдено в базе»: все
содержательные решётки `lattice_configs.csv` (демо-конфигурации в один элемент отбрасываются).
Источник восстанавливается из фактов, а не угадывается: суб-решётки и их названия — из
`sub_lattices.json` (наследуют `.lte` родителя), основная — из `lte_mapping.json[lattice_id]`, её
папка `.lte` — из манифеста снимка базы; сторонние плоские решётки сопоставляются плоским
конфигурациям только при однозначном соответствии. Не удалось определить `.lte` — поле пустое,
проект всё равно рабочий (путь нужен лишь для перезагрузки решётки). При открытии найденная решётка
попадает в реестр.

**Мастер нового проекта** (4 шага): файл/папка `.lte` (формат определяет `load_config`) → проверка
кольца `lte_ring.py` с возможностью записать замкнутую копию → пучок (готовая группа из базы либо
новая: 5 частиц «центр + 4 спутника» или 13 «центр + 12 по кругу», радиус, скорость, масса, заряд) →
номера решётки/опыта и `load_config.py … --force`.

| Вкладка | Что делает |
|---|---|
| **Проект и база** | сводка проекта; правка таблиц базы (`experiments`, `particle_groups`, `radiation_params`, `rf_cavities`, `pulsed_kickers`, `kicker_timing`, `bpm_config`, `sp_elements`, `lattice_configs`, `hardware_library`, `design_currents`, `coupling_matrices`) с фильтром, добавлением/удалением строк и резервной копией при записи; кнопки `assemble_lattice_configs`, `warmstart_ring`, `load_config --force`, `db_snapshot save/check` |
| **Матрицы связи** | `element_compare.py matrices` / `library` (флаги отчёта, демо-конфигураций, HTML) / `library <элемент>` / `all`; **формат отчёта** DOCX/ODT/PDF с автоматической конвертацией после сборки; кнопка **проектных токов** (`design_currents.py`) с показом таблицы и предупреждением о свежести матриц; открытие отчёта |
| **Симуляция** | выбор опыта, **установки и пучка** (см. ниже) и ядра: **C++ диффур** (`track3.py --mode diff`), **C++ кик** (`MatrixTracker --track/--full`), **Python кик** (`track3.py --mode kick-phys`); обороты, режим записи (глобальные / локальные / длинный), одна частица со смещением; излучение (СИ, ISR, ВЧ, проектная энергия); остановка расчёта |
| **Визуализация** | `visualize.py` и `live_visualizer.py` отдельными окнами; **«Траектория кикового ядра → 3D»** (`matrix_traj_export.py inject`); снимок `viz_shot.py` с предпросмотром внутри окна; **два HTML-отчёта**: 3D-сцена (`viz_html.py`, лёгкая/детальная/обе) и анализ траектории (`traj_analyzer.py`) |

**Грабли оболочки:**
- **Излучение у C++ кикового ядра** задаётся не флагами, а ПРАВИЛОМ из `radiation_params.csv`
  (§4), поэтому переключатели излучения при этом ядре **правят строку опыта в этой таблице**
  (прежняя версия уходит в `workspace/tables/backups/`). У Python-кика — обычные флаги, база не
  меняется. У диффурного ядра излучения нет — переключатели гаснут.
- **ВЧ работает только в длинном режиме** (турн-by-turn у плоскости), поэтому в остальных режимах
  переключатель ВЧ недоступен.
- **Режим записи определяет, что дальше можно посмотреть:** глобальные траектории → `visualize.py`
  и HTML-сцена; локальные/длинный → `traj_analyzer.py`. Диффурное ядро пишет только глобальные,
  C++ киковое — только `.npz`. Хотите 3D-картинку от КИКОВОГО ядра (или диффурный `.bin` протух) —
  кнопка «Траектория кикового ядра → 3D» перезапишет `trajectories_exp<N>.bin` его орбитой.
- **Отчёты ложатся в РАЗНЫЕ папки:** 3D-сцена — в `workspace/results/html/`, анализ траектории — в
  `workspace/results/`. Полный путь каждого (и собран ли он, какого размера, когда) написан прямо
  под кнопками, у каждого своя кнопка «Открыть». Имя файла можно задать своё — поле «Имя файла»,
  пусто ⇒ имя по умолчанию (оно же показано подсказкой); расширение `.html` добавляется само.
- **Вид отчёта об анализе траектории выбирается САМ** — `traj_analyzer` смотрит поле `mode` в
  `.npz`: запись «локальные координаты» ⇒ подробный отчёт x(S), y(S), спектр и тюны; запись
  «длинный турн-by-turn» ⇒ x(оборот), огибающая амплитуды и фазовый портрет (тысячи оборотов,
  график прорежен). Кнопка одна; что именно получится — написано строкой под кнопками просмотра
  (там же — дата файлов, число частиц и точек).
- **Установку и пучок можно выбрать любые.** По умолчанию они подставляются из строки опыта; если
  выбрать другую пару, перед запуском выполняется `track3.py --author-only --exp N --lattice L
  --group G` — он переписывает установку и пучок в строке опыта (плоскости опыта не трогает: новой строке —
  плоскости по умолчанию, остальное — `exp_planes.py`). Так все три ядра стартуют из одной конфигурации (автономный C++ MatrixTracker
  читает только базу, флагов установки/пучка у него нет). Оболочка предупреждает жёлтой строкой,
  какой опыт будет переписан; чтобы не трогать существующий — заведите свободный номер опыта в
  `experiments.csv`.
- **Очередь одна:** команды выполняются последовательно, кнопки на время работы гаснут — два
  трекинга одновременно испортили бы общие таблицы базы. Кнопка **«Остановить»** — в шапке журнала
  (общая для всех вкладок, активна только пока идёт задача).
- **Прерывание безопасно.** `element_compare` временно правит 4 таблицы базы (`lattice_configs`,
  `element_connectivity`, `particle_groups`, `experiments`) и возвращает их в конце. Если процесс
  УБИТЬ (кнопка «Остановить», закрытие окна), возврат не отработает, поэтому перед правкой снимается
  копия в `workspace/tables/_cmp_backup/` и ставится метка `in_progress`. Метка, пережившая процесс,
  означает прерывание: при следующем запуске инструмента таблицы возвращаются из копии
  автоматически (в журнале — строка «прошлый прогон был прерван»).
- **Консольные окна не всплывают.** Дочерние программы (`SynchrotronTracker`, `MatrixTracker`, `git`)
  запускаются с `_common.no_window()` — Windows не выдаёт им отдельного окна, при этом вывод
  по-прежнему идёт в журнал оболочки и в консоль при запуске из терминала. Новый вызов
  `subprocess` в продакшн-скрипте добавляйте с `**no_window()`.
- После правки `sp_elements.csv` оболочка напоминает про пересборку — без неё ядра прочтут прежние
  значения (§3).
