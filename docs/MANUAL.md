# Мануал — SynchrotronSim (командный справочник)

Все команды — из корня проекта. Интерпретатор — **`py -3.14`** (в нём numpy, pandas, pyvista, scipy,
matplotlib). Диффурное ядро — бинарь `build\SynchrotronTracker.exe`, оптимизатор —
`build\SynchrotronOptimizer.exe` (собираются из `src/` через CMake).

> **То же самое мышкой:** `gui.bat` (или `py -3.14 gui_app.py`) — графическая оболочка над всем
> конвейером ниже. Она ничего не считает сама, а запускает эти же команды и показывает их вывод,
> поэтому результаты совпадают. См. **§12**.

> **Linux / macOS.** Везде ниже вместо `py -3.14` пишите `python3` (лаунчер `py` — только Windows),
> вместо `gui.bat` — `./gui.sh`. Бинари собираются без суффикса (`build/SynchrotronTracker`), код
> подставляет его сам через `_common.exe_name`. Каталог исходных карт ANSYS лежит вне репозитория и
> задаётся переменной `SS_ANSYS_DIR` (по умолчанию — путь рабочей машины). Единственное, чего нет
> вовсе, — ярлык `make_shortcut.py` (`.lnk` — формат Windows).

**Установки в БД:** `1` — СИЛА, полное кольцо (2082 магнита, замкнутое); `2` — Сибирь (сторонний
импорт, 144 магнита); `3` — SP1, первый супериод СИЛЫ (53 магнита). Эксперименты `1`/`2`/`3` ссылаются

## 1. Проверка и замыкание .lte

**`lte_ring.py`** — универсальный инструмент, работает по ПУТИ к файлу, ничего не знает про имена
папок и установок.

```powershell
py -3.14 lte_ring.py ring.lte                                  # один файл с LINE=(...) — только отчёт
py -3.14 lte_ring.py desc.lte --line line.lte                  # последовательность отдельным файлом
py -3.14 lte_ring.py desc.lte --line line.lte --out fixed.lte  # записать замкнутую копию
py -3.14 lte_ring.py ring.lte --beamline RING --out fixed.lte  # выбрать линию, если их несколько
```

Без `--out` ничего не пишет. Форматы определяются по содержимому: голый список токенов в отдельном
файле (СИЛА), `NAME: LINE=(&...)` внутри файла (Сибирь, elegant); разворот с вложенностью, `n*ELEM`, `-SUB`.

**Что проверяет:**
- **Σ ANGLE** по кольцу — замыкание по УГЛУ (нужно ровно 2π).
- **Замыкание по ПОЛОЖЕНИЮ** — прогон всей линии **с дрейфами**, зазор конец→начало. Это ОТДЕЛЬНОЕ
  условие: угол свести мало, кольцо может не сойтись в точку.
  ⚠️ Мерить «выход последнего магнита → вход первого» **нельзя** — на стыке стоит законный длинный
  дрейф (`RING` начинается с `DR_01_2P651` = 2.651 м), и такой замер даёт метры мнимого зазора.
- **δ = E1+E2−ANGLE** — константность внутри группы (тип+длина). Если разошлась, сборка БД упадёт
  в `build_matrix_db.add_edge_delta`.

**Чем замыкает:** масштабирует ANGLE **и E1/E2** чистых диполей (без K1) на
`close_scale = (2π − Σ ANGLE_DQ) / Σ ANGLE_pure`; combined-function (K1≠0) не трогает. Края обязаны
ехать тем же множителем, иначе δ перестаёт быть константой типа.

### Приведение чужого .lte к плоскому виду (`lte_flatten.py`)

Файлы установок приходят в разном синтаксисе: многострочные определения через `&`, вложенные линии,
повторители `38*CELL`, МАТРИЧНЫЕ типы элементов (`SBEN/QUAD/SEXT/OCTU`), служебные элементы (импеданс,
апертура, ВЧ, WATCH). Загрузчик `s2lattice_to_db` ждёт одно определение на строку и одну развёрнутую
линию `ring: LINE=(...)`, а сверка с elegant — КИКОВЫЕ типы (иначе elegant считает элемент матрицей и
`N_SLICES` на него не действует). `lte_flatten.py` делает и то и другое за один проход.

```powershell
py -3.14 lte_flatten.py вход.lte --list                        # какие линии есть в файле
py -3.14 lte_flatten.py вход.lte --beamline R                  # только отчёт (состав, периметр, зазор)
py -3.14 lte_flatten.py вход.lte --beamline R --out workspace/lte/configuration_vN/имя.lte
```

Переводит `SBEN/RBEN/BEND → CSBEND`, `QUAD → KQUAD`, `SEXT → KSEXT`, `OCTU → KOCT`,
`EDRIFT/DRIFT → DRIF`; ставит `N_SLICES` (`--n-slices`, по умолчанию 5); выбрасывает то, чего нет в
матричной модели (ВЧ, апертуры, импеданс, заряд, WATCH) и печатает, что именно. Силы и углы НЕ
трогает — замыканием занимается `lte_ring.py`.

⚠️ **Готча продолжений строк.** `&` в конце переносит ТОЛЬКО следующую строку; пустая строка обрывает
определение — так читает сам elegant. Если склеивать `&\s*\n\s*` (с `\s`, который ест переводы
строк), определение съедает соседние и часть элементов теряется.

### Импорт плоского .lte как новой решётки

```powershell
py -3.14 s2lattice_to_db.py --lte workspace/lte/configuration_v5_sila2026/sila2026.lte `
    --lattice 26 --exp 26 --prefix "sila26_"
```

`--prefix` — префикс имён устройств (по умолчанию `s2_`), `--n-slices` — срезы в строке решётки
(по умолчанию 40), `--monitors` — заводить `MONI` как датчики положения (`kind=monitor`, устройство
`BPM`). ⚠️ Датчики ломают определение старт/финиш-плоскости у замкнутого кольца (все 400 носят одно
имя `BPM`) — по умолчанию выключены.

Изгиб **с градиентом** заводится видом `dq`, а не `dipole`: у `dipole` ядро считает `mat_G`
ОТНОСИТЕЛЬНЫМ градиентом (`src/matrix_core.h`, `g *= b`), у `dq` — абсолютным. Края `E1/E2`
переносятся со знаком угла: `edge = −E` (в БД `θ0 = −ANGLE`).

## 2. Загрузка конфигурации в БД

**`load_config.py`** принимает ПУТЬ (папку или файл):

```powershell
py -3.14 load_config.py --list                                     # что лежит в workspace/lte/
py -3.14 load_config.py workspace/lte/configuration_v1_closed --force
py -3.14 load_config.py path/to/desc.lte --line path/to/line.lte --force
py -3.14 load_config.py path/to/ring.lte --lattice 2 --force       # сторонний плоский .lte
py -3.14 load_config.py --config v1 --force                        # короткое имя (удобство)
py -3.14 load_config.py <путь> --parse-only                        # только разбор, БД не трогается
```

| Формат | Определяется по | Пайплайн |
|---|---|---|
| **desc+line** | `*_desc.lte` + `*_line.lte` | `lte_to_lattice` → `assemble_lattice_configs` → `build_matrix_db` → `warmstart_ring` → `assemble --sync-subs` |
| **плоский** | один `.lte` с `LINE=(...)` | `s2lattice_to_db` |

- `--force` обязателен, если решётка уже есть: полная загрузка **сбрасывает `mat_*` к проектным K**
  из `.lte` (бэкапы → `workspace/tables/backups/`).
- **Конфигурации сосуществуют.** Загрузка объявляет СВОИ решётки (сама + суб-решётки из
  `sub_lattices.json`) и передаёт их вниз через `--lattices`; строки чужих установок переносятся как
  есть, со всеми столбцами. Раньше каждая загрузка СИЛЫ стирала Сибирь — теперь нет.
- **Порядок конвейера важен:** он обязан заканчиваться `assemble_lattice_configs.py --sync-subs`.
  `assemble` создаёт суб-решётки в начале, когда `mat_*` ещё пусты, а заполняют их следующие шаги и
  только у родителя — без финального шага суб-решётка остаётся с нулевой физикой.

### Отдельные шаги (вызывает load_config, можно и вручную)

| Команда | Что делает |
|---|---|
| `lte_to_lattice.py [--lte-dir DIR]` | `.lte` → `sp_elements.csv` (шаблон супериода) + `lattice_layout.csv` (геометрия экземпляров). Существующие `arg_val` сохраняются. |
| `assemble_lattice_configs.py` | Шаблон + геометрия → `lattice_configs.csv`. Запускать после правки `sp_elements.csv`. |
| `assemble_lattice_configs.py --sync-subs` | Суб-решётки = копия родителя со всеми столбцами. ПОСЛЕ warmstart. |
| `build_matrix_db.py [--lte-dir DIR] [--lattices 1,3]` | Структурные столбцы, края E1/E2 и δ из `.lte` папки `DIR`, связность. `--lattices` — какие решётки можно перезаписывать. |
| `warmstart_ring.py N [--lte-dir DIR]` | `mat_*` решётки N = проектные K из `.lte`. |
| `lte_to_design_orbit.py` | `.lte` → сегменты опорной орбиты (для оптимизатора). |
| `s2lattice_to_db.py --lte <файл> --lattice N --exp M` | Импорт стороннего плоского `.lte`. |

## 3. Откуда ядра читают конфигурацию

**Оба ядра читают `lattice_configs.csv`** — матричное (`matrix_tracker.py:186`) и диффурное C++
(`src/main.cpp:174`, по индексам столбцов). Это и есть «большая таблица»: строка на каждый экземпляр
магнита, со своей геометрией и коэффициентами. `element_connectivity.csv` задаёт **порядок** обхода.

```
.lte → lte_to_lattice → sp_elements.csv   (ШАБЛОН: слот в супериоде, правится руками)
                      → lattice_layout.csv (геометрия каждого экземпляра)
                           ↓ assemble_lattice_configs
                      → lattice_configs.csv   ← ОБА ЯДРА ЧИТАЮТ ЭТО
                           ↓ build_matrix_db  (структурные столбцы, края)
                           ↓ warmstart_ring   (mat_* = проектные K)
                           ↓ assemble --sync-subs
```

⚠️ **Адресные правки в `lattice_configs.csv` живут до следующей пересборки.** `assemble` берёт
`arg_val`/`correct_coeff` из ШАБЛОНА по ключу `(sp_type, sp_element_id)` — то есть все супериоды
получают одно значение слота, — а `mat_*` следом перезаписывает `warmstart`. Сценарий рабочий:
«собрал → поправил руками → посчитал», просто не перезагружать `.lte` после правок. Сохранение
per-instance правок между пересборками сознательно не делалось (решение 2026-07-17: не усложнять БД).

## 4. Трекинг

```powershell
py -3.14 track3.py --author-only --exp 20 --lattice 1 --group 3    # только конфиг опыта (установка+пучок+плоскость)
py -3.14 track3.py --mode kick-phys --exp 1 [--turns N] [--thin ε_мм] [--local]
py -3.14 track3.py --mode kick-phys --exp 1 --long --turns 10000 --sr --rf ideal   # излучение + затухание
py -3.14 track3.py --mode diff      --exp 1
```

Установка и пучок берутся из `experiments.csv[exp]`; `--lattice`/`--group` переопределяют (и создают
строку опыта, если её нет). Траектории (ГЛОБАЛЬНЫЕ X,Y,Z) → `workspace/results/trajectories_expN.bin` —
их пишет **только `track3.py`**, поэтому после любой правки физики прогоните его заново, иначе визуализатор
покажет старое.

**`--local`** доп. пишет `trajectories_local_expN.npz` — **ЛОКАЛЬНЫЕ** координаты матядра (S · x · x'≡px · y ·
y'≡py · ct · δ + элемент, на границах элементов). Локальный трек идёт СЕКТОРНОЙ моделью `m.body()` (x =
отклонение от опорной орбиты, бит-в-бит elegant), поэтому `track3.py` по умолчанию форсит `SS_SECTOR=1`
(`SS_SECTOR=0` — боксовая; глоб. `.bin` всегда боксовый `body_global`). ГОТЧА: боксовая модель диполей
раздувает пучок (её `x` = отклонение от ПРЯМОЙ оси), секторная — нет.

**`traj_analyzer.py N [--no-open] [--out f.html] [--csv]`** — анализ траектории в относительных координатах,
**ИНТЕРАКТИВНОЕ ОКНО** (самодостаточный HTML, авто-открытие в браузере; панели тянутся мышкой за разделители):
таблица общей информации, координаты x(S)/y(S) раздельно, спектр колебаний (**Фурье** — амплитуда по
**ЧАСТОТЕ (МГц)**, `частота = Q·c/кольцо`, пучок v≈c; у явных пиков вертикальный пунктир + ранг + тюн Q + частота). Для
**многооборотных опытов** (`track3 --turns K --local`) x(S)/y(S) — **ПОЛНАЯ траектория за все K оборотов**
(склейка S=0..K·кольцо, равномерно прорежена), спектр за K оборотов даёт **точный тюн** Qx/Qy с дробной
частью (напр. 55.22), плюс выживание за K оборотов в таблице. `--csv` — сводка запятой-десятичной; `--no-open`
— не открывать окно.

**ДЛИННЫЙ режим (10к+ оборотов):** полную траекторию не переварить, поэтому `mte.long_trajectories(lattice,
group, n_turns, states_override)` пишет (x,x') у плоскости РАЗ ЗА ОБОРОТ (поле `mode='long'` в .npz).
`traj_analyzer` сам детектит long-режим и строит отчёт: таблица · x(оборот) · **огибающая амплитуды** ·
**фазовый портрет (x,x')** цвет по обороту (эллипс=сохранение, спираль=затухание/рост). `states_override`
(список 6-состояний у плоскости) — трек ПРОИЗВОЛЬНОЙ частицы вместо пучка группы (сканы апертуры).

### Синхротронное излучение и затухание амплитуд (SR + ВЧ)

```powershell
# длинный турн-by-turn трек СИЛЫ (радиация/ВЧ берутся из radiation_params.csv по exp_id — флаги не нужны):
py -3.14 track3.py --mode kick-phys --exp 1 --long --turns 10000 --x0-mm 5
py -3.14 traj_analyzer.py 1            # огибающая покажет затухание (спад амплитуды)
```

**ПРАВИЛО (таблица `workspace/tables/radiation_params.csv`):** трекер (матричное ядро) проверяет её по
`exp_id` **перед запуском**. Есть строка для опыта → синхротронное излучение учитывается (энергия/ВЧ из
строки); **нет строки → СИ не учитывается** (дефолт). Столбцы: `exp_id; design_energy_mev; isr(0/1);
rf(none/ideal); rf_voltage_mv; rf_harmonic` (два последних — задел под синусоидальный ВЧ). Загрузчик —
`matrix_tracker.load_radiation(exp_id)`. Так проектная энергия не хардкодится в код, а лежит по машине в БД.
CLI-флаги ниже **перекрывают** таблицу (приоритет аргумент > БД > дефолт).

`--long` — длинный турн-by-turn трек СЕКТОРНОЙ моделью (минует боксовый глоб. путь), пишет
`trajectories_local_expN.npz` (`mode='long'`) для `traj_analyzer`. `--x0-mm/--y0-mm` — ОДНА частица
со смещением вместо пучка группы.

- **`--sr`** — **распределённое синхротронное излучение**: на каждом срезе изгиба частица теряет энергию
  `δ −= rad_coef·(1+δ)²·F²·ds` (порт elegant `integrate_csbend_ordn`). `rad_coef = (2/3)·r_e·γ³/ρ²`.
  ГОТЧА: трекер гоняет **сурогатный** пучок (γ≈7 из `particle_groups.csv`), а SR ∝ γ⁴ зависит от
  **ПРОЕКТНОЙ** энергии — её задаёт **`--design-mev`** (СИЛА `6000`, дефолт). Всё в формуле дробное
  (δ, нормир. F, сохранение угла `QX/(1+δ)`), поэтому проектную γ подставляем прямо в `rad_coef`.
  Проверка: осевая частица теряет за оборот СИЛЫ **U₀ = 1.99 МэВ** (совпало 0.17%).
- **`--rf ideal`** — идеальный ВЧ-резонатор: восстанавливает δ до значения начала оборота (компенсация
  потерь). Именно ВЧ переводит падение канонич. импульса в диполях в **затухание поперечного УГЛА** — без
  ВЧ распределённая SR только роняет δ, углы не гасит (сохраняются). Проверка: τx≈14.7, τy≈22.3 мс.
- **`--isr`** (требует `--sr`) — квантовое возбуждение ISR (гауссов шум фотонов) для равновесного
  эмиттанса/энергоразброса. Без него амплитуда затухает к нулю; с ним — к равновесию.

По умолчанию (нет строки опыта в `radiation_params.csv` и нет флагов) радиации нет (`rad_coef=0`), тело
бит-в-бит как раньше (симплектика). Флаги-переопределения: `--sr`/`--isr`/`--rf`/`--design-mev` (env
`SS_SR`/`SS_ISR`/`SS_DESIGN_MEV`). Диффурное ядро (`--mode diff`) радиацию не моделирует — правило только
для матричного. См. `matrix_tracker._body_sector_symplectic` и `load_radiation`.

### Автономное матричное ядро на C++ (MatrixTracker)

```powershell
cmake --build build --target MatrixTracker           # собрать (MinGW g++ / MSVC через CMake)
./build/MatrixTracker.exe --track 1 10000 5 0        # СИЛА, 10к об., 1 частица x0=5мм → .npz
py -3.14 traj_analyzer.py 1                           # Python ТОЛЬКО рисует
```

C++ ядро (`src/matrix_core.h` физдвижок + `src/matrix_ring.h` кольцо) считает **автономно**: читает БД
(`experiments`/`lattice_configs`/`element_connectivity`/`particle_groups`/`radiation_params`), строит кольцо
с полной геометрией (`frame`/`_rot`, секторные дуги, `modified_drift`), инжектирует пучок, трекает N оборотов
с СИ+ВЧ (правило `radiation_params.csv`) и пишет `results/trajectories_local_exp<exp>.npz` для `traj_analyzer`.
Python больше **не считает** — только БД/анализ/визуализация. Режимы:
- `--track <exp> <turns> [x0_mm y0_mm]` — turn-by-turn у плоскости + ВЧ → mode=long (затухание/огибающая);
- `--full <exp> <turns> [x0_mm y0_mm]` — запись на границах элементов → mode=full (x(S)/спектр/тюны, без ВЧ);
- `--element …` — тело одного элемента (валидация). x0/y0 ⇒ одна частица (скан).
- `--ring-serve <lattice> <lead_m|nan> <design_mev> <sr> <isr> <nsl> <order> <rf> <volt_mv> <harmonic> <phase_deg> <seed>`
  — **сервер кольца для анализа** (`src/matrix_ring_serve.h`): порт `ring_analysis.Ring` (плоскость наблюдения
  перед первым магнитом, ВЧ как RFCA с FIDUCIAL=light, СИ и ISR по срезам изгибов, у каждой частицы свой
  генератор). Двоичный протокол по stdin/stdout: `TRACK`/`TBT`/`ELEM`/`PIECES`/`JUNCTION` + float64,
  `INFO`/`PIECEMETA`, возмущения `KICK`/`VKICK j θ` (гор./верт. доп. кик) / `DK j dk` (±Δ нормального
  градиента k1 обеих плоскостей — BBA) / `DSK j dks` (скью-градиент ks, связь x↔y — коррекция связи) /
  `YAW j α` / `RESET`. Частицы параллельно (OpenMP). Python-обёртка —
  `ring_cpp.CppRing` (интерфейс как у `ring_analysis.Ring`: `track`, `track_tbt`, `track_elements`,
  `track_pieces`, `with_kick`, `with_yaw`, `perturbed`, `junction`; `apply_perturb(kicks, vkicks, dks, dsks)`
  — RESET + набор возмущений на том же сервере, ошибки рассогласования сохраняются); сверка с
  Python-эталоном — до 1e-11, быстрее в 150–450 раз.

Python-ядро `matrix_tracker.py` — **эталон** для разработки/опытов: новое явление сначала в Python, потом порт
в C++; регрессия `test_matrix_core_cpp.py` (элемент, бит-в-бит) и `test_matrix_core_ring.py` (кольцо+npz,
end-to-end ~1e-11) ловит расхождение до бита; сервер кольца — `TestRingCpp` в `test_synchrotronsim.py`.
ISR и порядок Йошиды 2/4/6 портированы (сервер кольца); box-тело — только кик корректора (`hkick`, дрейф–кик–дрейф
по `n_slices` из БД) для опытов с откликом орбиты.

**Режимы:** `diff` — диффурное ядро (Boris по картам поля, эталон); `kick-phys` — **киковое** ядро
(`matrix_tracker`, симплектич. drift-kick-drift в режиме `SS_SECTOR`, а не передаточные матрицы) на
физкоэф. `mat_*` из `.lte`. Токовый режим (`kick-current`) **архивирован**: связь ток↔физкоэф. не была
доверенной, ядро читает только `mat_*`.

### Ошибки установки: ансамбль машин (`--errors`)

Ядро трекает решётку по геометрии x/y/z/yaw/pitch/roll и полям mat_* из `lattice_configs`, поэтому
ошибки моделируются как ВОЗМУЩЁННАЯ решётка. Допуски (СКО) задаются по типу магнита в
**`workspace/tables/element_errors.csv`** (`kind; dx; dy; dz; dyaw; dpitch; droll; field_pct` — сдвиги [м],
повороты [рад], ошибка поля [%]).

```powershell
py -3.14 facility_report.py 26 --errors                 # ансамбль 32 машин, → facility_exp26_errors.html
py -3.14 facility_report.py 26 --errors --correct       # + коррекция орбиты → facility_exp26_errors_corr.html
py -3.14 facility_report.py 26 --errors --correct --nsl 12   # ансамбль в ~3× быстрее (см. ниже)
py -3.14 facility_report.py 26 --errors --seeds 64 --turns 1024
py -3.14 facility_report.py 26 --errors --errors-table my_tol.csv --cutoff 3
```

**`--nsl` (срезов магнита в трекинге).** По умолчанию 40 — «геройская» точность для паспорта идеальной
машины. Для ансамбля это избыточно: бенчмарк ДА решётки 26 показал, что граница (+x/−x = 7.219 мм)
**идентична** при nsl от 40 до 6, а расхождение маски выживания (~20 ячеек из 656) — фрактальный шум на
краю, не ошибка интегратора; лёгкий дрейф числа выживших начинается лишь с nsl=8. Значит для ансамблей
безопасно `--nsl 12` (граница не сдвигается, с запасом над точкой дрейфа) — время ×3 меньше (прогон
32/1024 с коррекцией: ~3–4 ч → ~1 ч). Матрица отклика кэшируется отдельно на каждый nsl.

`errors.py`: на каждый seed рисует гауссовы (обрезка `--cutoff`·σ) отклонения на КАЖДЫЙ экземпляр,
сдвигает его в ЛОКАЛЬНОЙ рамке (u,v,axis по yaw/pitch/roll), поворачивает, масштабирует поля на (1+δ),
и пишет возмущённую рабочую папку во временный каталог; ядро запускается на ней через новый аргумент
`--ws` сервера (`ring_cpp.CppRing(ws=...)`). Реальная БД не трогается.

Отчёт: ДА как **доля выживших машин**, средняя карта диффузии, импульсная как доля, таблица влияния
(искажение орбиты СКО, разброс частот, доля неустойчивых машин). По умолчанию (без `--errors`) — идеал.

### Коррекция орбиты (`--correct`)

Ультрамалоэмиттансное кольцо СИЛА **без** коррекции терпит лишь ~10–20 мкм рассогласования (при 30+ мкм
орбита разлетается). Реальные допуски 50–100 мкм работают только с коррекцией замкнутой орбиты
корректорами. Флаг `--correct` (вместе с `--errors`) включает глобальную коррекцию на **каждой** машине
ансамбля — отчёт тогда отражает уже скорректированную установку.

`orbit_correct.py` — стандартная схема «матрица отклика + SVD»:
- **корректоры** — магниты `kind=kicker` (в решётках СИЛА это слоты SH1A/SH2B/SH3E; 120 штук, гор.+верт.);
- **точки наблюдения** — выходы всех магнитов (least-squares гладит орбиту по всему кольцу);
- **матрица отклика** R (BPM × корректоры, отдельно x/y) считается ОДИН раз на идеальной решётке
  (≈2–3 мин) и кэшируется в `workspace/results/orbit_resp_exp{N}_nsl{nsl}.pkl` (инвалидация по
  n_mag/периметру/nsl; рядом хранится причинная матрица T для протяжки);
- на каждый seed: измерить искажённую орбиту → θ = −R⁺·o (псевдообратная через SVD, `rcond=1e-2`) →
  применить кики (`CppRing.apply_perturb`: RESET сохраняет ошибки, сбрасывает лишь кики) → повторить
  4 раза → трекинг ДА/диффузии на скорректированном кольце. Настройка **стационарна** для данной машины.

**Бутстрап протяжкой (threading).** При больших ошибках замкнутой орбиты из нуля нет (Ньютон расходится),
и штатный SVD не стартует. Тогда `_thread` сначала гасит ОДНООБОРОТНУЮ траекторию причинной матрицей
отклика T (кик влияет лишь ниже по ходу), сектор за сектором, с недорелаксацией, — пока не появится
замкнутая орбита, — и лишь затем идёт штатный SVD. Важно гасить до МАЛОЙ траектории (не «до апертуры»):
большая орбита через секступоли даёт feed-down и уводит тюн на резонанс. Протяжка сдвигает потолок
коррекции с ~15 до ~30 мкм (доля вытянутых машин: 20 мкм 16→88 %, 30 мкм 0→63 %). Таблица влияния
показывает, сколько машин вытянуто протяжкой.

Таблица влияния тогда показывает: число корректоров, СКО орбиты **до → после** коррекции (x и y),
СКО и максимум углов корректоров. Значения в `element_errors.csv` — плейсхолдеры ~10 мкм.

## 10. Сравнение моделей — диффур vs кик (element_compare)

`element_compare.py` сопоставляет **диффурную** (C++ SynchrotronTracker, Boris по картам поля) и
**киковую** (Python `matrix_tracker` в режиме `SS_SECTOR` — симплектический drift-kick-drift, порт
elegant KQUAD/KSEXT/KOCT/CSBEND, а **не** передаточные матрицы) модели по одиночным элементам. Собирает
временный одно-элементный конфиг (пучок 13 частиц → дрейф → элемент → дрейф → финиш-плоскость; длины
дрейфов **не** из диффура), гоняет обе модели, фитит физкоэф на каждый ток + **один** L_eff на элемент
(геом. константа). Изгибающие сравниваются в **проекции Френе** (отклонение от опорной дуги).

| Команда | Что делает |
|---|---|
| `element_compare.py <dev> [ток_А] [--arg]` | Один элемент при одном **физическом** токе питания (А, по умолч. 10 А; конвертируется в `arg` карты по виткам + `ENERGY_FACTOR`). Флаг `--arg` — трактовать значение как сырой `arg`. Диффур + фит кика, печать физкоэф, L_eff, RMS невязки. Быстрая проверка. |
| `element_compare.py all quad,sext,oct,dipole,dq` | Полный Word-отчёт сравнения → `…/element_compare_report.docx` (глава/элемент: общий L_eff, таблица ток↔коэф+RMS, xy-проекция пучка, траектории) + датасеты `dataset_<dev>.csv`. |
| `element_compare.py combo <base> [ngrid]` | Комбо-датасет DQ: **все комбинации** токов обмоток I1/I2/I3 (`ngrid=4` ⇒ 4³=64 ≤120). `<base>`=`L400`/`L1000` → `combo_dataset_<base>.csv` (`I1;I2;I3;B;G;RMS`). |
| `element_compare.py matrices` | **Только Word-отчёт** матриц связи ток→физкоэф (прямые + обратные) по всему охвату. Однородный раздел/элемент: матрицы → таблица свипа (RMSE, R², **радиус ρ** у изгибающих) → графики траекторий x/y и сечения x-y при нескольких токах. **Все токи — ФИЗИЧЕСКИЕ амперы питания** (arg × `ENERGY_FACTOR` / витки; сырой arg в отчёте не используется) + % номинала. Не трогает таблицу БД / HTML. Быстро. |
| `element_compare.py library` | **Полный конвейер матриц связи для ВСЕЙ библиотеки** (см. ниже): матрицы+датасеты → таблица БД `coupling_matrices.csv` → Word-отчёт → демо-конфиги → HTML-отчёты. |
| `element_compare.py library <element>` | То же для **ОДНОГО элемента**: матрица+датасет+печать M/M⁺, **upsert только его записи** в таблице БД (остальные не трогает). Word/demo/HTML — только по флагам. |
| `element_compare.py viz-all` | Постоянные демо-конфиги для `visualize.py`/HTML по всем элементам, **id 4–15**, каждый при **проектном токе**. Пишет диффур `trajectories_exp<id>.bin` + кик `…_kick.bin`. |
| `element_compare.py viz <dev> [ток] [id]` | То же для одного элемента (по умолч. — проектный ток, id 4). |

**Флаги `library`** (переопределяют дефолты; для `all`-режима всё включено, для single — только матрица+таблица):
`--report`/`--no-report` (пересобрать Word), `--demo`/`--no-demo` (демо-конфиги), `--html`/`--no-html` (HTML).

Примеры:
```bash
py -3.14 element_compare.py library                       # вся библиотека: матрицы+таблица+Word+demo+HTML
py -3.14 element_compare.py library --no-html             # то же, но без (медленных) HTML-отчётов
py -3.14 element_compare.py library QP_L_1A_L295          # один квад: матрица + upsert его записи в таблице БД
py -3.14 element_compare.py library corrector_100A_L100   # корректор (5 обмоток → B,Bv,G,Gv,S)
py -3.14 element_compare.py library L400 --report         # DQ_L400 + пересобрать общий Word-отчёт
```

### Матрицы связи ток→физкоэф (прямые и обратные)

Для каждого элемента с **проектными данными lte** (`mat_*`) **и** картой поля строится **матрица связи**
`M`: (моменты)ᵀ = `M`·(токи обмоток)ᵀ, элемент `M_ij = ∂(коэф_i)/∂(ток_j)`. Извлечение — из **кика** диффура
(выходные наклоны 13 частиц раскладываются по (Y,Z) до октуполя). Обратная матрица `M⁺` (коэф→ток) —
псевдообратная Мура–Пенроуза (`= M⁻¹` для квадратной невырожденной; мин. норма при избытке обмоток, МНК при
недостатке). Каждый элемент несёт **только свой момент** (как elegant: квад→G, sext→S, oct→O; корректор
многофункционален → B,Bv,G,Gv,S; DQ→B,G через combo; PM-диполи — фикс. поле, свипа нет).

- **Ток свипа привязан к РАБОЧЕЙ точке** каждого элемента (не фиксирован): слабый квад рабочит при ~2 А,
  гнать его до десятков А бессмысленно. **Лестница свипа, таблицы данных и графики отчёта — РАБОЧАЯ
  ОБЛАСТЬ**: 25–150 % рабочего тока (корректор — до 125 % номинала). **Релевантный диапазон** тока —
  критерий **R² ≥ 0.95** (линейность `коэф = slope·ток`); ищется **отдельными пробами выше рабочей
  области** (до 50 А сырого arg, в таблицы отчёта не входят); в этих пределах матрица (и обратная)
  справедлива.
- **Комбо-проверка суперпозиции** (многообмоточные): предсказание `M·I` сверяется с диффуром на сетке
  комбинаций токов обмоток → `datasets/combo_<element>.csv`. Секступоли <0.1 %; у корректора сильные диполи
  1–4 %, слабые G/S на шумовом полу карты.
- **Датасеты** (`workspace/results/element_compare/datasets/`): `sweep_<element>.csv` (лестница токов →
  извлечённые мультиполи), `combo_<element>.csv` (комбо-проверка).

### Формат отчёта: Word, LibreOffice, PDF

Отчёты собираются в `.docx` **чистым Python** (`python-docx`) — Microsoft Word для сборки не нужен,
на Linux и macOS всё работает, а LibreOffice открывает `.docx` напрямую. Нужен другой формат —
конвертирует сама LibreOffice, второго генератора документов в проекте нет:

```powershell
py -3.14 office_convert.py workspace/results/element_compare/element_compare_report.docx --to odt
py -3.14 office_convert.py <отчёт>.docx --to pdf [--outdir куда]
```

В оболочке формат выбирается **до сборки** — список «Формат отчёта» рядом с кнопками измерения.
DOCX собирается напрямую; при ODT/PDF конвертация ставится в очередь СЛЕДОМ за сборкой и делается
автоматически. Кнопка «Конвертировать готовый» переводит уже собранный отчёт в выбранный формат, не
пересобирая его. Путь итогового файла и его состояние («есть, 8.0 МБ, 24.08 15:33» / «ещё не
собран») показаны строкой под кнопками. Нужна установленная LibreOffice: ищется в `PATH` и типовых
местах, путь переопределяется `SS_SOFFICE`.

**Формулы.** `latex2omml.py` делает НАТИВНЫЕ формулы Word: `latex2mathml` (чистый Python) → OMML
через XSL `MML2OMML.XSL` **из Microsoft Office**. Файл — часть Office, скопировать в репозиторий
нельзя, но путь переопределяется `MML2OMML_XSL`: перенеся копию с Windows-машины, нативные формулы
получают и на Linux. Без XSL формулы вставляются ТЕКСТОМ (курсивом) и печатается предупреждение —
отчёт при этом собирается целиком.

### Таблица БД `workspace/tables/coupling_matrices.csv`

Постоянная таблица со **всеми** матрицами (прямыми и обратными). **UPSERT:** `library <element>` обновляет
**только** запись данного магнита, чужие не трогает. Длинный формат, `;`-разделитель, точка-десятичная.
Одна строка = один элемент матрицы:

| колонка | смысл |
|---|---|
| `element`, `kind` | имя элемента, вид (quad/sext/oct/kicker/dq/dipole) |
| `n_windings`, `n_moments` | размер матрицы: обмоток × моментов |
| `direction` | `forward` (коэф←ток), `inverse` (ток←коэф), `fixed` (PM — фикс. поле) |
| `out_label`, `in_label` | выход←вход: forward — момент←обмотка; inverse — обмотка←момент |
| `value` | элемент матрицы (`coef/A` для forward, `A/coef` для inverse) |
| `units`, `eff_length`, `i_op`, `imax`, `r2` | единицы, L_eff, рабочий ток, релевантный |ток| (R²≥0.95), R² линейности |

Восстановление матрицы: сгруппировать строки по `(element, direction)`. Проверка: `M·M⁺ ≈ I`.

### Проектные токи обмоток (`design_currents.py`)

Обратная задача по УЖЕ измеренным матрицам: проектные `mat_*` решётки (`.lte`) → токи обмоток.
Считает мгновенно — это линейная алгебра над таблицей `coupling_matrices.csv`, диффур не гоняется.

```powershell
py -3.14 design_currents.py                 # таблица на экран + workspace/tables/design_currents.csv
py -3.14 design_currents.py --lattice 2     # проектные mat_* берутся из этой решётки
py -3.14 design_currents.py --no-save --quiet
```

Столбцы: `element; kind; winding; device; arg; current_a; turns; nominal_a; percent; status` —
**сырой ток** (`arg` карты, вход модели) и **физический ток питания** (А при 6 ГэВ = `arg` ×
`ENERGY_FACTOR` / витки-на-катушку) с процентом номинала. Элементы без проектных `mat_*` (корректоры)
и PM-диполи помечаются в `status`.

⚠️ **Свежесть матриц.** Матрица описывает конкретную карту поля и геометрию, поэтому при обновлении
таблицы `element_compare` кладёт рядом **отпечаток входных данных** каждого элемента —
`workspace/tables/coupling_matrices.inputs.json` (хэш от `map_bin_path`, `nominal_arg`,
`use_symmetry`, `field_direction`, `correct_coeff`, `rot_x/y/z_deg` и `eff_length`/`kind` решётки 1).
`design_currents.py` сверяет его с текущим состоянием и называет ИМЕННО ТЕ элементы, чьи матрицы
устарели. Лечится пересборкой: `element_compare.py library --no-report --no-demo --no-html`.

Сравнение идёт по данным, а НЕ по датам файлов: `element_compare` сам переписывает
`lattice_configs.csv` по ходу работы (временные одно-элементные конфигурации, а с `--demo` — ещё и
демо-конфигурации ПОСЛЕ записи таблицы), поэтому таблица оказывалась «старее» собственных входов
сразу после честной пересборки. Витки и номинал в отпечаток не входят — они пересчитывают `arg` в
амперы уже после измерения и читаются всегда свежими.

### HTML-отчёты элементов

`library` (или `--html`) для каждой демо-конфигурации вызывает `viz_html` →
`workspace/results/html/element_<dev>.html` — самодостаточный (offline) HTML: **3D-визуализация** магнита с
траекториями сверху + графики траекторий в **относительных координатах** (`x(s)`, `y(s)`) снизу.

- **Токи:** прямые токовые свипятся вокруг рабочей точки; DQ — вокруг **рабочего** тока (~3–7 А; ±50 А =
  перегруз ×17, пучок раздувается); PM-диполи — одна конфигурация (поле фиксировано). Проектный ток может
  быть **отрицательным** (полярность обмотки).
- **Число киков** (`SS_SECTOR_NSL`, дефолт 5) на невязку **не влияет** — интегратор Йошида-4 сошёлся;
  остаток у нелинейных элементов — от шума карты поля, а не дискретизации.
- **3D-сравнение:** после `viz-all`/`viz` — `visualize.py <id>` (диффур цветной по частицам + кик поверх;
  цвет/толщина кика — `kick_color`/`kick_line_width` в `visualizer.json`). Кик в лаб-XYZ получается
  наложением локальных координат на опорную орбиту в рамке Френе.

### Сверка кикового ядра с elegant (`verify_elegant.py`)

Один и тот же алгоритм (`ring_analysis.py`) считается поверх двух трекеров: SynchrotronSim — **продакшн-ядро
C++** через сервер кольца (`ring_cpp.CppRing` → `MatrixTracker --ring-serve`, решётка БД установки) — и elegant
(`elegant_diag.ElegantRing`, та же решётка). Python-ядро `matrix_tracker.py` (`ring_analysis.Ring`) в опытах
не трекает: оно эталон, с которым C++ сверяется опытом `kernel`. Всё — из трекинга: матрицы разностями
(4-точечная схема, шаг 1e-5), частоты NAFF, затухание по собственным числам и спаду амплитуды, эмиттанс
методом Чао (траектории по срезам изгибов — `CppRing.track_pieces`).

```
py -3.14 verify_elegant.py kernel       # C++-ядро против Python-эталона на решётке установки
py -3.14 verify_elegant.py linear       # орбита, β, α, ψ, η, частоты, αc (+ twiss_output elegant)
py -3.14 verify_elegant.py matrices     # матрицы 6×6 магнитов (+ matrix_output)
py -3.14 verify_elegant.py chrom        # ν(δ), ξ1…ξ3, αc2: отображение ring_map, twiss_output, трекинг обоих
py -3.14 verify_elegant.py integrator   # частоты при N_SLICES 3…40 и порядке 2/4/6
py -3.14 verify_elegant.py tbt          # портреты, спектр, ν от амплитуды (1024 об.), ∂ν/∂J, driving terms
py -3.14 verify_elegant.py long         # ВЧ, U0, Qs, времена затухания (4096 об.) + интегралы излучения
py -3.14 verify_elegant.py rad          # портреты с излучением (40000 об.) + ансамбль 64 частиц с ISR
py -3.14 verify_elegant.py emit         # равновесные εx, σδ, σz: Чао, moments_output, интегралы обеих программ
py -3.14 verify_elegant.py fma          # динамическая апертура, карта частот, сетка резонансов
                                        # (сетка и порог потери — fma_x_mm/fma_y_mm/loss_limit_m установки)
py -3.14 verify_elegant.py analytic     # аналитические матрицы элементов и аффинные матрицы стыков
py -3.14 verify_elegant.py response     # матрицы отклика, коррекция орбиты по SVD, допуска на магниты
py -3.14 verify_report.py               # → workspace/results/verify_elegant_report.docx
py -3.14 verify_report_params.py --machine siberia   # глава на параметр → verify_elegant_params_siberia.docx
```

`verify_report_params.py` — второй формат отчёта: глава 1 — установка и настройки обеих программ, далее по главе на параметр (физический смысл → чем считается → результаты → расхождения отдельной таблицей в конце главы). Данные те же, что у `verify_report.py`; графики орбиты, β и η строятся из кэша в `…/params_report/`.

**Установка — ключ `--machine`** (есть у каждого опыта и у отчёта). Описания в `elegant_diag.MACHINES`:
`sila` (описание + линия, решётка 1 БД, 6 ГэВ) и `siberia` (чужой `s2lattice.lte` берётся файлом целиком,
его линия оборачивается в `SSRING`, решётка 2 БД, 3 ГэВ). Из описания берутся энергия, номер решётки,
промежуток до первого магнита, число супериодов, ВЧ, корректоры, число срезов интегратора и амплитуды
сканов. Результаты чужой установки — в подпапке её имени, отчёт — отдельным файлом:

```
py -3.14 verify_elegant.py linear --machine siberia
py -3.14 verify_report.py --machine siberia    # → workspace/results/verify_elegant_report_siberia.docx
```

Матричный механизм (аналитика, без трекинга): `ring_matrix.py` — матрицы элементов и АФФИННЫЕ матрицы
стыков (модифицированных дрейфов), `py -3.14 ring_matrix.py twiss|check`; `ring_response.py` — матрицы
отклика орбиты на корректоры, обращение SVD, допуска на градиенты, `py -3.14 ring_response.py orbit|tolerances`.
Только секторный режим ядра.

Высшие порядки (аналитика): `ring_map.py` — отображение оборота до порядка N (по умолчанию 5 в опыте `chrom`)
методом дифференциальной алгебры: усечённые ряды по (x, px, y, py, t, δ); стыки — точная формула пролёта между
гранями над рядами (клин входит во все порядки), тела элементов — `exp(L·D)` по векторному полю ядра (без
срезов), края — тонкие линзы. Даёт замкнутую орбиту рядом по δ, ξ1…ξ(N−1) и αc, αc2:
`py -3.14 ring_map.py --lattice 2 --lead 1.4335 --mev 3000`. Готча: элементы разложены около нуля, поэтому
при ненулевой орбите (клинья стыков) старший коэффициент получает подмешивание от усечённого порядка N+1 —
для ξ3 брать N = 5.

`ring_map.normal_form(ring, order=4)` — НОРМАЛЬНАЯ ФОРМА: отображение вокруг замкнутой орбиты переводится в
комплексный базис (линейная часть = поворот), заменой переменных степень за степенью убираются нерезонансные
члены, и остаётся зависимость угла поворота от действий — `∂ν/∂J` (`dnux/dJx`, `dnux/dJy`, `dnuy/dJy`,
`dnuy/dJx`). Действие `J = (q² + (αq + βp)²)/(2β)` (ε = 2J, как у elegant). Контроль внутри результата —
`|re|dnu…`: у настоящей нормальной формы резонансный коэффициент чисто мнимый. Готчи: ветвь частоты
выбирается по частоте Куранта–Снайдера блока 2×2 (у собственного вектора фаза может идти в обратную сторону);
трекинговую оценку ∂ν/∂J брать по САМЫМ МАЛЫМ амплитудам (дальше вступают J² и дробная частота
«заворачивается»); сдвигать ряд к орбите только через `da.var(i, z0)` — `da.var(i) + z0` прибавляет число ко
ВСЕМ коэффициентам ряда (эта ошибка ломала симплектичность на 1e-6).

`ring_matrix.radiation_integrals(ring, nodes=8)` — интегралы излучения I₁…I₅ по описанию решётки (без
трекинга): изгибы проходятся узлами Гаусса–Лежандра, β/α/η/η′ в узлах берутся из матриц, у граней
учитывается краевой член I₄ (`−Σ η·h²·tg E`). Дальше U₀, Jx/Jy/Js, τx/τy/τs, εx, σδ, αc, а при `ring.rf` —
Qs, φs, σz. Совпадает с `radiation_integrals` elegant до 1e-7 на обеих установках:
`py -3.14 ring_matrix.py radiation --lattice 2`.

Результаты и кэш — `workspace/results/verify_elegant/<опыт>/` (`--refresh` пересчитывает). SynchrotronSim
параллелится внутри C++ (OpenMP по частицам), elegant — потоками по запускам. На C++ все опыты Сибири, кроме
`rad` и `fma`, укладываются в пару минут; `rad` (ансамбль 64 × 40000 об.) и `fma` упираются в elegant
(~3.7 мс на частицу-оборот при 40 срезах). У каждого запуска elegant с ISR свой `random_number_seed`.

**Точность геометрии в БД.** Импортёр чужой решётки `s2lattice_to_db.py` пишет x/y/yaw и eff_length с
ПОЛНОЙ точностью double (12 знаков после запятой). Раньше было `%.6f` (шаг 1 мкм) и `%.5f` у длины —
от этого у Сибири была остаточная замкнутая орбита ±2,3 мкм, невязка периметра 0,585 мкм и остаток
аналитической пары νx 6,7·10⁻⁷ / β 4,9·10⁻⁶. После перезаливки: периметр сходится с .lte до 8·10⁻¹¹ м,
νx до 2·10⁻¹³, β до 1·10⁻¹¹, орбита 0,0005 мкм. ГОТЧА: C++-ядро берёт `eff_length`, `kind` и `n_slices`
ИЗ СТРОКИ `lattice_configs` (Python умеет падать на hardware_library/element_transforms, C++ — нет);
импортёр обязан их заполнять, иначе длины элементов в C++ станут нулевыми.

**ГОТЧА ОПОРНОГО ИМПУЛЬСА (найдена 2026-09-21).** elegant считает `p_central` по СВОЕЙ массе электрона
0.51099906 МэВ (старое значение), а `elegant_diag.ME_MEV` — современная 0.51099895069. Если писать
частицы по нашей массе, elegant видит их с δ = +2.1·10⁻⁷: появляется «замкнутая орбита» η(s)·δ
(0.24 мкм у Сибири — форма в точности повторяет дисперсию) и сдвиг частот ξ·δ (3.6·10⁻⁶ по νx,
2.7·10⁻⁶ по νy). Именно это годами выглядело как «предел интегратора». Теперь `elegant_me()` один раз
на процесс узнаёт массу по `pCentral` из служебного twiss, а `write_particles` получает `pc` явно.
После фикса осевая частица за оборот смещается на 0.46 нм у ОБЕИХ программ (при 160 срезах 0.0035 нм),
Δνx = 3.6·10⁻⁹. Диагностика на будущее: прогнать осевую частицу по элементам — если кик появляется
в первом же CSBEND и пропорционален ANGLE, это рассогласование импульса, а не модель изгиба. Постоянные НЕ подгоняются: `ME_MEV` остаётся современной (наше значение точнее), согласованы
только единицы передачи координат; `ME_ELEGANT_MEV = 0.51099906` рядом с ней — документированное
значение elegant, `elegant_me()` предупреждает, если измеренный `pCentral` даёт другое. Остаточный
пол: γ у программ всё равно разные, поэтому U₀ ∝ γ⁴ несёт ~4·δ₀ (измерено 4.3·10⁻⁷). В отчётах это
объясняет `verify_report.mass_section(R, head)` — в основном отчёте своя глава, в отчёте по
показателям h2 в конце главы 1; все числа берутся из summary.csv, а не зашиты.

Готчи: `twiss_output`/`matrix_output` elegant — точные матрицы, не N_SLICES (частоты отличаются от трекинга на
0.01/0.03); `higher_order_chromaticity` — только при `default_order=3`; решётку 1 заполнять
`warmstart_ring.py 1 --lte-dir workspace/lte/configuration_v1_closed`.

**Число срезов у elegant.** По умолчанию `N_SLICES=1` у `KQUAD`/`KSEXT` и 4 у `CSBEND` (`track.h`,
`track_data.c`), то есть линза проходится ОДНИМ шагом интегратора. У СИЛА линзы длинные и слабые, и это
незаметно; у Сибири (`K1` до 4.07 м⁻², набег 0.79 на линзу) один шаг ошибается на 0.7 % по силе линзы, и
трекинг elegant расходится с его же матрицами настолько, что кольцо выходит НЕУСТОЙЧИВЫМ (cos μx = 4.76).
Ставить число срезов обоим трекерам одинаково: elegant — `&alter_elements name=*, type=KQUAD, item=N_SLICES`,
SynchrotronSim — `SS_SECTOR_NSL` (до сборки кольца).

## 11. Конвенции и грабли

- **Знак изгиба:** положительный `ANGLE` из `.lte` = поворот **ВПРАВО** (yaw убывает), как в
  elegant/MAD. Отсюда `+x` смотрит **наружу** кольца. Единственный источник конвенции —
  `lte_to_lattice.step`; `design_orbit`, `s2lattice_to_db`, `lte_ring` берут её оттуда.
  Следствие: `k1=+K1`, `k2=+K2`, `k3=+K3` из `.lte` верны дословно, а `mat_B = −ANGLE/(QP·L_eff)`
  (`warmstart_ring.py:28`). Если уложить кольцо зеркально, переворот потребуется кикам ЧЁТНЫМ по x
  (диполь ∝x⁰, секступоль ∝x²), а нечётным (квадруполь ∝x¹, октуполь ∝x³) — нет.
- **Мультиполи в изгибающих элементах** берут `u = x − x_ref`, где `x_ref` — прогиб опорной дуги
  (`Magnet._ref_bow`): ящик прямой, а опорная внутри изгиба отходит от оси на сагитту `L·θ₀/8`.
  Без этого сама опорная ловит кик `k1·сагитта` (у DQ_L1000 это ~2 мм за элемент). elegant решает то
  же конструктивно: `CSBEND` — СЕКТОР, рама гнётся вместе с опорной.
- **`sp_elements.csv` — точка правки токов руками** (шаблон супериода → всё кольцо). После правки
  нужен `assemble_lattice_configs.py`.
- **Тюн не применён намеренно:** `mat_*` = проектные K из `.lte`, чтобы сверка с elegant шла на одних
  и тех же коэффициентах.
- **Легаси** (скрипты опытов, отчёты, внешние коды) — в `legacy/`, в сценарии не нужны. Токовый режим и
  матрицы связи (`coupling_matrix`, `element_coupling`) архивированы. Ядро на физкоэф. — эталонный Python
  `matrix_tracker.py` (в режиме `SS_SECTOR` = киковый, §4) + автономный C++ `MatrixTracker.exe` (§4,
  валидируется бит-в-бит против Python).
- Сборка C++ (при изменении `src/`): CMake → `build/SynchrotronTracker.exe`, `SynchrotronOptimizer.exe`.

## 12. Графическая оболочка

```powershell
gui.bat                        # или: py -3.14 gui_app.py
```

**Ярлык.** В корне проекта лежит `SynchrotronSim.lnk` — запускает оболочку через `pythonw.exe`, без
консольного окна. Ярлык хранит абсолютные пути, поэтому в git не входит; на новой машине (или после
переноса проекта) пересоздаётся:

```powershell
py -3.14 make_shortcut.py                 # ярлык в корне проекта
py -3.14 make_shortcut.py --desktop       # ещё и на рабочий стол
py -3.14 make_shortcut.py --console       # с консольным окном (видно ранние ошибки запуска)
```

Иконка рисуется в `gui/synchrotronsim.ico` (требуется Pillow; без него берётся иконка интерпретатора).
Запуск без консоли означает, что `print` не виден, поэтому ошибки старта оболочка показывает окном.

Окно на PySide6 поверх всего конвейера. **Оболочка не считает сама** — она собирает те же командные
строки, запускает их процессами и стримит вывод в общий журнал внизу окна. Поэтому результат из окна
и из консоли совпадает, а расхождение оболочки с CLI невозможно по построению. Код — в `gui/`,
точка входа `gui_app.py`.

**Проект** — связка «файл решётки `.lte` ↔ решётка и опыт в базе». Реестр проектов:
`workspace/configs/gui_projects.json` (сама база одна, конфигурации в ней сосуществуют по
`lattice_id`). При старте — окно выбора проекта либо мастер нового.

**Решётки из базы предлагаются сами.** Реестр — файл оболочки, а решётки могли быть загружены
раньше или из консоли, поэтому окно выбора показывает вторым списком «найдено в базе»: все
содержательные решётки `lattice_configs.csv` (демо-конфигурации в один элемент отбрасываются).
Источник восстанавливается из фактов, а не угадывается: суб-решётки и их названия — из
`sub_lattices.json` (наследуют `.lte` родителя), основная — из `lte_mapping.json[lattice_id]`, её
папка `.lte` — из манифеста снимка базы; сторонние плоские решётки сопоставляются плоским
конфигурациям только при однозначном соответствии. Не удалось определить `.lte` — поле пустое,
проект всё равно рабочий (путь нужен лишь для перезагрузки решётки). При открытии найденная решётка
попадает в реестр.

**Мастер нового проекта** (4 шага): файл/папка `.lte` (формат определяет `load_config`) → проверка
кольца `lte_ring.py` с возможностью записать замкнутую копию → пучок (готовая группа из базы либо
новая: 5 частиц «центр + 4 спутника» или 13 «центр + 12 по кругу», радиус, скорость, масса, заряд) →
номера решётки/опыта и `load_config.py … --force`.

| Вкладка | Что делает |
|---|---|
| **Проект и база** | сводка проекта; правка таблиц базы (`experiments`, `particle_groups`, `radiation_params`, `bpm_config`, `sp_elements`, `lattice_configs`, `hardware_library`, `design_currents`, `coupling_matrices`) с фильтром, добавлением/удалением строк и резервной копией при записи; кнопки `assemble_lattice_configs`, `warmstart_ring`, `load_config --force`, `db_snapshot save/check` |
| **Матрицы связи** | `element_compare.py matrices` / `library` (флаги отчёта, демо-конфигураций, HTML) / `library <элемент>` / `all`; **формат отчёта** DOCX/ODT/PDF с автоматической конвертацией после сборки; кнопка **проектных токов** (`design_currents.py`) с показом таблицы и предупреждением о свежести матриц; открытие отчёта |
| **Симуляция** | выбор опыта, **установки и пучка** (см. ниже) и ядра: **C++ диффур** (`track3.py --mode diff`), **C++ кик** (`MatrixTracker --track/--full`), **Python кик** (`track3.py --mode kick-phys`); обороты, режим записи (глобальные / локальные / длинный), одна частица со смещением; излучение (СИ, ISR, ВЧ, проектная энергия); остановка расчёта |
| **Визуализация** | `visualize.py` и `live_visualizer.py` отдельными окнами; **«Траектория кикового ядра → 3D»** (`matrix_traj_export.py inject`); снимок `viz_shot.py` с предпросмотром внутри окна; **два HTML-отчёта**: 3D-сцена (`viz_html.py`, лёгкая/детальная/обе) и анализ траектории (`traj_analyzer.py`) |

**Грабли оболочки:**
- **Излучение у C++ кикового ядра** задаётся не флагами, а ПРАВИЛОМ из `radiation_params.csv`
  (§4), поэтому переключатели излучения при этом ядре **правят строку опыта в этой таблице**
  (прежняя версия уходит в `workspace/tables/backups/`). У Python-кика — обычные флаги, база не
  меняется. У диффурного ядра излучения нет — переключатели гаснут.
- **ВЧ работает только в длинном режиме** (турн-by-turn у плоскости), поэтому в остальных режимах
  переключатель ВЧ недоступен.
- **Режим записи определяет, что дальше можно посмотреть:** глобальные траектории → `visualize.py`
  и HTML-сцена; локальные/длинный → `traj_analyzer.py`. Диффурное ядро пишет только глобальные,
  C++ киковое — только `.npz`. Хотите 3D-картинку от КИКОВОГО ядра (или диффурный `.bin` протух) —
  кнопка «Траектория кикового ядра → 3D» перезапишет `trajectories_exp<N>.bin` его орбитой.
- **Отчёты ложатся в РАЗНЫЕ папки:** 3D-сцена — в `workspace/results/html/`, анализ траектории — в
  `workspace/results/`. Полный путь каждого (и собран ли он, какого размера, когда) написан прямо
  под кнопками, у каждого своя кнопка «Открыть». Имя файла можно задать своё — поле «Имя файла»,
  пусто ⇒ имя по умолчанию (оно же показано подсказкой); расширение `.html` добавляется само.
- **Вид отчёта об анализе траектории выбирается САМ** — `traj_analyzer` смотрит поле `mode` в
  `.npz`: запись «локальные координаты» ⇒ подробный отчёт x(S), y(S), спектр и тюны; запись
  «длинный турн-by-turn» ⇒ x(оборот), огибающая амплитуды и фазовый портрет (тысячи оборотов,
  график прорежен). Кнопка одна; что именно получится — написано строкой под кнопками просмотра
  (там же — дата файлов, число частиц и точек).
- **Установку и пучок можно выбрать любые.** По умолчанию они подставляются из строки опыта; если
  выбрать другую пару, перед запуском выполняется `track3.py --author-only --exp N --lattice L
  --group G` — он переписывает строку опыта и пересчитывает финиш-плоскость по плоскости инжекции
  ВЫБРАННОГО пучка. Так все три ядра стартуют из одной конфигурации (автономный C++ MatrixTracker
  читает только базу, флагов установки/пучка у него нет). Оболочка предупреждает жёлтой строкой,
  какой опыт будет переписан; чтобы не трогать существующий — заведите свободный номер опыта в
  `experiments.csv`.
- **Очередь одна:** команды выполняются последовательно, кнопки на время работы гаснут — два
  трекинга одновременно испортили бы общие таблицы базы. Кнопка **«Остановить»** — в шапке журнала
  (общая для всех вкладок, активна только пока идёт задача).
- **Прерывание безопасно.** `element_compare` временно правит 4 таблицы базы (`lattice_configs`,
  `element_connectivity`, `particle_groups`, `experiments`) и возвращает их в конце. Если процесс
  УБИТЬ (кнопка «Остановить», закрытие окна), возврат не отработает, поэтому перед правкой снимается
  копия в `workspace/tables/_cmp_backup/` и ставится метка `in_progress`. Метка, пережившая процесс,
  означает прерывание: при следующем запуске инструмента таблицы возвращаются из копии
  автоматически (в журнале — строка «прошлый прогон был прерван»).
- **Консольные окна не всплывают.** Дочерние программы (`SynchrotronTracker`, `MatrixTracker`, `git`)
  запускаются с `_common.no_window()` — Windows не выдаёт им отдельного окна, при этом вывод
  по-прежнему идёт в журнал оболочки и в консоль при запуске из терминала. Новый вызов
  `subprocess` в продакшн-скрипте добавляйте с `**no_window()`.
- После правки `sp_elements.csv` оболочка напоминает про пересборку — без неё ядра прочтут прежние
  значения (§3).
