# Библиотека SynchrotronSim: модель данных и C++-движок

**Статус:** проект для обсуждения, 2026-11-24. Реализовано только то, что помечено «есть».
Старый [ARCHITECTURE.md](../ARCHITECTURE.md) в корне описывает диффур-ядро (Борис) образца весны и этим
документом не заменяется.

---

## 0. Решения в одном абзаце

1. SynchrotronSim становится пакетом `synchrotronsim` (Python) с модулем расширения `synchrotronsim._engine`
   (C++). Расширение собирается из тех же заголовков `src/matrix_core.h`, `src/matrix_ring.h`, что и сегодняшний
   `MatrixTracker`.
2. **Граница Python ↔ C++ проводится по частоте вызова.** Всё, что повторяется «на частицу × на элемент ×
   на оборот», живёт в C++. Python обращается к движку не чаще такта контура, и каждый вызов — пакет
   (N частиц × M оборотов). Внутри вызова GIL отпущен, частицы считаются параллельно (OpenMP).
3. Модель данных — четыре слоя: **Установка** (`Machine`) → **Опыт** (`Experiment`) → **Живое состояние**
   (`State`, доска) → **Прогон** (`Run`, результат с паспортом происхождения). Их сшивает **единое адресное
   пространство**: любая величина, которую можно показать, записать или подвинуть, имеет адрес.
4. На диске БД остаётся набором `;`-CSV в `workspace/tables/` (её правят руками и в Excel). Библиотека
   читает таблицы в типизированные объекты, а для блокнотов и статей умеет упаковать опыт в один
   переносимый пакет.
5. Блокнот и клиент строят **один и тот же объект `Experiment`** и запускают один и тот же стандартный цикл.
   Галочка «записывать» в справочном окне клиента и строка `exp.record.watch(...)` в блокноте — одно действие.
6. Переход постепенный. После каждого шага программа рабочая, и каждый шаг сверяется бит-в-бит с текущим кодом.

## 1. Где сейчас тратится время (замер 2026-11-24)

Решётка 26, 4882 магнита, СИ + ВЧ (фаза 165°), `nsl = 8`, машина на 16 потоков. Движок — сервер кольца
`MatrixTracker --ring-serve`, вызовы из Python через `ring_cpp.CppRing` (канал stdin/stdout).

| Операция | Время | Что это значит |
|---|---|---|
| Запуск сервера (процесс + сборка решётки) | 0,97 с | один раз на кольцо |
| `track_tbt`: 1 частица × 1 оборот | 17,9 мс | **один поток: ≈ 3,7 мкс на элемент** |
| `track_tbt`: 12 частиц × 1 оборот | 23,3 мс | 12 частиц на 16 потоках почти бесплатно |
| `track_tbt`: 48 частиц × 1 оборот | 72,4 мс | насыщение: 1,5 мс на частицу·оборот |
| `track_tbt`: 12 частиц × 15 оборотов (шаг `TbtPlant`) | 345 мс | один такт контура в кокпите |
| то же, полюса ИД `nsl = 1` (режим клиента) | 11,7 мс на оборот (12 частиц) | вдвое быстрее |
| `track_elements`: 21 частица (оптика, отклик) | 55 мс | |
| `set_kicks` (1 корректор, без перестройки) | 0,11 мс | **накладные канала + Python** |
| `apply_perturb` (RESET: перечитать CSV, собрать решётку) | 0,33 с | на каждый столбец матрицы отклика |
| Апдейт контура `IntegralSVD` (400 × 200) в numpy | 0,03 мс | |

Выводы.

- **Python сейчас не тормоз.** Команда стоит 0,1 мс, а шаг ядра — 23–345 мс; накладные ниже 0,1 %. Это
  потому, что код уже следует правилу из пункта 0.2: Python зовёт ядро пакетами.
- **Тормоз — само ядро, и это время C++.** Оборот стоит ≈ 3,7 мкс модельного времени (τ = 2655 оборотов
  = 9,8 мс). При 12 частицах в режиме клиента он считается 11,7 мс, то есть в ≈ 3200 раз медленнее реальной
  машины: 1 с жизни машины ≈ 53 мин счёта. Ускорять надо внутри C++ (раздел 4.6), и библиотека
  **не имеет права** добавить Python-цикл по оборотам.
- **Вторая статья расходов — перестройки.** Каждое `apply_perturb` перечитывает таблицы и собирает решётку
  заново: 0,33 с. На матрицу отклика в 200 столбцов это 66 с одних перестроек, хотя трекинг в ней — секунды.
- **Простаивают ядра процессора на задачах с одной частицей.** Замкнутая орбита, одиночные пробы и
  столбцы отклика идут по 1–21 частице, а параллелизм есть только по частицам: из 16 потоков работают
  несколько. Нужен второй уровень параллелизма — по копиям машины (разделы 4.4, 4.6).

## 3. Модель данных

### 3.1 Принципы

- **Типизированные объекты.** Каждая сущность — dataclass с `id` и **отпечатком** (хэш содержимого).
  Отпечаток — ключ всех кэшей (матрицы отклика, оптика) и поле паспорта прогона.
- **Статичное неизменяемо.** `Machine` и `Experiment` после сборки не меняются (`frozen`). Меняется только
  живое состояние, и только через адреса. Правка машины даёт **новую** машину или её вариант с новым
  отпечатком.
- **Таблицы по столбцам.** 5000 элементов хранятся не списком объектов, а столбцами numpy (структура
  массивов). Это быстро в Python и почти без преобразования уходит в C++.
- **Ссылки по имени, не по позиции.** Сегодня C++ читает `lattice_configs` по номеру столбца — новые столбцы
  можно добавлять только в конец. Новый загрузчик читает по заголовку.
- **Единицы.** В памяти — СИ (м, рад, Тл, с). Единица в таблице записана суффиксом имени столбца
  (`width_mm`, `loss_radius_mm`) и переводится только в слое `ss.db`. Каждый адрес несёт свою единицу
  в метаданных. Исключение по смыслу — зазор ИД `gap_mm` (так его называют на установке); он явно помечен.
- **Таблицы для людей и для машин.** Человеко-читаемые сводки — CSV с запятой и «;» (для Excel), машинные
  ряды — бинарные массивы (раздел 3.5).

### 3.2 Слой 0. Проект решётки (`LatticeDesign`), опционально

Исходник, из которого собирают установку: `.lte`, шаблон супериода (`sp_elements`), развёртка
(`lattice_layout`), `design_orbit_segments`. Сборка `assemble(design) → Machine` — это сегодняшние
`lte_to_lattice` → `assemble_lattice_configs` → `build_matrix_db` → `warmstart_ring`. Слой нужен будущему
режиму создания решётки. Остальной библиотеке он не нужен: она работает с готовой `Machine`.

### 3.3 Слой 1. Установка (`Machine`)

```
Machine                                     источник в БД
├─ id, name, design_energy, fingerprint
├─ devices: {device_type_id: DeviceType}    hardware_library + element_transforms
│    DeviceType: kind, eff_length, n_slices, stl, nominal_arg/current, windings,
│                maps[] (field_maps, fields_bin), rotation (rot_*_deg)
│    MagnetModel (ток → поле):              coupling_matrices, linear_coupling, saturation_models,
│                                            saturation_branches(+members), mec_sigma_weights, design_currents
├─ elements: ElementTable (столбцы)         lattice_configs + element_connectivity
│    instance_id, device_type, order, pose(x,y,z,yaw,pitch,roll),
│    strengths(mat_B, mat_G, mat_Gv, mat_S, mat_O), edges(e1, e2, lf1, lf2),
│    eff_length, kind, n_slices, arg_val, correct_coeff
├─ groups: [ElementGroup]                   element_groups (ИД und_NN, жёсткие группы)
├─ ring_devices:
│    cavities[]  rf_cavities      kickers[]  pulsed_kickers
│    bpms[]      bpm_config + элементы kind=monitor
│    screens[]   screens          undulators[] группы + параметры модели излучения
└─ errors: ErrorModel                       element_errors (σ по типам)
```

**Вариант машины (`MachineVariant`)** = `Machine` + разреженная дельта `(instance_id, поле, значение)`:
реализация ошибок, юстировка, ручные сдвиги. Сегодня ансамбль ошибок пишет копию `lattice_configs` в
отдельный workspace (`errors.py`), а Python подменяет из него только две таблицы из пяти. Дельта решает
обе проблемы: она маленькая, и её каналы — те же, что у живых ручек движка (раздел 4.4).

Инструментальные таблицы оптимизатора (`matrix_knobs`, `matrix_knob_members`, `matrix_tune*`,
`bench_experiments`) остаются принадлежностью своих инструментов и в ядро модели не входят.

### 3.4 Слой 2. Опыт (`Experiment`) — наш сценарий

Опыт отвечает на вопрос «что делаем с машиной». Это и есть то, что у elegant лежит в `.ele`, но у нас это
объект, а не текст.

```
Experiment                                  источник в БД (сегодня)
├─ id, name, fingerprint
├─ machine: ссылка (id + отпечаток), variant (seed ансамбля или нет)
├─ beam: Beam                               particle_groups (частицы в рамке старт-плоскости)
│        или генератор (эмиттанс, σδ, N, seed)
├─ planes: start, finish                    experiments.start_*/finish_* (пустой финиш ⇒ кольцо)
├─ physics: EngineSettings                  experiments (n_slices, loss_radius_mm, max_time_s)
│        sr, isr, rf(type, V, h, φ, f), order,  + radiation_params
│        nsl, nsl_dev, seed, точность
├─ timeline: [Event]                        kicker_timing, disturbance_spec + fb_disturbances,
│        импульсы, рампы зазоров, возмущения   fb_drives
├─ control: ControlSpec                     fb_experiments (plant, steps, stride, settle, …) + fb_loops
│        plant, loops[] (имя, сенсор, актуатор, gain, rcond, rate_hz, ref, enabled)
├─ record: [Watch]                          fb_record
│        адрес, каденс, редукция, хранение
└─ run: RunLimits                           (сейчас разбросано: max_turns, steps, max_time_s)
         max_turns | max_time, restart_after, n_restarts, stop_when(адрес, условие)
```

Пункты из твоего описания клиента ложатся сюда без новых сущностей:

| Твоё описание | Поле опыта |
|---|---|
| «ограничение времени несколькими оборотами, после которых симуляция начинается заново» | `run.max_turns`, `run.restart_after` |
| «отметить в справочных окнах, какие параметры сохранить» | `record.watch(addr, …)` |
| «в настройках записать точность счёта» | `physics` (`nsl`, `order`, `nsl_dev`, `sr/isr`) |
| «нажать рестарт, и симуляция будет записывать результаты в таблицы и видео тепловых карт» | `Simulation(exp).run()` → `Run` (раздел 3.5) |

Сегодня у опыта два пространства номеров: `experiments.exp_id` (трекинг) и `fb_experiments.fb_exp_id`
(контуры). В модели это один `Experiment` с необязательным разделом `control`. Старый `fb_exp_id` при
переходе остаётся псевдонимом.

### 3.5 Слой 3. Живое состояние (`State`, доска) — есть

Это `control/state.py:ExperimentState`, его не надо придумывать заново. Регионы: `config`, `actual`,
`dynamics`, `limits`, `target_slots`, `observables`, `refs`, `sensors`, `noise`, `undulators`, `beam`,
`machine`, `optics`, `history`, `t`. Контур читает через `StateView` и пишет только свой слот.

Меняется одно: **каждая величина доски получает адрес** (раздел 3.7), и адресный реестр знает, где она
физически живёт: в Python-доске или в буфере C++-движка. Поэтому запись не таскает массивы через Python,
если её можно редуцировать внутри движка.

### 3.6 Слой 4. Прогон (`Run`) — результат с паспортом

```
workspace/runs/<run_id>/
├─ manifest.json   паспорт: ПОЛНАЯ копия Experiment (не ссылка), отпечаток Machine,
│                  git sha + признак незакоммиченных правок, сборка движка (версия, компилятор, флаги),
│                  seed, машина, время начала/конца, статус (in_progress | done | stopped | failed)
├─ signals.npz     временные ряды по адресам: для каждого Watch — t, step, value
├─ tables/         человеко-читаемые сводки (CSV с запятой и «;»)
├─ artifacts/      PNG/SVG/HTML, видео тепловых карт, спектры
└─ log.txt
```

В БД — индекс `runs.csv` (`run_id; exp_id; status; started; finished; path; note`). Он заменяет длинную
таблицу `fb_results` (`fb_exp_id; signal; step; value`, уже 1364 строки на 6 опытов): она плохо растёт и не
хранит, на каком коде и какой сборке ядра получено число. На время перехода `fb_results` пишется параллельно.

Формат рядов — `npz` + `manifest.json`: numpy понимает его без зависимостей, C++ уже пишет npz
(`src/matrix_npz.h`), в Colab он открывается сразу. HDF5 и Parquet — экспорт по запросу, не основной формат.

**Пакет опыта для блокнотов и статей:** `bundle.zip` = `manifest.json` + строки таблиц только этой машины
и этого опыта + (только для диффур-ядра) карты поля по хэшу. В Colab: `ss.load_bundle(path_or_url)`.
Блокнот + пакет = расчёт, который читатель статьи перепроверит одной кнопкой.

### 3.7 Адресное пространство

Сейчас адресных схем три:
- адреса клиента (`client/addresses.py`: `obs.`, `drive.`, `undulator.`, `optics.`, `element.`, `loop.`,
  `meta.`, `screen.`, `diag.`);
- имена сигналов рекордеров (`control/recorders.py`: `orbit_rms`, `rf`, `light`, `bpm`, `phase`, `screen`,
  `tune`/`chroma`/`adts`);
- id актуаторов в `Schema` (`corr.000.hkick`, `quad.<fam>.dk`, `sext.<fam>.dk2`, `oct.<fam>.dk3`, `rf.freq`).

Предлагается одна грамматика (база — схема клиента, она стабильнее всех):

```
<область>.<объект>[.<атрибут>][@<место>][:<редукция>]
```

| Область | Пример | Что |
|---|---|---|
| `element` | `element.SP03.COR05.k1` | магнит: поза, силы (статика + живое) |
| `act` | `act.corr.000.hkick`, `act.quad.QF1A.dk` | актуатор (что пишет контур); свойства привода: `act.corr.000.hkick.slew` |
| `obs` | `obs.ebpm.x:rms`, `obs.tune.x` | наблюдаемая (выход Observer) |
| `beam` | `beam.centroid.x@BPM_012`, `beam.sigma.x` | пучок в точке наблюдения (считает движок) |
| `optics` | `optics.nux`, `optics.beta_x@QF1A_03` | линейная оптика |
| `undulator` | `undulator.und_01.gap` | ИД |
| `screen` | `screen.SCR_U01.power`, `screen.SCR_DP12.flux` | экран (дорогой: считается по запросу) |
| `rf` | `rf.freq`, `rf.volt` | ВЧ |
| `loop` | `loop.fofb_x.enabled`, `loop.fofb_x.gain` | контур |
| `meta` | `meta.model_time`, `meta.turn` | прогон |
| `diag` | `diag.orbit_modes` | стандартный график |

У каждого адреса — метаданные (`AddrMeta` расширяется): имя, единица, тип и форма, **можно ли писать**,
естественная частота обновления, **владелец** (доска Python / буфер движка / вычисляемое по запросу),
**цена** (дешёвый / дорогой). Для старых имён — таблица псевдонимов, чтобы сохранённые раскладки окон
(`workspace/layouts/…`) и `fb_record` продолжали работать.

**`Watch`** = (адрес, каденс, редукция, хранение). Один и тот же объект создаёт и блокнот
(`exp.record.watch(...)`), и галочка «записывать» в клиенте. Рекордеры становятся реализациями `Watch` для
дорогих адресов (экран, спектр), а простые адреса записываются общим механизмом.

## 4. C++-движок

### 4.1 Что есть

- **Ядро физики** `src/matrix_core.h`: `State{x, px, y, py, t, δ}`, Йошида 2/4/6, `Element` с телами
  `body_sector` (CSBEND-подобный симплектический сектор с классическим СИ/ISR), `body_kick`
  (KQUAD/KSEXT/KOCT), `body_kicker`.
- **Кольцо** `src/matrix_ring.h`: чтение CSV, `buildLine`, рамки, `modified_drift`, плоскости
  инжекции, ВЧ (`RfSpec` none/ideal/sine), импульсные кикеры (`KickerPulse`, `KickClock`), циклы оборота.
- **Сервер** `src/matrix_ring_serve.h`: двоичный протокол stdin/stdout (`TRACK`, `TBT`, `ELEM`, `PIECES`,
  `JUNCTION`, `KICK|VKICK|YAW|DK|DKV|DSK|DK2|DK3|BSCALE`, `RF`, `RESET`). Возмущения меняют элементы на
  месте и пересчитывают кэш; `RESET` перечитывает таблицы.
- Весь код заголовочный, в пространстве имён `mc`, **без глобального состояния**. Поэтому его можно
  обернуть в расширение почти без переписывания.
- OpenMP по частицам в `TRACK/TBT/ELEM/PIECES`, у каждой частицы свой ГСЧ ISR (splitmix по seed):
  результат не зависит от числа потоков.
- Python-эталон `matrix_tracker.py`; сверка C++ ↔ Python бит-в-бит.
- Связки pybind11, ctypes или Cython в проекте **нет**: Python общается с C++ только через процессы.
- **В C++ нет замкнутой орбиты, Твисса и нормальных форм.** Всё это Python поверх `track`/`track_elements`
  (`ring_analysis`, `ring_map`).

### 4.2 Решение: расширение `_engine` и сервер как второй бэкенд

```
           ss.engine.Ring  (Python-протокол EngineBackend)
              ├── InProc:  _engine.Ring   — расширение CPython (по умолчанию)
              └── Pipe:    сервер --ring-serve + CppRing   — изоляция, старые скрипты, сверки
                     обе реализации собраны из одних заголовков src/matrix_*.h
```

Что даёт расширение (честно: не скорость трекинга — канал стоит 0,1 мс):
- **живые ручки без RESET** — все поля элемента меняются на месте (раздел 4.4): минус 0,33 с на столбец отклика;
- **одна модель геометрии.** Сегодня `CppRing.mags/.plane` строят ПАРАЛЛЕЛЬНУЮ Python-решётку через
  `matrix_tracker.build_line`, а сторож (`ring_cpp.py:266`) проверяет, не разошлись ли две модели.
  Расширение отдаёт геометрию из самого движка, и вторая модель уходит;
- **несколько машин в одном процессе** на общем пуле потоков: ансамбли ошибок, столбцы отклика параллельно;
- **без копий** — numpy-массивы передаются в C++ и обратно по указателю;
- **установка в Colab** одной командой `pip install` (бинарник-сервер в колесо упаковывать неудобно).

Сервер остаётся: процесс-изолятор нужен, когда ядро может упасть (клиент и блокнот не падают вместе с ним),
и для сверок с elegant. Python-эталон остаётся эталоном. Тесты сверяют три реализации: эталон ↔
расширение ↔ сервер.

### 4.3 Скомпилированная машина

```python
ring = ss.engine.compile(machine_or_variant, physics)   # → _engine.Ring
ring.fingerprint                                          # хэш(машина + настройки): ключ кэшей
ring.elements                                             # numpy-структура ТОЛЬКО ДЛЯ ЧТЕНИЯ, из движка:
                                                          #   s, entry/exit, рамки, kind, силы, срезы
```

- C++ `buildLine` получает **массивы** (структуру столбцов `ElementTable`), а не путь к CSV. Чтение CSV
  остаётся одним из поставщиков массивов — для CLI и сервера.
- Компиляция делается один раз: склейка совмещённых строк, рамки, `modified_drift`, срезы.
- Узлы (`Node`) — в непрерывном массиве; горячие поля каждого вида тела — отдельными столбцами
  (подготовка к векторизации, раздел 4.6).

### 4.4 Живые ручки без перестройки

```python
k = ring.knob("dk1", element_ids)       # дескриптор разрешается один раз
k.set(values)                           # векторно, на месте, кэш только у затронутых; срезы диполей — лениво
snap = ring.snapshot(); ...; ring.restore(snap)   # дешёвый откат сил (столбец отклика: возмущение → трекинг → откат)
r2 = ring.clone()                       # копия для параллельной работы
```

- Каналы: `hkick, vkick, dk1, dk1v, dks, dk2, dk3, bscale` (есть в сервере), плюс **поза** `dx, dy, dz,
  yaw, pitch, roll` — сейчас для этого нужна копия БД через `errors.py`; плюс `rf.volt/phase/freq`.
- Адрес `element.QF1A_03.k1` или `act.quad.QF1A.dk` переводится в дескриптор ручки один раз, при подписке.
- Ручки — единственный путь, которым живое состояние доски попадает в движок. `Arbiter.combine` →
  `Limits.apply` → `knob.set`.

### 4.5 Пакетные вызовы, мониторы, время внутри движка

```python
out = ring.track(states, turns=15, monitors=mon, reduce="centroid")   # GIL отпущен, OpenMP по частицам
```

- **Мониторы** — точки наблюдения (BPM, источники экранов, плоскости) с каденсом. Движок пишет в заранее
  выделенный numpy-буфер и, если адресу нужна только редукция (центроид, σ), сворачивает прямо в C++:
  через границу не идут все частицы.
- **Python вызывается на шаг контура, а не на оборот.** В кокпите шаг сейчас = 15 оборотов. Контуру FOFB
  10 кГц хватает шага ≈ 27 оборотов, так что Python-контуры успевают вплоть до десятков килогерц
  модельного времени.
- **Расписание событий исполняет движок.** Импульсы кикеров (`KickClock` уже в C++), рампы зазоров,
  ВЧ-рампы, гармоники возмущений — кусочно-заданные расписания по оборотам. Python задаёт их один раз
  и не трогает каждый оборот.
- **Контуры на C++ — запасной вариант.** Если понадобится обратная связь чаще шага, у движка будет
  минимальный интерфейс контура (матрица × вектор на оборот). Контур на Python остаётся основным.

### 4.6 Ускорение самого ядра

Здесь живёт время: 3,7 мкс на элемент на один поток. Рычаги перечислены в порядке ожидаемой отдачи;
каждый проверяется сверкой с эталоном или тестом сходимости. Физика не меняется, клампов и порогов нет.

1. **Параллелизм по копиям машины.** Одночастичные задачи (замкнутая орбита, столбцы отклика, сканы)
   раскладываются по `clone()` на все 16 потоков. Сейчас на одной частице заняты единицы потоков.
2. **Тяжёлая аналитика — в C++.** Ньютон замкнутой орбиты и матрица оборота сейчас ходят в ядро десятки раз
   с Python-обвязкой. В C++ они параллелятся и не перестраивают решётку. Туда же — матрицы отклика
   (столбцы параллельно по клонам) и диффузия ISR.
3. **Векторизация по частицам** (столбцы частиц, AVX2: 4 частицы за инструкцию). Тела одинаковы для всех
   частиц пучка, данные в кэше одни.
4. **Слияние элементов без изменения физики.** Подряд идущие дрейфы, повторяющиеся одинаковые срезы.
5. **Число срезов по сходимости.** `nsl_dev` уже есть. Нужен инструмент, который для каждого типа
   устройства подбирает срезы по тесту сходимости, а не на глаз (паспорт 26-й требует `nsl = 40`, клиент
   живёт на 5–8).
6. **Тепловые карты (`undulators/sr_trace.py`).** Интеграл Льенара «пиксели × точки траектории» сейчас
   идёт в numpy + потоки — прямой кандидат на C++/OpenMP.
7. GPU — не сейчас; столбцовая раскладка его не исключает.

**Бит-в-бит.** Векторизация и слитое умножение-сложение (FMA) меняют последние биты. Поэтому две сборки:
- **эталонная** (скалярная, `-ffp-contract=off`) — бит-в-бит с Python-эталоном и сервером, на ней все сверки;
- **быстрая** — сверяется с эталонной с допуском ~1e-12 (относительно).

- `pyproject.toml` + **scikit-build-core** + существующий `CMakeLists.txt`; связка — **nanobind**

- **Linux / Colab (после открытия кода).** Колёса manylinux через cibuildwheel (GitHub Actions); в Colab `pip install …`.
  Ядро заголовочное, так что сборка из исходников в Colab тоже возможна (минуты). OpenMP — libgomp.

## 7. Несостыковки, которые модель данных обязана закрыть

Найдены при инвентаризации, все проверяемы в коде.

1. **C++ читает `lattice_configs` по номеру столбца** (`src/main.cpp`) — новые столбцы только в конец.
   → чтение по заголовку.
2. **Порядок элементов берётся только из `instance_id`.** `prev_instance_id`/`next_instance_id` в
   `element_connectivity` не используются нигде, хотя `TECHNICAL_SPEC.md` называет связность «источником
   правды». → явный столбец порядка `order` (или реальное использование связности) — решить.
3. **Строки с совпадающими x, y, z молча складываются в один магнит** (`matrix_tracker.py:339`). Так задаются
   обмотки одного магнита. → сделать явным: обмотки — записи одного элемента.
4. **Подмена ws неполная.** Python берёт из возмущённого workspace только `lattice_configs` и связность;
   пучок, резонаторы и кикеры читает из основной БД. C++ подменяет всё. → вариант машины как дельта (3.3).
5. **Пути к таблицам** частью от текущей папки (`mt.TB`), частью от корня. Скрипт, запущенный не из корня,
   читает не то. → `ss.db.Repository(root)`.
6. **Два пространства номеров опыта** (`exp_id` и `fb_exp_id`). → один `Experiment` (3.4).
7. **Три адресные схемы** (клиент, рекордеры, `Schema`). → одна грамматика + псевдонимы (3.7).
8. ~~**Параллельная Python-модель геометрии внутри `CppRing`** со сторожем расхождения.~~ → геометрия из движка
   (4.2). **Закрыто шагом 3.**
9. **Результаты без паспорта происхождения** (код, сборка ядра) и в длинной таблице. → `Run` (3.6).
10. **`loss_radius_m` читается, но не используется**: апертур в ядре нет, частица теряется только при
    p⊥ > p или нечисловом состоянии. → поле апертуры в `Machine`/`Physics` есть, физика — отдельной задачей.
11. **Паспорт установки (энергия, ВЧ, суперпериоды) — в коде** (`synchrotronsim/machines.py`, бывший
    `facility_report.LATTICE_INFO`), а не в БД; у решётки 27 его нет. → таблица установок в БД.
12. **`TECHNICAL_SPEC.md` устарел** в части ядер: пишет, что C++ матричное ядро архивировано, а рабочее
    ядро сейчас именно `MatrixTracker`. → обновить вместе с шагом 2.

  с 53-битной (0x027F). В ядре `pow` с дробной степенью был только в ISR, и ISR расходился на ~1e-11. Дробные
  степени заменены на выражения через `sqrt` (точное округление IEEE на SSE): теперь ISR совпадает бит-в-бит,
  а у сервера ISR сдвинулся на уровне последнего бита (статистически ничего не меняется; детерминированная
  физика не тронута). Правило для ядра: `std::pow` с дробной степенью не использовать.
- **Скорость.** Трекинг тот же, что у сервера (12 частиц × 15 оборотов: 0,335 с против 0,339 с) — как и

### 8.7 Шаг 6, часть 1 (2026-11-25): замкнутая орбита и отклик

- **Замер.** Столбец отклика (реш. 26, nsl 8) — 159 мс (4D) / 232 мс (6D, СИ+ВЧ), из них ~90 % — замкнутая

  собственного шума. `floor=0` — прежнее поведение бит-в-бит.

  возмущений), `set_threads(n)` (C++ `RingModel::threads`, клауза `num_threads`; сохраняется через RESET и

  новая сборка — в фоне; окна-подписчики, их подписки, отметки «● запись», настройки записи, зазоры ондуляторов,
  настройки экранов и режим пуск/пауза переносятся, сцена перерисовывается по новой геометрии. Сохраняемый опыт —
  с ЖИВЫМИ флагами контуров, отмеченными величинами и лимитом (`Cockpit.current_experiment`). Замер на реш. 26:
  первая сборка ~50 с (с откликом), пересборка ~19 с.
- **Таблицы — через `Repository`.** Сцена (`scene3d._read_screens`, справочник устройств для STL) и список
  экранов кокпита читают БД через `synchrotronsim.db`, а не открывают CSV сами (сверено: то же содержимое).
- **Физический перенос `control/` и `client/` в пакет — на шаге 7**, не сейчас. Причина: 34 модуля этих папок
  вычисляют пути к `workspace/` (кэш откликов `CACHE_DIR`, раскладки окон, таблицы, `undulators/`) от
  СОБСТВЕННОГО расположения файла (`dirname(__file__)/..`). Перенос на уровень глубже без правки молча увёл бы
  кэши (пересчёт откликов и нормальной формы — минуты на решётку) и раскладки в `synchrotronsim/workspace`.
  Правильно — один источник корня проекта/рабочей папки (`synchrotronsim.db.PROJECT_ROOT`, `Repository.workspace`,
  с переопределением — это же нужно для установки не в режиме `-e` и для запуска из пакета опыта), и это работа
  шага 7 вместе с `pyproject`. Сам перенос в поведении ничего не меняет: `control` импортируют только 4 скрипта
  корня, оболочка `gui/` и тесты; 26 модулей `control/` — запускаемые скрипты (`py -3.14 control/mode4_run.py`),
  их команды поменяются один раз — тогда же. Pickle-кэши содержат только массивы numpy (проверено по всем 79
  файлам) — от переноса не зависят.
- **Осталось:** запуск модели прямо из распакованного пакета (plant'ам нужен путь к рабочей папке); запись экранов
  (видео тепловых карт) и спектров; экраны в сцене пока не фильтруются по решётке (как и раньше — по
  ондулятору-источнику).
