# Протокол данных SynchrotronSim: хранилище, вычислитель, сеть, правка проекта

Статус: **принят 2026-11-25**, реализация — по этапам раздела 10; **этапы 1–3 выполнены 2026-11-25**. Связан с `docs/LIBRARY_ARCHITECTURE.md`
(модель данных Machine → Experiment → Run, адреса, `Watch`, `Run`).

## 1. Решения

1. **Библиотека говорит с БД только документами.** Сохранить — передать документ (машину, опыт, результат);
   получить — назвать вид, id и ревизию и получить документ. Ни один модуль счёта не открывает таблицы сам.
2. **Источник правды — хранилище с ревизиями** (вариант A, решение пользователя 2026-11-25). CSV — формат
   обмена: выгрузил, поправил в Excel, загрузил → новая ревизия с показом разницы.
3. **Три вида документов и справочник:** машина @ ревизия → опыт @ ревизия (ссылается на машину с ревизией)
   → прогон (ссылается на оба). Справочник устройств (типы, карты, калибровки) — общий для проекта.
4. **Хранилище, вычислитель и клиент могут быть на разных компьютерах локальной сети.** Где что работает —
   задаёт объект связи `Site`; по умолчанию всё в одном процессе, как сейчас.
5. **Вычислителю передаётся ссылка, а не данные.** Данные целиком — только если их нет в хранилище
   (черновик, работа без сети).
6. **Правка проекта — журнал правок на языке адресов.** Один формат для живой правки из клиента, сохранения,
   отмены, паспорта прогона и будущего редактора решётки.

## 3. Понятия

| Понятие | Что это | Пример |
|---|---|---|
| проект | пространство имён: справочник устройств + машины + опыты + прогоны | «СИЛА» |
| машина | конфигурация установки: решётка, устройства на кольце, паспорт | `26` («СИЛА-26») |
| справочник устройств | типы устройств, STL, карты поля, калибровки ток → поле | `DP_L_PM_L418` |
| опыт | постановка: модель, контуры, возмущения, подписка, лимиты + ссылка на машину | `fb_exp_3`, `cockpit` |
| прогон | результат исполнения опыта: паспорт, ряды, артефакты | `20261125-…-simulation-7d46` |
| ревизия | неизменяемая версия документа; новая — поверх родительской | `26@r14` |
| ссылка | вид + id + ревизия (или «последняя») | `Ref("machine", "26", "r14")` |
| журнал правок | список правок «адрес, было, стало» поверх ревизии | `[set element.QF1A.k1 …]` |
| черновик | ревизия + несохранённый журнал | правка из кокпита до «Сохранить» |

Машина в документе **самодостаточна для кикового ядра**: в ней лежат использованные типы устройств (как
сейчас `Machine.devices`). Карты поля и STL — по ссылке на блоб (хеш содержимого), не внутри документа.

## 4. Документы и форматы

- **Конверт** — JSON: `format` (`synchrotronsim.machine/1`, `…experiment/1`, `…run/1`), `id`, `rev`,
  `parent`, `fingerprint`, `created`, `author`, `note`, затем содержимое.
- **Числовые столбцы** (таблицы машины, ряды прогона) — бинарными массивами рядом с конвертом (npz; формат
  обмена можно сменить без смены протокола). Упаковка — zip: `document.json` + `arrays.npz` (без pickle).
  Документ решётки 26 — 0,23 МБ (запись 0,07 с, чтение 0,14 с).
- **Идентичность** — отпечаток содержимого (sha256, как `Machine.fingerprint`); номер ревизии `rN` — для
  людей. Одинаковое содержимое ⇒ одинаковый отпечаток ⇒ кэш по нему корректен на любом компьютере.
- **Версия формата** в каждом документе; читатель отказывает с понятной ошибкой на незнакомую старшую версию.
- **Единицы** — СИ, как в `synchrotronsim.model` (перевод из `_mm`, `_mrad`, `_deg`, `_pct` — только на
  импорте/экспорте CSV).
- **Паспорт машины** (энергия, ВЧ, суперпериоды — сейчас `synchrotronsim/machines.py`) переезжает в документ
  машины.

## 5. Протокол хранилища

Операции одинаковы для любого транспорта (локальные вызовы, HTTP):

| Операция | Что делает | Ошибки |
|---|---|---|
| `get(вид, id, rev=None)` | документ; без rev — последняя ревизия | нет документа; неизвестная версия формата |
| `list(вид, фильтр)` | id, ревизии, подписи, даты | — |
| `history(вид, id)` | цепочка ревизий с авторами и заметками | — |
| `commit(вид, id, parent, документ \| журнал, note)` | новая ревизия поверх `parent` | **конфликт**: последняя ревизия ≠ `parent` |
| `blob_put(байты)` / `blob_get(хеш)` | крупные файлы по хешу (карты, STL, ряды, артефакты) | — |
| `run_create / run_append / run_finish / run_query` | прогоны: только дописываются | — |
| `watch(вид, id)` | уведомления о новых ревизиях (несколько клиентов) | — |

- Ревизии **не удаляются и не переписываются**. Конфликт не перезаписывается молча: клиент переносит свой
  журнал на новую ревизию (правки по разным адресам — автоматически, по одним и тем же — с вопросом).
- Прогон ссылается на опыт и машину **с ревизиями**; прогон на черновике — на ревизию + хеш журнала (журнал
  кладётся в прогон).
- Хранилище за протоколом: этап 1 — поверх нынешних CSV (`LocalCsvStore`), этап 2 — SQLite с ревизиями
  (одним файлом; по нашим объёмам хватит и на сервере); PostgreSQL — если появится много одновременных пишущих.

## 6. Протокол вычислителя

| Операция | Что делает |
|---|---|
| `open(опыт \| ссылка, store=…)` | сессия: вычислитель сам берёт машину и опыт из хранилища по ссылке, кэширует по ревизии |
| `run(steps) / step / stop / restart` | исполнение (пакетное и живое — один исполнитель `Runner`) |
| `apply(журнал)` | живые правки (раздел 8) |
| `subscribe / unsubscribe / watch / unwatch / record / command / control` | то, что сейчас идёт через `Link` |
| `close` | закрыть сессию |

- Прогоны пишет **вычислитель прямо в хранилище**; клиент получает id прогона. Живой кокпит получает поток
  снимков; запись идёт на стороне вычислителя.
- Нынешний `InProcLink` — локальная реализация этого протокола; сетевой `Link` — та же сигнатура поверх
  постоянного соединения.

## 7. Где что работает: объект связи `Site`

```python
from synchrotronsim import Site
lab = Site.load("lab")             # профиль: адрес хранилища, адрес вычислителя
print(lab.check())                 # отчёт: связь, задержка, версии протокола и формата, сборка ядра
exp = lab.store.get("experiment", "fofb_demo")
run = Simulation(exp, on=lab.compute).run()
```

- **`Site.local()` по умолчанию:** всё в одном процессе, прямые вызовы без сериализации — нынешний код и
  скорость не меняются. Флаги в коде: `open_store(site=…)`, `Simulation(exp, on=…)`, `launch_cockpit(…, site=…)`.
- **Транспорт подменяемый:** хранилище — HTTP (просто, отлаживается браузером, проходит сети); вычислитель —
  постоянное соединение (живому кокпиту нужен поток снимков). Конкретные библиотеки — на этапе 3 (их установка —
  с разрешения пользователя).
- **Профили** — файл настроек (`workspace/configs/sites.json` или в домашней папке); копию профиля можно
  сохранить в хранилище. **Пароли и токены — только локально**, в хранилище не кладутся. Сеть — локальная, наружу
  не публикуется; доступ — по токену площадки.
- **`check()` сверяет:** доступность и задержку, версию протокола, версию схемы хранилища, сборку ядра на
  вычислителе (компилятор, флаги, коммит), число ядер, свободное место. Сервер, скорее всего, на Linux с другим
  компилятором — **бит-в-бит с Windows-сборкой не гарантирован** (уже видели на x87). Поэтому паспорт прогона
  пишет, где и какой сборкой считалось; сверки между разными сборками — с допуском, на одной сборке — бит-в-бит.

## 8. Правка проекта из клиента (заложить сейчас, делать на этапе 4)

- **Правка** = `(op, адрес, было, стало)`: `set element.SP01.QF1A.k1 1.20 → 1.23`; позже структурные —
  `insert` / `delete` / `move` элемента, `replace_device`. Язык адресов — тот же, что у подписок
  (`synchrotronsim/addresses.py`).
- **Один журнал правок:** (1) уходит в сессию вычислителя и применяется сразу; (2) «Сохранить» = `commit`
  журнала → новая ревизия машины; (3) отмена/повтор; (4) паспорт: прогон на черновике хранит «ревизия +
  журнал» — воспроизводим, даже если правку не сохранили.
- **Цена правки** (поле `cost` в реестре адресов): горячая — сила/сдвиг существующего элемента, ручка ядра,
  мгновенно; тёплая — длина, срезы, вставка элемента, пересборка линии из массивов (~0,5 с) с сохранением пучка;
  холодная — то, от чего зависят матрицы отклика: кэш сбрасывается по отпечатку (уже работает), пересчёт.
- **Два рода адресов:** параметры проекта (проектная сила, положение, длина — сохраняются в машину) и живое
  состояние (ток сейчас, зазор сейчас, усиление контура — в опыт или никуда). Реестр адресов получит пометку
  «параметр проекта / живое состояние». Сейчас кокпит меняет только живое состояние.
- **Редактор решётки** — тот же механизм с перевесом структурных правок; документ машины и журнал — его модель.

## 10. Этапы

**Этап 1 — протокол хранилища и счёт только из документов** (без сети).

1. Документ машины: `Machine` ↔ конверт + столбцы; круг «машина → документ → машина» сохраняет отпечаток, ядро
   по восстановленной машине — бит-в-бит. Паспорт — в документ.
2. Интерфейс `Store` + `LocalCsvStore`: машины — из нынешних CSV (ревизия = отпечаток); при каждом прогоне
   документ машины сохраняется снимком в хранилище (`workspace/store/…`) — прогоны воспроизводимы уже здесь;
   опыты — из fb_* и JSON-файлов; прогоны — нынешние `workspace/runs` + индекс.
3. `Experiment.machine = Ref(…)` с ревизией (`lattice_id` — псевдоним «последней»); `Simulation` и кокпит берут
   машину через хранилище по ссылке; в паспорте прогона — ссылка с ревизией.
4. Путь счёта — только из документов: места из таблицы раздела 2.
5. **Критерий:** тест «модель считает, не открыв ни одной таблицы» — перехват `open` на время `Simulation` и
   шагов кокпита с экранами; разрешены только кэши вычислителя.
6. Пакет опыта (`save_bundle/load_bundle`) — документ опыта + документ машины: запуск без БД.

Исследовательские скрипты корня могут читать CSV по-старому до этапа 2.

  размером 60×60 мм. Теперь экраны берутся только из своей машины: у 26 все называются `SCR_und_NN`, размер по
  умолчанию 50×50 мм, 20 м (у `und_01` карта та же, у `und_19` экран теперь 50 мм вместо 60). Нужны свои экраны
  у 26 — строки решётки 26 в таблице `screens`.
- Перевод мм → м → мм у размеров экранов точен для значений из таблицы (50, 60, 80, 30, 100 мм); у
  произвольной десятичной доли миллиметра возможна разница в последнем бите.

**Этап 2 — хранилище с ревизиями** (SQLite): импорт нынешних таблиц как первых ревизий, экспорт/импорт CSV
для Excel (десятичная запятая и «;» для человекочитаемых), показ разницы ревизий, история; инструменты-миграции
(`insert_undulators`, `apply_*`) пишут ревизиями вместо правки CSV.

**Итог этапа 2 (2026-11-25):**
- **Что хранит ревизия машины.** Не документ `Machine`, а **срез её таблиц** (`synchrotronsim/tableset.py`):
  строки её решётки в `lattice_configs`, `element_connectivity`, `element_groups`, `rf_cavities`,
  `pulsed_kickers`, `bpm_config`, `screens` — ячейки как текст, без потерь (пусто и «-», единицы таблиц, столбцы
  вне модели), + паспорт (из `machines.py` на момент фиксации) + ссылка на ревизию справочника устройств
  (`hardware_library`, `element_transforms`, `field_maps` — отдельный документ `library`). Причина: `Machine` —
  разобранный вид (NaN вместо пустой ячейки и «-», СИ вместо мм/мрад), по нему таблицы точно не восстановить, и
  «выгрузил → поправил → загрузил» давал бы ложные правки. Документ `Machine` для счёта строится из среза тем же
  разбором, что из CSV (`MemoryRepository`): на всех 21 решётке отпечаток совпадает.
- **Хранилище** `synchrotronsim/store_sqlite.py` (`SqliteStore`), файл `workspace/store/store.sqlite` (в git не
  хранится): ревизии (машины, справочник, опыты, документы машин из пакетов), указатели последних ревизий, блобы
  (сжатые). Ревизия = sha256 содержимого; `commit` в транзакции с проверкой родителя (`ConflictError`);
  `revision()` находит ревизию по номеру, его префиксу или отпечатку `Machine`. `open_store()` выбирает его сам,
  если файл есть (иначе — хранилище этапа 1).
- **Рабочая копия** (как в git) — `workspace/tables`. `working.json` помнит, с какой ревизии выгружена каждая
  машина: `status` (без изменений / изменена / новая / отстала / нет в таблицах), `diff` по ячейкам, `commit`
  (родитель — базовая ревизия: если кто-то зафиксировал после выгрузки — конфликт), `checkout` (изменённую
  рабочую копию не затирает без `force`; выгрузка ревизии воспроизводит файлы байт-в-байт). **Модель на этом
  компьютере считает рабочую копию** (`get("machine", id)` без ревизии) — скрипты, Excel и модель видят одно и
  то же; прогон на незафиксированной копии фиксирует её **черновой ревизией** (указатель последней не
  двигается), при `commit` черновик становится ревизией. Без рабочей копии (будущий сервер хранилища)
  `get` без ревизии — последняя зафиксированная.
- **Excel** (`ss_store.py export|import`): выгрузка среза — числа с десятичной запятой, «;», UTF-8 с BOM, рядом
  `.base.json` (срез-база) и `export.json`. Загрузка сравнивает с базой по ячейкам: ячейка, совпавшая с базой на
  15 значащих цифрах (точность Excel; «001» = «1», «1,00E-05» = «1e-05»), правкой не считается. Правки
  накладываются на текущую рабочую копию: независимые правки не теряются, одна ячейка, изменённая с двух сторон, —
  конфликт (ничего не пишется; `--partial` — бесконфликтные). Столбцы в выгрузке не правятся (заголовок сверяется).
  Excel может переделать текст (например, «1-2» в дату) — такая ячейка видна в разнице при загрузке.
- **Команды** `ss_store.py`: `init`, `status`, `diff`, `commit`, `log`, `checkout`, `export`, `import`. Проект
  импортирован: 22 ревизии (справочник + 21 решётка), 0,66 МБ.
- **Миграции** (`insert_undulators`, `apply_*`, …) по-прежнему правят рабочую копию; правка становится ревизией по
  `ss_store.py commit -m …` (с показом разницы).
- **Ограничения этапа:** правка справочника устройств даёт новые ревизии всех машин (ревизия машины включает
  ссылку на справочник); опыты из таблиц fb_* в хранилище не импортированы (читаются из рабочей копии как
  `fb:N`); калибровки ток → поле, `experiments`, `element_errors` пока вне ревизий.

**Этап 3 — сеть:** сервер хранилища, сервер вычислителя, `Site` + `check()`, сетевой `Link` для кокпита,
сборка ядра на сервере.

**Итог этапа 3 (2026-11-25):** только стандартная библиотека Python (`http.server`, `socketserver`, `urllib`) —
на серверах ничего доустанавливать не нужно, кроме Python, пакета и собранного ядра.
- **Формат** `synchrotronsim/wire.py`: JSON-заголовок + бинарные вложения (массивы numpy, байты), метки для
  кортежей, NaN/±inf, нестроковых ключей; без pickle. Поток — кадры «8 байт длины + сообщение».
- **Слои хранилища.** `synchrotronsim/working.py` (`WorkingCopyStore`) — вся логика ревизий и рабочей копии
  поверх 14 простых операций (head, revision, history, list, содержимое справочника/машины/опыта, запись с
  родителем, поиск по отпечатку, блобы, прогоны); их реализуют `SqliteStore` (файл) и `RemoteStore` (сеть)
  одинаково. Поэтому `ss_store.py --site lab status|diff|commit|checkout|export|import` работает против сервера
  с рабочей копией этого компьютера (база — `workspace/store/working-<площадка>.json`). Рабочая копия, совпавшая с
  последней ревизией, при `status` запоминает её базой; правка без базы — конфликт с подсказкой.
- **Сервер хранилища** `synchrotronsim/remote.py` (`StoreServer`, `ss_server.py store`): HTTP, `GET /v1/ping` (без
  токена), `POST /v1/rpc` — простые операции; токен в заголовке `Authorization: Bearer`, сравнение
  `hmac.compare_digest`; без токена слушает только 127.0.0.1. Машина 26 по сети — 0,5 с (срез + справочник,
  сборка `Machine` у клиента; содержимое ревизий кэшируется клиентом).
- **Площадка** `synchrotronsim/site.py` (`Site`, `ss_server.py site add|list|check|remove|publish`): профили —
  `~/.synchrotronsim/sites.json`, токены — `~/.synchrotronsim/credentials.json` или `SS_TOKEN_<ИМЯ>`; профиль (без
  токена) можно положить в хранилище (`publish`, документ вида `site`). `check()`: доступность, задержка (медиана),
  протокол, доступ по токену, сервер (ОС, Python, ядра), хранилище, код на сервере (коммит, есть ли
  незафиксированные правки), **сборка ядра** (тот же файл — бит-в-бит; другой — предупреждение), расхождение
  часов. Флаги в коде: `open_store(site=…)`, `Simulation(exp, on=…)`, `launch_cockpit(…, site=…)`,
  `py -3.14 -m client --site lab`.
- **Вычислитель** `synchrotronsim/compute.py` (`ComputeServer`, `ss_server.py compute`): TCP, рукопожатие с
  токеном и версией протокола, очередь заданий (по одному — ядро занимает все потоки). Клиент
  (`RemoteCompute.run`, через `Simulation(exp, on=site)`) фиксирует машину в хранилище площадки (черновик, если
  рабочая копия не зафиксирована) и шлёт **ссылку**; вычислитель берёт машину по ссылке, считает, кладёт прогон
  (zip папки) в хранилище; клиент получает прогон оттуда. Без сервера хранилища — шлётся документ машины, прогон
  отдаёт сам вычислитель. Проверено тремя процессами (хранилище, вычислитель, клиент): fb:3 — 23,5 с, ряды
  удалённого и локального прогона **бит-в-бит**.
- **Живой кокпит по сети** — `client/netlink.py` (`NetLink`, клиентская половина шва Link) и
  `synchrotronsim/live.py` (на вычислителе: сборка модели, `EngineThread` за InProcLink, пересылка сообщений и
  снимков ≤ 60 Гц, прогоны живого сеанса — в хранилище по окончании прохода). Кокпит строит интерфейс из
  **описания сеанса** (`client.engine.describe_session`: опыт, геометрия сцены, ондуляторы, контуры, оптика,
  наблюдаемые, экраны, машина) — одинаково для модели здесь и на вычислителе. NetLink помнит подписки, отметки
  записи, настройки экранов и записи, пуск и повторяет их в новом сеансе; зазоры переносятся в рукопожатии; пуск
  повторяется, когда интерфейс готов. Проверено на решётке 26 (вычислитель — отдельный процесс): сборка 28 с,
  прогон, тепловые карты ондулятора и линейки диполей, пересборка из окна «Опыт» 19 с с переносом всего.
- **Ядро на сервере (Linux):** `cmake -S . -B build-py -DCMAKE_BUILD_TYPE=Release -DSS_BUILD_PYTHON=ON
  -DPython_EXECUTABLE=$(which python3)` + `cmake --build build-py --target _engine` (нужен nanobind в Python сервера);
  общая ветка CMake (gcc + OpenMP) есть, но на Linux ещё не собиралась — проверить на сервере. Сборка с другим
  компилятором бит-в-бит с Windows не совпадёт — `Site.check()` об этом предупредит, паспорт прогона пишет платформу.
- **Не входит:** шифрование (TLS) — в локальной сети не используется; пользователи и права (один токен на
  площадку); повторное подключение живого сеанса при обрыве связи (сейчас — сообщение в статусе, пересборка
  кнопкой «Опыт…»).

## 11. Открытые вопросы

1. **Ветки ревизий.** Предложение: история машины линейная; вариант решётки — новая машина с `parent` от
   ревизии исходной (`26` → `26-ironfix`).
2. **Опыты.** `experiments`, `bench_experiments` и `fb_*` — один документ «опыт» с полем вида (bench / fb /
   cockpit / tracking) или разные виды документов. Предложение: один вид, разные разделы.
3. **Хранение рядов** — npz (сейчас) или HDF5/Parquet; на протокол не влияет.
4. **Доступ:** токен площадки достаточен для локальной сети или нужны пользователи и права.
5. **ОС сервера** — для сборки ядра (предполагается Linux).
